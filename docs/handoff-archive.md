- **2026-07-30 (2)**: 🚀✅ **§0-DEPLOY 9건 prod 백엔드 배포 완료** (#5 앱 버전 게이트 / #10 이메일 수집 중단 / #11 닉네임 24시간화 / #1 탈퇴 UX 재설계 / #14 탈퇴 사유 / #2 의견 보내기 / #4 모달 전환·성별 `OTHER` 제거 / #9ⓐ 자료형 통일 / #9ⓑ `amount.category` enum 전환).
  - **런북의 8단계 마이그레이션 SQL 을 안 탔다 — DB 를 통째로 재생성했다.** 사용자가 라이브 데이터 소멸을 승인해서, `docker compose down` → `tenk_db-data`·`tenk_uploads`·`tenk_dbinit` 볼륨 삭제 → `dbinit` 을 현재 `docs/schema.sql` 로 재시딩 → `pull && up -d` 로 MariaDB clean init. **재사용 가능한 절차는 [docker-deployment.md](docker-deployment.md) §5.7 에 런북으로 승격.**
  - **왜 그게 더 안전했나**: 8단계 SQL 은 전부 *데이터를 보존하며* 스키마를 맞추려는 작업이라, 보존이 필요 없어지는 순간 **위험만 남고 이득이 없다.** 특히 (f) `gender='OTHER'`→NULL, (h) `amount.category` 레거시→`ETC` 는 **이미지 재배포 전에 반드시** 쳐야 하는 순서 결합(빼먹으면 `@Enumerated(STRING)` 이 enum 에 없는 값을 만나 그 row 조회가 예외로 죽음)이었는데, 클린 재생성에선 그런 값 자체가 존재하지 않아 **함정이 성립하지 않는다.** (c) `DROP COLUMN` 의 비가역성도 마찬가지로 소멸. 결과 스키마가 `docs/schema.sql` 과 **정의상 일치**하는 것도 부수 이득 — 드리프트 가능성 0.
  - **이미지**: 윈도우에서 `docker buildx build --platform linux/arm64 -t hjson248/tenk:latest --push .` → `sha256:7aa572a8…`(arm64 확인). **맥 SSH 는 못 썼다** — `~/.ssh/id_ed25519` 가 실제로는 **PuTTY `.ppk`**(암호화)라 OpenSSH 가 못 읽고 ssh-agent 도 중지 상태. 맥 명령은 사용자가 직접 실행했고, `schema.sql`·배포 스크립트는 **Taildrop(`tailscale file cp`)** 으로 전달 + **md5 대조**(`610b8bc18b3ddef79b070103bf83276c`)로 무결성 확인. 시드 md5 는 볼륨 안에서 한 번 더 검증.
  - ✅ **서버 측 검증 전항목 통과**: `/api/challenges` → 401 `C0003` envelope / 버전 게이트 `1.0.0`→`LATEST`·`0.9.0`→`UPDATE_REQUIRED` / 테이블 10개(`app_config`·`withdrawal_feedback`·`feedback` 신규) / `app_config` 시드 1행 / badge 9행 / **`user` 에 `email` 없음**(#10) / 코드성 8개 컬럼(`provider`·`result`·`type`·`gender`·`role`·`reason_code`·`category`·`feedback.type`) **전부 `varchar`, `enum(...)` 0개**(#9ⓐ).

  - **관찰**: `app_config.updated_dt` 가 UTC 로 찍힌다 — compose 의 `TZ: Asia/Seoul` 이 **backend 에만** 있고 `db` 컨테이너엔 없어서 MariaDB 의 `DEFAULT current_timestamp()` 만 UTC. 도메인 시각(`created_dt`/`spent_dt`)은 전부 JPA 가 KST JVM 으로 박으므로 **기능 영향 없음**. 예전 KST 버그와 같은 계열이라 기록만 남긴다.
- **2026-07-30**: 🗄️✅ **DB 코드성 컬럼 정리(#9)** — 회의록 [decisions.md](decisions.md) "DB 코드성 컬럼 정리", 규칙은 [../CLAUDE.md](../CLAUDE.md) "코딩 컨벤션 — 백엔드". 커밋 `9ecc8d7`(축 1) → `b63ecab`(축 2) → `de2fabd`(E2E).
  - **백로그 문구가 절반만 가리키고 있었다.** 목록화해보니 **두 개의 다른 축**이 각각 어긋나 있었다 — ⓐ **DB 자료형**: `user.provider`·`challenge.result`·`badge.type` 만 네이티브 `ENUM`, 나머지 5개는 `VARCHAR` ⓑ **Java 매핑**: 8개 중 7개가 이미 `@Enumerated(STRING)`, `amount.category` 만 raw String. `@Enumerated(STRING)` 은 **자료형이 아니라 매핑 방식**이라 상대가 `ENUM` 이든 `VARCHAR` 든 `validate` 를 통과한다 — 그래서 아무도 몰랐다. 두 축을 뭉개면 "7개는 끝났다" 는 잘못된 결론이 나온다. **둘 다 실행.**
  - **ⓐ 네이티브 `ENUM` 3개 → `VARCHAR` (Java 코드 변경 0).** 핵심 논거는 **상수 목록이 코드와 DB 두 곳에 생긴다** — `AuthProvider.TEST` 가 코드에선 `@Deprecated` 인데 DB `ENUM` 엔 멀쩡히 살아 있었다. 값 변경마다 `ALTER` 가 붙는 것도 문제고, **바로 전날 `Gender.OTHER` 제거가 `VARCHAR` 라 `UPDATE` 한 줄로 끝난 게 실사례**였다. 그 외 함정: 중간 삽입·삭제 시 테이블 재구축 / `ORDER BY` 가 선언 순서 / **정수와 비교하면 인덱스로 해석**(`WHERE result = 1`). `ENUM` 의 최대 장점인 다중 쓰기 주체 방어는 앱이 DB 를 단독 소유해 해당 없음. **이 `ALTER` 만은 코드 배포와 순서 커플링이 없다**(양쪽 다 validate 통과).
  - **ⓑ `amount.category` → `SpendCategory` + `@Enumerated(STRING)`**, 컬럼도 `VARCHAR(255)→(20)`. raw String 의 근거였던 *"쓰기는 엄격, 읽기는 관대"*(2026-07-11 검증 도입 이전 자유 텍스트 보호)는 **유효기간이 지났다** — 레거시를 `ETC` 로 접으면 남는 건 방어 가치 없는 String 뿐이고, 지금이 가장 싼 시점(로컬 0건·라이브도 내부 테스터뿐). 클라가 이미 미매칭 코드를 '기타'로 폴백해 그려서 **화면상 변화 0**.
  - **변환 지점 설계가 이 작업의 실질 내용**: `SpendCategory.from()` **한 곳**에서만 변환하고 호출은 **엔티티 정적 팩토리 안**에서만. 서비스로 올리는 대안은 셋을 깬다 — ① 빈 카테고리가 A0005(`CATEGORY_CONTENT_REQUIRED`) 대신 A0008(`CATEGORY_INVALID`) 로 나가 **에러 코드가 뭉개짐** ② **무지출의 "카테고리 무시" 규칙이 깨짐**(파싱이 early return 보다 앞섬) ③ invariant 검증이 엔티티 밖으로 샘. 그래서 **`from()` 은 null·공백에 예외 대신 null 을 반환**하는 계약 — 이 한 줄이 두 에러 코드를 갈라놓는다.
  - **DTO 는 `String` 유지 → Flutter 변경 0.** 요청을 enum 으로 올리면 Jackson 파싱 실패가 A0008 의 한국어 메시지를 범용 400 으로 덮고, 응답은 클라와의 코드 계약이라 wire format 을 지켜야 한다. **이게 유일한 실질 리스크**라 회귀 가드(`AmountTest.response_emits_category_as_code_string`)를 따로 뒀다.
  - **🕳️ 함정 — 네이티브 SQL 테스트 헬퍼가 검증을 우회하고 있었다.** 전환 후 통합 테스트 **5건이 `No enum constant SpendCategory.x`** 로 깨졌다. `AmountRepositoryIntegrationTest`/`BadgeEventIntegrationTest` 가 시딩 속도를 위해 `INSERT` 로 `'x'`·`'test-category'` 를 박고 있었던 것 — **쓸 땐 통과하고 읽을 때 죽는** 자리다. 고친 건 사소하지만 **enum 전환이 실제로 잡아낸 종류의 문제**이고, String 이었다면 영원히 안 드러났다.
  - **룩업 테이블은 도입 안 함** — 기준("코드 말고 그 값에 딸린 다른 정보가 있나")에 맞는 건 `badge`(조건값·아이콘 경로) 하나뿐이고 이미 그렇다. `SpendCategory` 만 애매했는데 **아이콘이 Dart `IconData` 라 DB 에 못 넣어**, 옮기면 "라벨은 DB·아이콘은 코드" 로 오히려 갈라진다.
  - ✅ **테스트 200개 전원 통과**(신규 5 — `SpendCategoryTest` 4 + wire format 가드 1) + **에뮬 E2E 검증 완료** — 단위가 못 덮는 구간(Jackson 직렬화 → Flutter 파싱 → 카테고리 아이콘·라벨 매핑)이 실제로 이어지는지 확인.

- **2026-07-29 (2)**: ⚖️✅ **성별 수집·변경 회의(#16) — 현행 유지, 코드·스키마·문서 변경 0.** 회의록 [decisions.md](decisions.md) "성별 수집·변경", 규칙은 [../CLAUDE.md](../CLAUDE.md) "성별 (선택 수집)".

  - **노이즈는 편집이 아니라 최초 입력에서 들어온다.** 오탭은 편집을 막으면 **영구 고착**돼 우려한 오염을 오히려 만들고, 일부러 거짓 입력하는 경로는 막든 안 막든 동일(거짓이 박제될 뿐), 호기심 변경은 **바꿔도 화면에 아무 변화가 없어** 탐색할 게 없다. 전제도 한 겹 어긋나 있었다 — **우리가 여는 건 '성별 변경'이 아니라 '입력값 정정'** 이고, 이 컬럼에 든 건 실제 성별이 아니라 *사용자가 입력한 값*이라 실제로 틀린다.

  - **신설 규칙 — 변경 이력·변경 시각을 남기지 말 것.** "통계 신뢰도" 를 걱정하면 자연히 나오는 대안이지만, 성별 변경 이력은 일반 개인정보가 아니라 **트랜스젠더 아웃팅 위험이 있는 정보**다. **지금 이력이 안 남는 건 우연이라** 누가 "감사 목적" 으로 컬럼 하나만 붙여도 조용히 위험이 생긴다 — 그래서 규칙으로 못 박았다.
