# Play Console — 앱 콘텐츠 답안지

> **이 문서의 용도**: Play Console → **정책 및 프로그램 → 앱 콘텐츠** 의 각 폼에 무엇을 입력할지,
> 그리고 **그 답이 코드의 어느 사실에 근거하는지**를 한곳에 모은 참조 문서.
> 폼은 콘솔에서 사람이 직접 채운다 — 여기 있는 건 그때 그대로 옮겨 적을 답이다.
>
> **상태 (2026-09-15)**: §1~§7 **앱 콘텐츠 전 항목 콘솔 입력 완료.** 남은 건 §9 **스토어 설정·등록정보**.
>
> **갱신 규칙**: 수집 항목·권한·SDK·연령 정책이 바뀌면 **이 문서 + [privacy.html](../tenk-backend/src/main/resources/static/privacy.html) + Play Console 폼 3곳을 같이** 갱신할 것.
> 셋 중 하나만 바뀌면 심사에서 불일치로 걸린다. 진행 상태는 [handoff.md](handoff.md).

작성 기준일: 2026-07-20 (최종 갱신 2026-09-15) · 대상: applicationId `com.hjson.tenk_app` (표시 이름 **TenK**)

> 스토어 등록명도 **`TenK`** 로 이미 등록돼 있다 (2026-07-28 확인). 앱 표시 이름은 코드에서 바뀌지만

## 2. 앱 액세스 권한 (App access)

**"앱의 전체 또는 일부에 액세스 권한이 제한됩니다"** 를 선택하고 심사자용 접근 방법을 제공해야 한다.
카카오 로그인 전용이라 심사자가 그냥은 못 들어간다.

> ✅ **확정 — 데모 카카오 계정 방식** (2026-07-25 테스터 로그인 회의 결정, [decisions.md](decisions.md) "테스터 로그인 회의").
> 앱 내 우회 테스트 로그인은 **완전히 제거**했고(코드에 흔적 없음), 심사자는 데모 카카오 계정으로 순정 앱에
> 로그인한다. 이메일 전용 카카오계정(전화번호·본인인증 없이 `accounts.kakao.com` 가입)이 데모 계정으로
> 동작함을 에뮬레이터에서 확인했다.

**답안 — 데모 카카오 계정 로그인**:

⚠️ **폼 안내문은 영어로 써야 한다** — 콘솔이 *"정보는 영어로 제공해야 합니다"* 라고 명시한다.
'앱 액세스에 필요한 기타 정보' 칸은 **500자 제한**이라 아래는 478자로 맞춰뒀다.

```
앱에 제한된 부분이 있나요? : 예
이름 : Kakao demo account
사용자 이름/이메일 : <데모 카카오계정 이메일>
비밀번호 : <데모 카카오계정 비밀번호>
[v] 이 로그인 세부정보는 앱 내 모든 기능·콘텐츠에 대한 전체 액세스 권한을 제공합니다
```

앱 액세스에 필요한 기타 정보 (478자):

```
Kakao login is the only sign-in method. Tap the yellow Kakao login button.
No 2-step verification is required.

Signing in starts the normal first-time flow: enter a date of birth
(e.g. 1990-01-01), then accept the two required agreements.

The account is pre-loaded with sample challenges in every state. Open the
one marked "확정 대기" (awaiting result) and tap the confirm button to reach
the badge and result card screens.

No paid or premium content exists in this app.
```

- **생년월일 예시를 반드시 적는다** — 연령 게이트는 컷오프(만 14세)를 **일부러 안 알려주는** 설계(§5)라,
  안 적어주면 심사자가 어떤 값을 넣어야 통과인지 알 수 없다.
- `No 2-step verification is required.` 는 **새 기기 로그인 재현에서 실제로 안 떴을 때만** 남긴다.
  뜨면 그 줄을 지우고 통과 방법(이메일 인증코드 수신함 접근 등)을 대신 적는다 — 폼이
  *"만료되지 않는 재사용 가능한 로그인 세부정보"* 를 요구하므로 심사자가 못 뚫으면 그대로 거부다.
  ✅ **확인 완료 (2026-09-15)** — 새 기기(에뮬레이터·폰) 로그인에서 카카오 **추가 인증이 뜨지 않았다.** 문구 그대로 제출했다.

**준비물·주의**:
- **데모 카카오 계정을 1개 생성**해 위 칸에 아이디/비밀번호를 적는다. 아직 미생성 → 제출 전 실행 항목([handoff.md](handoff.md) §0).
- **데모 계정은 영구 유지** — Play 는 업데이트마다 바이너리를 재심사하므로 첫 심사만이 아니다.
- 새 기기(심사자 단말) 로그인 시 카카오가 추가 인증을 띄울 수 있다. 전화번호 없는 이메일 전용 계정이면 이메일
  인증코드로 나올 가능성이 높지만 카카오 정책이라 100% 보장은 아니다 — **제출 전 한 번 새 기기에서 재현**해
  추가 인증이 안 뜨거나 이메일 코드로 통과되는지 확인할 것. 뜨면 Review Notes 에 대응법을 적는다.
- 프로덕션 AAB 는 아무 특별 dart-define 없이 빌드하면 된다(테스트 로그인은 코드에서 제거됨). 서버도 테스트
  로그인 엔드포인트가 없다. **내부 테스터의 시딩**은 실제 카카오 계정을 DB 에서 `role='TESTER'` 로 승격해 쓴다.
- ⚠️ **데모 계정을 TESTER 로 승격하지 말 것** — '내 정보'에 '테스트 데이터 재생성' 버튼이 노출되고, 심사자가
  누르면 아래에서 준비한 데이터가 **통째로 wipe** 된다. 아래 §2-1 의 SQL 은 role 게이트를 거치지 않으므로
  **승격이 애초에 필요 없다.**

### 2-1. 데모 계정 준비 — 온보딩은 남기고 데이터만 심는다

> 2026-09-07 확정. **심사자가 봐야 할 것이 두 갈래로 갈린다** — ① 가입 흐름(연령 심사·필수 동의)은
> **가족 정책 대상 앱이라 정책적으로 가장 중요한 화면**이고, ② 확정 → 배지 → 결과 카드는 **날짜가 지나야
> 자연 발생**해서 갓 가입한 계정으로는 **하루를 기다려도 못 본다**(`확정`은 `today > endDate` 조건).
> 계정 하나로 둘 다 보여주는 방법이 아래다.

**원리**: `user` 행은 [AuthService.provisionUser](../tenk-backend/src/main/java/com/hjson/tenk/domain/auth/AuthService.java)
가 **카카오 로그인 순간** 만들고, 그때 `birth_date`·`terms_agreed_dt`·`privacy_agreed_dt` 는 **전부 NULL** 이다.
게이트는 그 NULL 을 보고 **클라이언트가 라우팅**할 뿐이라, 계정 행만 생긴 상태에서 챌린지 데이터를 붙여두면
심사자는 가입 흐름을 그대로 탄 뒤 홈에서 그 데이터를 만난다.

**절차** — [seed-review-demo.sql](seed-review-demo.sql) 한 파일로 끝난다 (2026-09-15 확정):

1. 데모 계정으로 **prod 앱에 카카오 로그인 1회** → 연령 확인 화면에서 **그대로 멈춘다** (계정 행만 생긴다)
2. DBeaver 에서 [seed-review-demo.sql](seed-review-demo.sql) 을 열고 **스크립트 전체 실행(Alt+X)** — Ctrl+Enter 는 한 문장만 돈다
3. 첫 SELECT 의 `user_id` 가 NULL 이면 계정이 없는 것이다(모든 INSERT 가 가드돼 아무것도 안 바뀐다).
   맨 아래 검증 결과가 파일 안의 **기대값 주석**과 같은지 확인

- **왜 SQL 인가**: 앱의 '테스트 데이터 재생성' 버튼은 게이트 **안쪽** 메뉴에 있어, 게이트를 비워둔 계정으로는
  누를 수 없다. 처음엔 *온보딩 통과 → TESTER 승격 → 버튼 → 강등 → 게이트 3컬럼 NULL 되돌리기* 6단계를 적었는데,
  SQL 은 **게이트도 role 도 거치지 않아** 그 우회가 통째로 사라진다. `/api/dev/seed` 를 직접 부르는 안(서버 시크릿으로
  토큰 발급)도 있었지만 **prod 자격증명을 쓰는 경로라 기각**했다.
- **서비스와 동일함을 실측했다** — 같은 계정에 `/api/dev/seed`(서비스)와 이 SQL 을 차례로 돌려 **기록 17건 ·
  배지 7개 · 챌린지 5개가 금액·카테고리·날짜·시각까지 일치**함을 로컬에서 대조했다.
  ⚠️ **[TestSupportService.seedAll](../tenk-backend/src/main/java/com/hjson/tenk/devtools/TestSupportService.java) 을
  바꾸면 이 SQL 도 같이 고칠 것** — 배지는 계산이 아니라 **결과를 박아 넣는** 방식이라 데이터만 바꾸면 어긋난다.
- ⚠️ **날짜는 KST 로 직접 계산한다** — prod DB 컨테이너엔 TZ 설정이 없어 **UTC** 라, `CURDATE()` 를 쓰면 한국
  오전 9시 전에 돌렸을 때 모든 날짜가 하루 밀린다(앱은 KST 로 판정). 스크립트가 `UTC_TIMESTAMP() + 9h` 를 쓰는 이유.
- **카카오 회원번호는 로컬·prod 가 같다** — 회원번호는 카카오 **앱 단위**로 발급되고 `tenk.auth.kakao.app-id` 가
  공통 yaml 하나뿐이다. 그래서 로컬에서 먼저 리허설한 계정을 그대로 prod 에 쓸 수 있다.

**결과**: 심사자는 로그인 → **연령 게이트 → 동의 게이트 → 홈에 5종 챌린지**를 본다.

- ⚠️ **닉네임 설정 화면만은 구조적으로 못 보여준다.** `isNewUser` 는 *"이 호출이 계정을 만들었나"* 라서
  계정이 존재하는 순간 영구히 false 이고, PK 를 미리 확보한다는 것 자체가 계정 생성을 뜻한다. 닉네임
  **기능**은 '내 정보 → 닉네임'으로 접근 가능하므로 손해는 이 한 화면뿐이다. **되살리려면 시딩을 포기해야 한다**
  (그 경우 순정 계정 하나를 그대로 주고 위 안내문에서 sample-challenge 문단을 뺀다).
- ⚠️ **시딩에는 유통기한이 있다 — 제출 직전에 돌릴 것.**
  [TestSupportService.seedAll](../tenk-backend/src/main/java/com/hjson/tenk/devtools/TestSupportService.java) 이
  **시딩한 날 기준 상대 날짜**로 만들기 때문이다:

  | 챌린지 | 기간 | 그 상태가 유지되는 기간 |
  |---|---|---|
  | 시작 전 | `+3 ~ +12` | **2일** (3일째부터 '진행 중') |
  | 진행 중 | `-4 ~ +5` | **5일** (6일째부터 '확정 대기') |
  | 확정 대기 | `-12 ~ -2` | 계속 |
  | 완료 성공/실패 | `-25 ~ -15` | 계속 |

  즉 **"5종 전부"는 시딩 후 2일까지**고, 12일이 지나면 확정 대기 3 + 완료 2 만 남는다(확정→결과 카드는 계속 된다).
  **업데이트를 제출할 때마다 스크립트를 다시 돌린다** — 그 계정의 데이터를 지우고 다시 만들어 반복 실행이 안전하다.
- ⚠️ **심사자가 이 계정으로 탈퇴를 테스트하면 데이터가 위험하다.** soft delete 라 재로그인 시 U0007 선택
  다이얼로그가 뜨고, **'탈퇴 철회'를 고르면 전부 복구**되지만 **'새로 시작'을 고르면 즉시 파기**된다.
  그 경우 새 계정이 생기므로(회원번호는 같다) 1단계(로그인 후 멈춤)부터 다시 하면 된다.

| 사용자 위치 공유 | **아니요** — 위치 권한·수집 없음 |
| 개인 정보를 다른 사용자에게 공개 | **아니요** |
| 디지털 구매 / 인앱 결제 | **아니요** |
| 사용자 생성 콘텐츠(UGC) | **아니요** — 영상은 본인만 보고, 공유는 OS 공유 시트로 사용자가 직접 내보내는 것뿐 |

> 헷갈리기 쉬운 지점: 영상 export 후 `share_plus` 로 공유할 수 있지만, 이는 **기기 OS 의 공유 기능**이지
> 앱이 제공하는 사용자 간 공유가 아니다. IARC 의 UGC/상호작용 질문은 "아니요" 가 맞다.

예상 등급: 전체이용가 (한국 GRAC 기준 전체이용가 / ESRB Everyone).

## 6. 데이터 안전 (Data safety)

### 6-1. 개요 질문

| 질문 | 답 |
|---|---|
| 앱이 사용자 데이터를 수집하거나 공유하나요? | **예 (수집함 / 공유 안 함)** |
| 전송 중 데이터가 암호화되나요? | **예** — 전 구간 HTTPS |
| 계정 생성 방법 | **OAuth** — 카카오 로그인 (자체 아이디/비밀번호 없음) |
| 계정 삭제 요청 URL | `https://tenk.hjson248.com/delete-account.html` |
| 계정을 삭제하지 않고 일부 데이터 삭제 요청 (선택 항목) | **비워둔다 / 아니요** — 앱의 챌린지 삭제는 **soft delete**(`Challenge.softDelete()`)라 계정 파기 때까지 서버에 남는다. "삭제된다"고 신고하면 사실이 아니다 |
| 독립적인 보안 검토(MASA)를 거쳤나요? | **아니요** (선택 안 함) |

> **"공유"의 정의 주의**: Play 에서 공유 = *제3자에게 데이터를 전송*. 카카오 로그인은 우리가 카카오로부터
> 정보를 **받는** 것이라 공유가 아니다. 영상·기록도 자체 서버에만 저장된다 → **전 항목 공유 아니요**.

### 6-2. 수집 항목별 답안

모든 항목 공통: **공유 = 아니요**, **수집 = 예**, **처리 방식 = 데이터가 서버로 전송되어 저장됨**(임시 처리 아님).

> ✅ **2026-09-15 콘솔 제출본**. Play 폼은 **데이터 유형 단위로 한 번씩만** 묻는다 — 아래 '항목 단위' 표를
> 유형별로 합쳐 답했다. **한 유형 안에 필수·선택이 섞이면 필수**, 목적은 합집합.

**콘솔에 입력한 값 (유형 단위)**:

| Play 데이터 유형 | 합쳐진 항목 | 필수/선택 | 목적 |
|---|---|---|---|
| 개인 정보 → **이름** | 닉네임 | 필수 | 앱 기능, 계정 관리 |
| 개인 정보 → **이메일 주소** | 의견·문의 답변받을 이메일 | 선택 | 앱 기능 |
| 개인 정보 → **사용자 ID** | 카카오 회원번호 | 필수 | 앱 기능, 계정 관리 |
| 개인 정보 → **기타 정보** | 생년월일(필수) · 성별(선택) | **필수** | 앱 기능, **분석** |
| 금융 정보 → **기타 금융 정보** | 지출 금액·카테고리·내용 | 선택 | 앱 기능 |
| 사진 및 동영상 → **동영상** | 2초 기록 영상 | 선택 | 앱 기능 |
| 앱 활동 → **기타 사용자 생성 콘텐츠** | 챌린지 이름·한 줄 평·의견 내용·문의 내용·탈퇴 사유 | 선택 | 앱 기능, **분석** |

> ⚠️ **분류 정정 (2026-09-15)** — 처음엔 의견·문의·탈퇴 사유를 *개인 정보 → 기타 정보* 에 넣었는데, 구글 정의상
> 그 칸은 **"생년월일·성별 같은 개인정보"** 이고 **자유 서술("open-ended responses")·메모("notes")의 정해진 자리는
> *앱 활동 → 기타 사용자 생성 콘텐츠*** 다. 챌린지 이름·한 줄 평도 같은 성격이라 함께 옮겼다.
> 목적 목록에 '고객 지원' 은 없고 구글 정의상 **앱 기능** 에 포함된다.

**항목 단위 원장** (근거 추적용 — 콘솔은 위 표로 합쳐 입력):

| 실제 항목 | Play 유형 | 필수/선택 | 목적 |
|---|---|---|---|
| 닉네임 | 이름 | 필수 | 앱 기능, 계정 관리 |
| 카카오 회원번호 | 사용자 ID | 필수 | 앱 기능, 계정 관리 |
| 생년월일 | 기타 정보 | 필수 | 앱 기능(이용 가능 연령 확인) |
| 성별 | 기타 정보 | **선택** | **분석** (이용자 통계) |
| 지출 금액·카테고리·내용 | 기타 금융 정보 | 선택 | 앱 기능 |
| 2초 영상 | 동영상 | 선택 | 앱 기능 |
| 챌린지 이름 · 한 줄 평(memo) | 기타 사용자 생성 콘텐츠 | 선택 | 앱 기능 |
| 탈퇴 사유(코드 + '기타' 자유 서술) | 기타 사용자 생성 콘텐츠 | **선택** | **분석** (이탈 원인 파악) |
| 의견 보내기 내용 | 기타 사용자 생성 콘텐츠 | **선택** | 앱 기능(고객 지원) |
| 문의 내용 | 기타 사용자 생성 콘텐츠 | **선택** | 앱 기능(고객 지원) |
| 의견·문의 답변받을 이메일 | 이메일 주소 | **선택** | 앱 기능(고객 지원) |

**이메일을 넣지 않는 이유** (2026-07-26): 카카오 '카카오계정(이메일)' 동의항목은 개인 개발자 일반 앱에서
'권한 없음'이라 애초에 내려오지 않았고, 서비스 기능에도 쓰이지 않아 **수집 자체를 접었다**(컬럼도 삭제).
비즈 앱 전환으로 받아올 수는 있지만 쓸 곳이 없어 최소수집 원칙에 어긋난다. 되살리면 이 표 + privacy.html
수집표·제3자 제공표를 함께 갱신할 것.

**"선택"으로 답하는 근거**: 지출 기록과 영상은 사용자가 입력·촬영을 선택했을 때만 수집된다.
로그인만 하고 아무것도 기록하지 않아도 앱은 동작한다. **성별**은 가입 흐름에 없고 '내 정보' 화면에서
본인이 원할 때만 입력하며, 언제든 '입력 안 함'으로 되돌려 삭제할 수 있다 — 기능은 이 값을 전혀 쓰지 않는다.

> **성별만 목적이 '분석'인 이유**: 나머지 항목은 서비스 기능 제공에 필요하지만 성별은 이용자 통계 용도뿐이다.
> 목적을 '앱 기능'으로 적으면 실제 동작과 어긋난다. 이 항목을 **필수로 바꾸거나 가입 흐름으로 옮기면
> 개인정보 최소수집 원칙에 걸리므로** 선택·사후 입력 구조를 유지할 것.

> ℹ️ **아래 "사용자와 연결" 구분은 Play 폼에 나오지 않았다** (2026-09-15 제출 시 확인). 연결 여부는 **Apple 앱스토어
> '앱 개인정보 보호'** 의 개념이라, iOS 출시 때 이 메모를 그대로 쓴다.

**⚠️ 탈퇴 사유는 "사용자와 연결됨 = 아니요"로 답한다** (2026-07-28 추가). 항목마다
*수집 여부*와 *사용자 신원과 연결되는지*를 따로 묻는 폼에서는, 탈퇴 사유는 `withdrawal_feedback` 테이블에
**user_id 없이** 저장되어 어느 계정이 남겼는지 알 수 없다. 전송 자체는 로그인 상태에서 일어나므로
**수집 = 예**로 답하되 **연결 = 아니요**로 답하는 조합이 실제 동작과 일치한다.

> **privacy.html 수집표에는 일부러 넣지 않았다.** 계정과 연결되지 않아 국내법상 개인정보가 아니기
> 때문이고, 개인정보 수집 항목 표에 비개인정보를 섞으면 오히려 고지가 흐려진다. **즉 이 한 항목만
> Play 폼과 privacy.html 이 의도적으로 다르다** — 아래 §8 대조 체크리스트에서 이것만 예외로 볼 것.
> 나중에 이 테이블에 계정을 식별할 값을 추가하면 그 즉시 개인정보가 되므로 privacy.html 수집표와
> 보관 기간 규칙(탈퇴 후 1개월)까지 함께 적용해야 한다.

**⚠️ 의견 보내기는 한 화면 안에서 두 항목의 답이 갈린다** (2026-07-28 추가).
`feedback` 테이블도 **user_id 없이** 저장하므로 의견 **내용**은 탈퇴 사유와 똑같이
**수집 = 예 / 연결 = 아니요**다. 반면 **회신용 이메일은 그 자체가 개인 식별자**라
**연결 = 예**로 답해야 한다. 한 화면에서 보냈다고 두 항목을 같은 값으로 묶지 말 것.

> **이메일만 privacy.html 수집표에 넣은 이유**도 같은 선이다 — 의견 내용은 계정과 연결되지 않아
> 개인정보가 아니고, 이메일은 개인정보다. 그래서 privacy.html §1 에는 '의견 보내기 (선택) —
> 답변받을 이메일 주소' 한 줄만 있고 의견 내용은 없다. **§8 대조 체크리스트의 두 번째 예외.**
> 참고로 **이메일은 답변 후 파기, 미회신 시 최대 1년**이 상한이고 이건 문서만의 약속이 아니라
> 매일 새벽 도는 배치(`FeedbackRetentionScheduler`)가 강제한다 — 기간을 바꾸면 코드도 같이.

**⚠️ '문의하기'는 의견 보내기와 답이 반대다** (2026-08-05 추가).
`inquiry` 테이블은 **`user_id` 를 저장**하므로 문의 내용·회신 이메일 **둘 다 연결 = 예**다.
열람·정정·삭제 요구는 누구의 정보에 대한 요청인지 확인돼야 처리할 수 있어 익명일 수가 없다.
그래서 **privacy.html §1 수집표에도 두 항목이 모두 들어가 있다** — 의견 보내기처럼 한쪽만 넣는
예외가 아니다(§8 대조 체크리스트에서 예외로 세지 말 것). 보관은 **회원 탈퇴 시까지**이고 계정이 파기될 때 함께 지워진다
(2026-08-06 변경 — 그 전엔 '답변 후 3개월' 배치가 있었다).

### 6-3. 수집하지 않는다고 답할 항목 (자주 헷갈리는 것들)

| 항목 | 답 | 근거 |
|---|---|---|
| 오디오 → 음성 녹음, 음악, 기타 오디오 | **미수집** | `enableAudio: false` — 영상 트랙에 오디오가 들어가지 않는다. 매니페스트에 `RECORD_AUDIO` 가 선언돼 있지만 **권한 선언 ≠ 수집**이며 Play 폼은 실제 수집 여부를 묻는다 |
| 위치 | 미수집 | 위치 권한·API 미사용 |
| 연락처 / 캘린더 / 문자 / 통화 기록 | 미수집 | 관련 권한·API 없음 |
| 기기 또는 기타 ID (광고 ID 포함) | 미수집 | 광고·애널리틱스 SDK 없음 |
| 앱 활동 → 앱 상호작용·검색 기록·설치된 앱·기타 작업 | 미수집 | 행동 로깅 SDK 없음. ⚠️ 단 **같은 앱 활동 안의 '기타 사용자 생성 콘텐츠'는 수집**으로 신고했다(§6-2) |
| 앱 정보 및 성능 (크래시 로그, 진단) | 미수집 | 크래시 리포팅 SDK 없음 |
| 결제 정보 / 구매 내역 | 미수집 | 인앱 결제 없음 |

> ⚠️ **판단이 갈릴 수 있는 한 지점 — 서버 접속 로그.** privacy.html §1 은 "서비스 이용 과정에서 생성되는
> 접속 로그 및 오류 기록"을 명시하고 있다. 이는 웹서버 운영 로그이고 사용자 계정 데이터로 DB 에 저장되지
> 않으므로 위 표대로 **"앱 정보 및 성능: 미수집"** 으로 답하는 게 통상적이다. 추후 크래시 리포팅
> SDK(Firebase Crashlytics 등)를 도입하면 **그 즉시 "크래시 로그: 수집"으로 바꿔야 한다.**

> ⚠️ **카테고리와 설명 문구는 [handoff.md](handoff.md) §1-I '만원 챌린지' 회의에 걸려 있다** — 아래는 현 컨셉 기준 초안이고,
> 결론이 바뀌면 콘솔에서만 고치면 된다(앱 업데이트 불필요).

### 9-1. 스토어 설정 (앱 카테고리 · 연락처)

| 칸 | 입력 |
|---|---|
| 앱 또는 게임 | **앱** |
| 카테고리 | **라이프스타일** (임시 — §1-I). 포지셔닝이 *절약·금융* 이 아니라 *챌린지 + 공유 재미* 라서. 금융 카테고리는 금융 서비스 앱으로 읽힌다 |
| 이메일 | `support.tenk@gmail.com` — ⚠️ **스토어에 공개된다.** privacy·terms 에 고지한 주소와 같아야 한다 |

### 9-2. 스토어 등록정보

| 칸 | 규격 | 상태 |
|---|---|---|
| 앱 이름 | 30자 | **TenK** (런처 이름과 맞춘다) |
| 간단한 설명 | 80자 | 초안 ↓ |
| 자세한 설명 | 4,000자 | 초안 ↓ |
| 앱 아이콘 | 512×512 PNG | `tenk_app/assets_src/icon/play_store_512.png` (#25 로 마크가 커진 새 버전) |
| 그래픽 이미지 | **1024×500** PNG/JPEG | ❌ **미제작 — 필수** |
| 휴대전화 스크린샷 | 2~8장 | ❌ **미제작 — 최소 2장 필수** |
| 태블릿 스크린샷 | — | 생략 (세로 전용 폰 앱) |

⚠️ **스크린샷은 긴 변이 짧은 변의 2배 이하여야 업로드된다.** 요즘 폰(20:9, 예 1080×2400)은 **2.22배라 거부**된다.
에뮬레이터를 `adb shell wm size 1080x1920` 으로 바꿔 찍으면 **9:16 이 네이티브로** 나와 잘라낸 흔적이 없다
(끝나면 `adb shell wm size reset`). 로컬 계정에 시딩 데이터를 넣고 목록·상세·배지 모달·결과 카드를 찍는다.

**설명 문구 원칙** — ⚠️ **앱 안에 '함께하기' 기능(그룹 챌린지·랭킹·피드)은 없다.** 콘텐츠 등급(§4)에서도
*사용자 간 상호작용 없음* 으로 답했으므로 "친구와 함께 도전" 같은 표현은 쓰지 않는다 — 스토어 설명이 실제 기능과
다르면 메타데이터 정책 위반이다. 공유는 **결과 카드·영상을 SNS·친구에게 자랑하는 것**(OS 공유 시트)으로 푼다.
'만원 챌린지'는 서비스 컨셉 이름이라 써도 되지만, 목표 금액이 고정이 아니므로 **"목표 금액과 기간은 마음대로"** 를 붙인다.

**간단한 설명**:
```
만원으로 버티는 챌린지! 2초 영상으로 기록하고, 결과 카드로 자랑해 보세요.
```
대안: `하루 2초 영상으로 남기는 만원 챌린지. 끝나면 결과 카드와 영상으로 자랑하세요!`

**자세한 설명**:
```
만원으로 며칠이나 버틸 수 있을까요?
TenK는 정해진 기간 동안 목표 금액 안에서 살아보는 '만원 챌린지' 앱이에요.

■ 2초 영상으로 남기는 하루
오늘 산 커피도, 아무것도 안 산 날도 2초 영상 한 컷이면 기록 끝.

■ 쌓일수록 반짝이는 배지
매일 이어서 기록하고 무지출 날을 모으면 배지가 하나씩 열려요.
챌린지에 성공하면 트로피까지!

■ 끝나면 자랑할 차례
챌린지가 끝나면 결과를 한 장의 카드로 정리해 드려요.
그동안 찍은 영상은 한 편의 영상으로 이어 붙일 수 있어요.
갤러리에 저장하거나 친구에게, SNS에 바로 공유해 보세요.

■ 이런 것도 돼요
• 목표 금액과 기간(최대 30일)은 마음대로
• 여러 챌린지를 동시에 진행
• 기록을 잊지 않게 알려주는 알림
• 광고 없이 깔끔하게
• 카카오 계정으로 간편하게 시작
```
- 모든 문장이 현재 기능에 대응한다(2초 영상 · STREAK/NO_SPEND 배지 · 성공 트로피 · 결과 카드 · 영상 합본 · 저장/공유 ·
  최대 30일 · 동시 진행 · 로컬 알림 · 광고 SDK 없음 · 카카오 로그인). ⚠️ **광고를 도입하면 "광고 없이" 줄을 지울 것.**
