## 관리자 패널 (2026-08-06)

> 백로그 #27(문의·의견 운영 도구 4건 묶음). ⑥[앱 버전 게이트](#앱-버전업데이트-게이트-회의)의 결정 4와 ⑳[문의 창구 정리](#문의-창구-정리-2026-08-05)의 "관리자 UI 는 여전히 짓지 않는다"를 **뒤집는 회의**다. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "관리자 패널".
> **결론: 짓는다. 다만 SQL 의례를 대체하는 최소한만.**

### 진단 — 백로그 ①의 문제의식이 반대 방향이었다

백로그는 *"접수번호로 PK 를 노출하면 enumeration"* 을 걱정하고 있었다. 코드를 열어보니 **정반대였다**:

- `InquiryService` 의 도착 알림 본문에 **`inquiry_id` 가 아예 없었다** (유형·회신·계정·접수·본문뿐).
- 리마인드 본문의 SQL 은 `WHERE inquiry_id=?;` — **물음표 그대로**였다.

즉 처리 표시를 하려면 ① SSH ② `docker compose exec db mariadb` ③ **`SELECT` 로 id 찾기** ④ `UPDATE` 의 4단계였다. **아픈 곳은 PK 가 새는 게 아니라 식별자가 안 나가서 SQL 을 못 치는 것**이었다. enumeration 은 *사용자에게* 번호를 보여줄 때 생기는 위험인데, 앱은 접수번호를 보여주지 않고 '내 문의 내역' 화면도 없다.

### 왜 방침을 뒤집었나

⑥ 에서 정한 패널 도입 트리거는 **UGC 모더레이션**이었고 그건 아직 안 왔다. 그럼에도 지은 이유:

- **사용자 판단이었다** — *"간단하게 기본적인 기능만. 문의 처리나 유저 승격이나. 그럼 지금 사이클에 없앨 수 있는 불필요한 부분도 없앨 수 있을 거고."*
- 실제로 **흡수 대상이 문의 하나가 아니었다.** ⑥ 이 *"그때 이 값들이 전부 DB 행 편집이라 패널에 자연히 흡수"* 라고 예고한 그대로 — 문의 처리 · 의견 열람 · TESTER 승격 · `app_config` 4가지가 한 화면 묶음으로 사라진다.
- ⭐ **백로그 4건 중 2건이 패널로 소멸했다.** ①(접수번호)은 화면에서 클릭하니 사람이 id 를 옮겨적을 일이 없어져 **별도 컬럼도, 알림에 id 를 싣는 일도 필요 없어졌고**, ③(미처리 조회)은 목록 화면이 곧 답이다. 남은 건 ②(처리 메모 컬럼 하나)와 ④(알림 본문)뿐.

### 결정 1 — 화면이 아니라 **인증**이 이 작업의 몸통이다

착수 전 조사에서 나온 블로커. 앱 로그인은 **카카오 모바일 SDK 전용**이라 브라우저에 진입로가 없고, `SecurityConfig` 는 `formLogin`·`httpBasic`·`csrf` 가 전부 disable 에 `STATELESS` 다. 즉 "간단한 화면 몇 개"가 아니라 **인증 스택을 새로 세우는 일**이었다. 판단에 중요한 정보라 착수 전에 먼저 알렸다.

### 결정 2 — 보안 체인을 2개로 쪼갠다 (앱 인증 무변경)

`@Order(1)` + `securityMatcher("/admin/**")` 로 패널 체인이 먼저 받고, 나머지는 기존 체인이 그대로. **전역으로 세션·CSRF 를 켰다면 앱이 401 JSON 대신 로그인 화면으로 리다이렉트되고 POST 마다 CSRF 를 요구하게 된다** — 앱의 인증 계약이 통째로 바뀌는 것이다. 이건 단위 테스트로 확인할 수 없어서 통합 테스트에 **"앱 API 는 여전히 401 `C0003`" / "앱 POST 는 CSRF 없이 통과"** 두 건을 명시적 가드로 박았다.

### 결정 3 — 관리자 계정은 `admin_user` 별도 테이블 (사용자 제안을 조정)

사용자 제안은 *"언젠가 앱 자체 계정이 생기면 이메일·비밀번호가 필요하니 `user` 컬럼에 추가하자"* 였다. 미래를 보는 관점은 맞지만 `user` 스키마를 열어보고 **분리를 권고했고 사용자가 수용**했다:

| 넣었을 때 벌어지는 일 | 근거 |
|---|---|
| **가짜 공급자 값**이 필요해진다 | `(provider, provider_user_id)` NOT NULL + UNIQUE. `AuthProvider.TEST` 가 정확히 그렇게 생겼다가 지금 `@Deprecated` 잔재로 남았다 |
| 그 행이 **이용자용 불변식에 전부 참여** | 동의 미완 · 연령 미확인 · 파기 배치 스캔 대상 · 사용자 통계 오염 |
| **DROP 한 컬럼을 되살리게 된다** | `user.email` 은 #10 에서 수집을 접으며 지웠고 schema.sql 에 "되살리려면 privacy·Play 를 함께" 체크리스트까지 붙어 있다 |

**핵심 논거: 두 계정의 생명주기가 다르다.** 이용자는 가입→동의→연령→탈퇴→파기 파이프라인을 타고 운영자는 아무것도 안 탄다. `UserRole.ADMIN` 주석이 이미 *"수신자가 늘면 `user` 가 아니라 별도 운영자 테이블"* 이라는 같은 결론을 예고해 뒀다.

**"나중에 중복 아니냐"에 대한 답**: 안 중복된다. 이용자 자체 계정이 생기면 그때 `user.email`/`password` 를 추가하는데, **그 시점엔 privacy.html 수집표·Play 폼 갱신이 어차피 따라온다** — 지금 미리 넣어도 그 작업이 면제되지 않고 **문서 갱신만 1년 앞당겨질 뿐**이다.

> 업계도 갈린다 — Django 는 한 테이블(`is_staff`), ActiveAdmin·Laravel Nova 는 별도 테이블/guard. **갈림의 기준은 "고객 테이블이 규제 라이프사이클을 타느냐"** 이고 TenK 은 확실히 타는 쪽이다.

### 결정 4 — 비밀번호는 yaml 이 진실의 원천 → **변경 화면을 두지 않는다**

부팅할 때마다 계정을 만들거나 해시를 yaml 값에 다시 맞춘다. jwt secret·SMTP 앱 비밀번호·텔레그램 토큰과 **같은 운영 방식**(private 레포 전제)이라 일관되다. 그 대가로 패널에 비밀번호 변경 화면을 두면 **다음 재부팅에 되돌아가 "바꿨는데 안 바뀐다"** 가 되므로 아예 만들지 않았다.

### 결정 5 — 답변은 패널에서 보내지 않는다 / 처리 메모만 남긴다

백로그 ②는 "답변 전문을 남길지 짧은 메모만 남길지" 를 물었다. **메모만.** 답변 전문을 DB 에 옮기면 보관 대상 개인정보가 늘어 privacy.html §1·§3 + Play §6-2 가 따라오는데, **메일 스레드가 이미 아카이브다** — ⑳ 에서 "문의 본문의 익명 사본" 을 기각한 것과 같은 논리다. SMTP 발송을 패널에 붙이면 **스팸 이슈까지 여기로 끌려온다**는 것도 이유.

의견 쪽 메모에는 경고가 하나 더 붙는다 — `feedback` 은 익명이라 수집표에 없으므로 **메모에 신원을 적으면 그 전제가 깨진다**(화면에도 안내를 띄웠다).

### 결정 6 — 액션 감사 로그를 남긴다

패널은 이용자 개인정보(문의 본문·닉네임·회신 이메일)를 열람하고 권한까지 바꾼다. 전용 로거(`TENK_ADMIN_AUDIT`)로 *누가·언제·무엇을* 남긴다. ⭐ **SQL 로 직접 치던 시절엔 아무 흔적도 안 남았다** — 패널로 옮기며 오히려 좋아진 부분이다. 단 **로그에 본문·이메일을 담지 않는다**(로그가 또 하나의 개인정보 보관소가 된다).

### 결정 7 — 안전성 확보조치를 문서와 코드 양쪽에서 메운다 (같은 날 후속)

결정 6 의 후속으로 "privacy.html 에 항목이 없다" 를 남겨뒀는데, *"없으면 법적으로 문제가 생기냐"* 는 질문에서 이어져 **같은 날 처리하기로** 했다. 정리한 사실관계:

- 의무는 **두 갈래** — 조치를 실제로 하는 것(법 제29조)과 처리방침에 적는 것(법 제30조).
- **조치는 대부분 이미 하고 있었다** — HTTPS · BCrypt · RT 해시 저장 · 세션 만료 · DB 포트 미공개 · 파기 배치. **빠진 건 문서화였지 조치가 아니었다.**
- **조치 자체가 미흡한 건 접속기록 하나.** `AdminAudit` 이 계정·일시·수행업무는 남기지만 **IP 가 없고 애플리케이션 로그로만 나가 재배포에 사라졌다** — "1년 보관" 이 성립하지 않는 상태.
- 위험이 현실화되는 건 대개 **유출 사고** 때고, 그때 "안전조치를 다했는가" 가 과징금 감경/가중의 핵심 판단 요소가 된다. TenK 은 고유식별정보·결제·민감정보가 없어 노출이 낮지만 **이용자 영상이 서버에 있어 출시 후에는 무게가 달라진다.**

그래서 **문서 + 코드를 같이** 메웠다:

- privacy.html **§8 신설** — 적은 5가지는 전부 실제 조치다(관리자 계정 분리 · 접근통제 · 암호화 · 접속기록 1년 · 자동 파기). ⚠️ **문서 안에 대응 코드를 HTML 주석으로 적어뒀다** — 다음 사람이 "이 문장이 뭘 근거로 하나" 를 찾을 수 있어야 문서와 코드가 같이 늙는다.
- 접속기록 완성 — **IP**(Traefik 뒤라 `X-Forwarded-For` 첫 값) · **로그인 성공·실패**(대입 공격 탐지의 유일한 수단) · **열람 기록**(고시의 '수행업무' 에 조회 포함, 유출은 열람에서 난다) · **전용 파일 13개월 롤링 + docker 볼륨**(둘 중 하나만 빠져도 고지가 거짓이 된다).
- ⚠️ **로그에 담지 않기로 한 3가지**: 본문·이메일 / **입력된 비밀번호**(오타는 대개 진짜 비밀번호의 변형이라 그 자체가 유출) / **검색어**(닉네임 검색은 그게 곧 개인정보 — `keyword=given/none` 만). 셋 다 회귀 가드가 있다.

### 결정 8 — 변호사 검수를 백로그에서 뺀다 (사용자 결정)

대신 **"문서 = 실제 동작"** 을 유지 기준으로 못박았다. 두 문서의 모든 문장은 코드·배치·설정에 대응하는 사실이어야 하고, **하지 않는 것을 적지 않는다** — 지키지 못할 약속은 사고 시 오히려 불리하다. 실제로 §8 을 쓸 때 악성프로그램 방지·물리적 안전조치·재해 대비는 **우리가 뭘 하는지 확신할 수 없어 적지 않았다.**

법률 자문이 필요해지는 트리거는 따로 남겼다 — **결제 도입 · 광고 SDK · 제3자 제공 · 해외 이전**. 문서가 사실 서술을 넘어 법적 판단을 요구하게 되는 지점이다.

### 안 만들기로 한 것 (스코프 방어)

"간단하게" 를 지키려면 경계를 먼저 못박아야 했다.

- ❌ **이용자 데이터 편집·삭제** — 삭제의 진실의 원천은 앱 탈퇴 흐름 + 파기 배치다. **패널이 우회로가 되면 그 계약이 무너진다.**
- ❌ **답변 발송**(결정 5) · ❌ 비밀번호 변경(결정 4) · ❌ 통계 대시보드 · ❌ 챌린지/기록/영상 조회
- ❌ **알림 2겹 제거** — 패널은 **'처리'**, 알림은 **'인지'** 를 맡는다. 도착 사실을 아는 건 여전히 알림의 일이라 뺄 수 없다.
- ❌ **`ADMIN` 승격** — 패널에서 이용자를 ADMIN 으로 올릴 수 없다. `UserRole.ADMIN` 과 `admin_user` 는 별개 축이고, 섞으면 권한 상승 경로가 생긴다.
- ❌ **텔레그램 봇 양방향(`/done 37`)** — 회의에서 중간지대로 제시했으나 패널이 SSH 마찰을 이미 없애 필요가 사라졌다. 그 마찰이 실제로 다시 아프면 그때.

### 곁가지로 나온 것

- ⚠️ **`schema.sql` 의 DROP 목록에 `inquiry` 가 빠져 있었다** — `user` 에 FK 가 있어 **클린 재실행이 실패하는 상태**였다(⑳ 때 누락). 같이 고쳤다.
- **`@ConfigurationPropertiesScan` 이 `basePackageClasses` 로 못박혀 있어** 새 패키지의 properties 가 안 잡혀 부팅이 죽었다. 다음에 같은 함정을 밟지 않게 그 자리에 주석을 남겼다.
- `FeedbackIntegrationTest` 의 **익명성 컬럼 검사가 `handler_note` 추가를 잡아냈다** — 가드가 의도대로 동작한 사례.

### 후속 — 로컬 구동 검증에서 나온 결정 3가지 (2026-08-07)

> 배포 전이라 운영 URL 이 안 열려 **로컬에서 5화면을 전부 눌러본** 자리에서 나왔다. 영구 규칙은
> [../CLAUDE.md](../CLAUDE.md) "관리자 패널" · "의견 보내기".

**결정 A — 유형 라벨은 서버 enum 에 두되, 앱 문구와 분리한다.**
목록·상세에 `PRIVACY` 같은 **코드가 그대로 노출**되고 있었다. 대안은 셋이었다:

| 안 | 판단 |
|---|---|
| 템플릿 안에서 코드→라벨 매핑 | ❌ 도메인 어휘가 화면 파일로 샌다 |
| 앱의 선택지 문구를 그대로 재사용 | ❌ 의견 문구가 `"불편하거나 오류가 있어요"` 라 **목록 한 칸에 안 들어간다** |
| **enum 에 `label` 추가** (`SpendCategory` 선례) | ✅ 채택 |

⚠️ **그래서 의견 유형은 두 곳의 문구가 일부러 다르다** — 앱은 *고르는* 화면이라 해요체 문장,
패널은 *훑는* 표라 짧은 분류명(`불편·오류`). **"표시 문구는 클라가 소유" 규칙은 그대로**고,
enum 라벨은 **패널 전용 분류명**이라는 별개 축이다. 둘을 같은 값으로 맞추려 들지 말 것.
문의 유형은 앱 쪽도 짧은 명사라 지금은 값이 같지만 규칙은 동일하다.

**결정 B — local 은 운영과 ID 만 공유하고 비밀번호는 따로 둔다.**
처음엔 자격증명을 통째로 맞췄다가(로컬에서 확인한 로그인이 곧 운영 로그인이 되게) 되돌렸다 —
**로컬 백엔드가 `0.0.0.0:8080` 에 열려** 같은 Wi-Fi 의 누구나 그 폼에 닿기 때문이다. 값을 공유하면
카페 같은 공용망에 운영 자격증명을 들고 나가는 셈이 된다. **ID 만 맞춰 "로컬에선 되는데" 를 막고,
비밀번호는 외우기 쉬운 로컬 전용**으로 가른다.

**결정 C — 테스트 계정 ID 는 실계정과 합치지 않는다 (한 번 합쳤다가 되돌림).**
`admin@test` 라는 안 쓰는 계정 행이 로컬 DB 에 남는 게 지저분해 보여 실계정 ID 로 통일했는데,
**`AdminAccountInitializer` 가 부팅마다 그 이메일 행의 해시를 yaml 값으로 맞춘다**는 사실이 드러났다
— 합치면 `./gradlew test` 한 번에 **로컬 패널 비밀번호가 `test-admin-pw` 로 덮인다.**
*"안 쓰는 행이 남는 쪽이 실계정 비밀번호가 흔들리는 것보다 낫다"* 로 결론(사용자 판단).

- **근본 해법은 테스트 전용 스키마 분리(`tenk_test`)이고, 지금은 하지 않기로 했다.** 검토는 했다 —
  통합 테스트가 dev 스키마를 공유해서 생기는 문제(재로그인·비밀번호 덮어쓰기)가 **URL 한 줄로**
  사라지지만, 사용자가 **현행 유지**를 골랐다. *"개발 데이터는 두고 테스트 데이터만 지우면 되지 않나"*
  도 같이 검토했으나 **불가**: 통합 테스트에 `findAll()`·`count()` 로 **테이블 전체를 단언**하는 곳이
  15군데고(`assertThat(feedbackRepository.findAll()).isEmpty()`), `evaluateAllActive`·`remindPending`
  처럼 **전체 스캔을 도는 배치 테스트**가 있어 dev 데이터가 남아 있으면 동작 자체가 달라진다.
  청소 방식의 문제가 아니라 **테스트 전면 재작성** 이야기가 된다.

## 문의 창구 정리 (2026-08-05)

> 백로그 #23. ⑩[의견 보내기](#의견-보내기-2026-07-28) 의 곁가지로 만든 '문의' 행을 다시 다루는 **2차 회의**다. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "문의하기" · "관리자 알림".
> **결론: 합치지 않는다. 대신 '고객센터' 허브에 나란히 모으고, mailto 를 인앱 폼으로 바꾸고, 관리자 알림을 붙인다.**

### 진단 — 전제가 한 겹 어긋나 있었다

발단은 *"창구가 둘이라 어디로 가야 할지 헷갈린다"* 였는데, **둘은 같은 층에 있지 않았다.** 메뉴에서 보이는 건 '의견 보내기' 하나뿐이고 '문의' 는 **'법적 고지' 안**에 있다. 즉 *"뭔가 말하고 싶다"* 로 메뉴를 여는 사람에게는 갈림길 자체가 안 생긴다.

⭐ **헷갈림의 실체는 창구 개수가 아니라 `'문의'` 라는 총칭 라벨이었다.** 그 단어가 일반 CS 창구처럼 읽혀서, 법적 고지 안에 있는데도 '의견 보내기' 와 역할이 경쟁했다.

### 합칠 수 없는 이유 3개

백로그가 미리 적어둔 쟁점을 하나씩 판정했다.

| 쟁점 | 판정 |
|---|---|
| 고지된 접수처를 앱에서 빼도 되나 | **법적으로는 된다** — 고지 지점은 privacy.html §9(당시 §8 — 2026-08-06 안전성 확보조치 신설로 번호가 밀렸다) / terms.html 제11조이고 공개 URL 로 접근된다. 하지만 그 행을 넣은 이유가 *"privacy 를 열어 스크롤해야만 보이던 걸 두 단계로 줄인 것"* 이라, 지우면 정확히 그 개선분만 되돌아간다. **얻는 건 행 하나뿐.** |
| '의견 보내기'로 합칠 수 있나 | **못 합친다.** 권리 행사는 *누구의 데이터인가*가 특정돼야 10일 내 조치가 되는데 `feedback` 은 `user_id` 를 안 저장한다. 그 경로만 신원을 받게 하면 익명이라 성립하던 설계가 무너진다. |
| 앱 밖 접근 | **어느 안을 골라도 영향 없다** — 탈퇴자·로그인 불가는 어차피 앱에 못 들어온다. 그들의 창구는 문서에 적힌 주소이고 이미 있다. |

백로그의 착지점 후보 중 *"'문의' 를 남기되 '의견 보내기' 로 유도"* 는 **같은 이유로 기각**했다 — 권리 요구를 익명 폼으로 밀어 넣는 꼴이다.

### 결정 1 — 각 화면이 각자의 계약을 갖는다

한 화면에 유형만 추가해 통합하는 안도 검토했다(그러면 창구가 진짜 하나가 된다). **기각한 이유**: privacy.html 이 *"'의견 보내기'로 보낸 내용은 계정과 연결하지 않아 누가 보냈는지 알 수 없다"* 고 **공개 약속**해 뒀다. 같은 화면의 어떤 유형만 계정과 연결되면 그 약속이 흐려지고, 사용자 입장에서 *"이 화면은 익명인가 아닌가"* 가 모호해진다. **모호한 익명성은 익명이 아닌 것보다 나쁘다.**

대신 **역할별로 자리를 갈랐다** (2026-08-06 2차 조정): **'의견 보내기'는 메뉴 최상위**(설정 위), **'문의하기'는 메뉴 → '고객센터' 안**.

한 번은 둘을 고객센터에 나란히 모아봤는데 되돌렸다 — ⭐ **의견 보내기는 '가볍게 남기는' 창구라 고객센터 안에 있으면 *문의할 일이 있어야 여는 곳*으로 읽혀 문턱이 올라간다.** 나란히 두면 차이는 잘 보이지만 그 대가로 진입 빈도가 낮은 쪽에 맞춰지는 셈이다. 고객센터는 항목이 하나뿐이어도 **FAQ·공지가 들어올 자리**라 허브로 남긴다.

처음엔 라벨만 `'개인정보 문의'` 로 좁혀 풀려 했는데, 사용자가 **일반 고객센터로 넓히자**고 해서 전제가 바뀌었다. ⭐ 그래도 **가르는 축은 유형이 아니라 "답변을 원하는가"** 하나라서, 오류 문의가 의견의 '불편/오류'와 겹쳐 보여도 문제가 아니다.

### 결정 2 — mailto 를 인앱 폼으로 (사용자 결정, 내 추천을 뒤집음)

나는 **폼 전환을 비추천**했다. 논거는 mailto 가 이미 ① Gmail 푸시로 알림이 오고 ② 답장 경로가 있고 ③ 보낸 주소로 본인이 특정된다는 것이었고, 폼으로 바꾸면 `user_id`·문의 내용이 **개인정보로 늘어** privacy.html 수집표·보관기간·Play 데이터 안전을 다시 짜야 한다는 것이었다.

사용자가 두 가지를 짚어 결론이 바뀌었다.

1. **"개인 메일이 노출된다"** — 맞다. 그리고 이건 폼 여부와 별개로 **전용 계정 신설**로 풀린다(고지 문서에는 어차피 주소가 남아야 하므로).
2. ⭐ **"메일은 내가 읽지 않았다고 다시 알림이 오지 않는다. 한 번 놓치면 모른다"** — 이게 결정적이었다. **내 논거 ①이 틀렸다** — Gmail 푸시는 *도착*을 알릴 뿐 *미처리*를 추적하지 못한다. 반면 DB 에 상태를 두면 **처리될 때까지 계속 알릴 수 있다.**

그래서 폼 + DB 로 갔다. 늘어나는 개인정보 비용은 **인정하고 문서에 반영**한 것이지 없앤 게 아니다(privacy.html §1·§3, play-console §6-2).

### 결정 3 — 알림은 2겹 + 미처리 리마인드

사용자가 제안한 **SMTP + 텔레그램 2겹**을 그대로 채택했다. 검토한 대안: 카카오톡 '나에게 보내기'(**개발자 본인 토큰을 서버가 상주 갱신**해야 해서 가장 비싸다) / 알림톡·SMS(유료·사업자 전제) / Discord 웹훅(텔레그램과 동급). **메일을 축으로 둔 건 이미 고지된 창구가 그 주소라 문의와 의견 알림이 같은 함으로 모이기 때문**이다.

⭐ **하지만 2겹도 "그 순간 한 번"일 뿐이다.** 자는 사이에 오면 둘 다 놓친다. 그래서 **미처리 리마인드**를 본체로 뒀다 — `PENDING` 이 남아 있으면 매일 **오전 9시**(새벽 배치가 아니라 *사람이 볼 시간*)에 다시 알린다. **0건이면 안 보낸다** — 매일 오는 "0건" 은 곧 무시되고, 그러면 진짜 알림도 같이 묻힌다.

의견에는 리마인드를 안 붙였다. 의견에는 "처리 완료" 라는 상태가 없고, ⑩ 에서 이미 *"즉시 처리해야 하는 큐가 아니라 모아서 보는 데이터"* 로 결론냈기 때문이다. **도착 알림만 붙인 건 그 결론과 모순이 아니다** — 모아서 보려면 *모였다는 사실*은 알아야 한다.

### 결정 4 — 발송 실패가 저장을 막지 않는다

`AdminNotifier` 는 **모든 예외를 삼키고 로그만 남긴다**. 알림이 안 가는 것보다 **사용자의 문의가 유실되는 게 훨씬 나쁘다.** 같은 이유로 `@Async` 다 — 외부 호출 지연이 사용자 응답에 붙으면 안 된다. 설정이 없으면 조용히 skip 하므로 local/test 에서 실제 발송이 나가지 않는다.

### 결정 5 — ADMIN role 은 권한용으로만, 수신 주소는 설정에 남긴다

사용자가 *"ADMIN role 을 만들어 그 유저에게 메일을 보내자"* 고 제안했다. ⚠️ **블로커가 있었다 — `user` 에 이메일 컬럼이 없다.** ⑩ 직후의 #10(2026-07-26)에서 **수집을 접고 컬럼까지 DROP** 했고 카카오에서도 못 받아온다. 수신자를 DB 에서 찾으려면 그 결정을 privacy·Play 답안까지 통째로 되돌려야 한다.

그래서 **`ADMIN` 은 만들되 권한용으로만** 뒀다(`canUseTestTools()` 가 TESTER·ADMIN 둘 다 true, 관리자 패널을 지을 때의 게이트 자리). **수신 주소는 `tenk.notify.mail.to` 가 진실의 원천**이다. 수신자가 늘어 DB 로 옮겨야 하면 `user` 가 아니라 **별도 운영자 연락처 테이블** — 운영자 연락처는 이용자 개인정보가 아니라 성격이 다르다.

### 결정 6 — 문의 본문의 익명 사본은 만들지 않는다

사용자 제안: *"문의는 계정 파기 시 삭제되니 익명 의견 테이블로 옮겨 계속 볼 수 있게"*. **기각했고 사용자도 동의**했다.

⭐ **문의 본문은 익명화가 안 된다.** `withdrawal_feedback`(코드)·`feedback`(제품 의견)이 익명으로 성립하는 건 **본문에 신원이 안 들어가기 때문**인데, 문의 본문은 *"제 계정 지워주세요, 연락처는 010-…"* 이 되기 쉽다. `user_id` 만 떼는 건 익명화가 아니고, 그 사본이 들어가는 순간 `feedback` 이 *"익명이라 수집표에 안 들어간다"* 는 성질을 잃는다. **삭제 요구를 받으면서 그 요구서를 파기 후에도 보관하는 모양새**이기도 하다.

그리고 **이미 사본이 있다** — 알림 메일에 유형·회신 이메일·본문이 통째로 들어가므로 **메일함이 곧 아카이브**고 계정 파기와 무관하다. 통계가 정말 필요해지면 **본문 없이** `유형 + 접수일 + 처리 소요일`만 남기면 되고, 그건 진짜 익명이라 `withdrawal_feedback` 과 같은 논리로 정당화된다.

### 결정 7 — 문의 유형은 굵게 4종, 보관은 회원 탈퇴 시까지 (2026-08-06)

**유형**: 처음엔 개인정보 권리 4종(열람/정정/삭제/철회)만 뒀다가 창구가 일반 고객센터로 넓어지며 7종까지 갔는데, **다시 4종으로 접었다** — 계정·로그인 / 서비스 이용 / 개인정보 / 기타. 국내 고객센터 표준이 **계정 / 결제 / 오류 / 기타**이고, 결제가 없는 TenK 은 그 자리를 개인정보가 대신한다. **'오류'를 따로 안 둔 건** 결제가 없어 서비스 이용 문의의 대부분이 곧 오류이고 순수 버그 제보는 이미 의견 보내기가 받기 때문. 세분화는 고르는 시간만 늘리고 분류 정확도는 오히려 떨어뜨린다.

**보관**: "답변 후 3개월" 배치를 **통째로 걷어내고 '회원 탈퇴 시까지'** 로 바꿨다. ⭐ 3개월은 내가 임의로 정한 값이었지 법이 요구한 게 아니다 — 전자상거래법의 "소비자 불만·분쟁 처리 기록 3년"은 **통신판매업자** 대상이라 TenK 은 해당 없고, 보호법은 "목적 달성 후 지체 없이"만 요구한다. 목적을 *문의 이력 관리*로 두면 회원 자격 기간이 곧 보유 기간이다. 얻는 것: **파기 배치가 사라지고**(규칙 하나 감소), 답변 여부와 보관이 분리되고, 재문의 맥락이 남는다. 잃는 것도 사실상 없다 — **계정 데이터 전체가 어차피 탈퇴 시까지 남아** 문의만 짧게 둔다고 사용자가 더 보호받지 않는다. `status` 는 **리마인드를 멈추는 용도**로만 남았다.

**화면 문구**: "어떤 점이 궁금하신가요?" → **"무엇을 도와드릴까요?"**. 사용자 지적대로 **이 창구는 궁금해서 오는 곳이 아니라 문제가 생겨서 오는 곳**이다. 하단 안내 2줄(계정 정보 전송·보관 기간)은 사용자 결정으로 삭제 — 수집·보관 고지는 privacy.html 이 한다.

### 검증에서 잡은 것 — From 을 안 채우면 메일이 조용히 안 나간다

에뮬 E2E 에서 문의는 저장됐는데 **메일만 실패**했다: `can't determine local email address`. 원인은 `spring.mail.username` 이 **인증용일 뿐 From 헤더가 되지 않는다**는 것. ⭐ **best-effort 설계라 예외를 삼켜서, 로그를 안 봤으면 '성공'으로 보였을 자리**다 — 결정 4(실패해도 저장은 성공)의 대가이기도 하다. `resolveFrom` 폴백(`tenk.notify.mail.from` → SMTP username)으로 고쳤고 재검증에서 2겹 모두 통과. **통합 테스트로는 절대 못 잡는 종류**(local/test 는 발송이 꺼져 있다)라 이 기능은 실제 발송 검증이 필수다.

### 검증에서 잡은 것 2 — 메일은 스팸함으로 간다

고친 뒤 재검증에서도 **텔레그램 2건은 오고 메일은 안 왔다.** SMTP 는 예외 없이 통과했고(같은 메서드에서 텔레그램이 나갔으니 `sendMail` 이 정상 종료한 게 확실) 실제로 **수신 계정 스팸함에 들어가 있었다.** 발신 계정이 새것이라 평판 이력이 없고, 짧은 본문 + 자동화 티 나는 제목이라 Gmail 이 의심한 것.

⭐ **코드로 고칠 문제가 아니다** — 표시 이름이나 본문을 다듬어도 수신측 판정은 바뀌지 않는다. 해결은 수신 계정의 **필터**(`from:system.tenk@` → 스팸으로 보내지 않기) + 스팸함 기존 메일을 '스팸이 아님' 으로 학습시키는 것.

그리고 이 사고가 **결정 3(2겹)의 가치를 실증했다** — 메일 한 겹이었으면 두 건 다 조용히 사라졌다. "한쪽을 놓쳐도 다른 쪽이 남는다" 가 가정이 아니라 실제로 일어났다.

### 남은 것

- 텔레그램 `chat-id` 는 채웠다(`8946220822`) — 봇에게 먼저 말을 걸어야 생긴다 — 봇에게 먼저 말을 걸어야 생긴다. 채우기 전까지 **텔레그램 갈래만 skip**, 메일은 정상.
- 관리자 UI 는 여전히 짓지 않는다. 처리 표시는 `UPDATE` 한 줄이고, 패널 도입 트리거는 ⑥ 에서 정한 대로 **UGC 모더레이션**이다.

## 알림 권유 화면 (2026-08-05)

> 백로그 #22. ⑰[알림 기능](#알림-기능-2026-08-02) 의 **결정 8(권한은 가입 직후 + 설정 양쪽)을 부분적으로 뒤집는** 2차 회의다. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "알림".
> **결론: 온보딩 뒤에서 빼고 첫 챌린지 생성 직후로 옮긴다. 형태는 바텀시트.**

### 진단 — 백로그가 물은 것보다 큰 게 나왔다

백로그의 안건은 *"온보딩 직후에 또 한 화면을 세우는 게 맞나"* 였다. 그건 취향 문제로 보였는데, 코드를 열어보니 **기능이 성립하지 않는 구간**이 있었다.

⭐ **가입 직후에 승인해도 예약되는 알림이 0건이다.** [notification_plan.dart](../tenk_app/lib/data/notification/notification_plan.dart) 는 그 날 기록할 챌린지가 없으면 리마인더·종료 임박을 건너뛰고(`active.isEmpty`), 확정 대기도 챌린지가 있어야 생긴다. 그런데 프라이밍이 뜨는 시점의 사용자는 **챌린지가 0개**다.

- 화면이 약속하는 세 가지(매일 저녁 / 마지막 날 / 결과 확인)가 **전부 챌린지 전제**다.
- 그래서 '알림 받기' 를 누른 사람은 **첫 챌린지를 만들기 전까지 알림을 한 개도 못 받는다.** 이유를 모르니 "켰는데 안 오네" 로 읽힌다.
- **이건 문구로 못 고친다** — 자리가 틀린 것이다.

부차적으로 두 가지가 더 있었다.

- **가장 비싼 자원을 가장 동기가 낮은 순간에 쓴다.** 요청 기회는 iOS 1회·Android 2회뿐인데 이 시점 사용자는 앱을 한 화면도 못 봤다. ⚠️ 다만 이 논거는 **생각보다 약하다** — 프라이밍 화면 자체는 요청을 태우지 않고('나중에' 는 시스템 다이얼로그를 안 띄운다) 태우는 건 승낙한 사람뿐이라 낭비가 아니다. 회의 중 스스로 깎았다.
- **필수 관문 3개 뒤에 붙어 게이트처럼 읽힌다.** 앞의 셋은 back 이 막힌 화면인데 넷째만 선택이고, 사용자는 그 차이를 모른다. (실기기 검증 체크리스트에 *"'나중에' 로 넘어감(게이트 아님 확인)"* 이 항목으로 있었다는 것 자체가 방증이다.)

### 업계 표준은 갈려 있고, 기준은 하나다

- **공식 가이드(Apple HIG · Android 13 `POST_NOTIFICATIONS` 문서)는 "기능의 가치를 이해한 순간에 요청"** 을 권하고 앱 시작 직후 요청을 명시적으로 피하라고 한다.
- **실무는 온보딩 프라이밍이 지배적**이고 승낙률도 나쁘지 않다(설정 모드라 임계가 낮다). *정확한 수치는 출처마다 편차가 커서 근거로 쓰지 않았다.*
- 두 진영을 가르는 기준은 **"알림이 그 앱의 핵심 루프인가"** — 메신저·알람은 온보딩에서 물어도 정당하고, 부가 기능이면 맥락으로 미룬다.
- **TenK 은 중간**이다. 알림이 없어도 앱은 성립하지만(기록은 앱 안에서만 한다) *매일 기록하게 만드는 것*이 제품의 핵심 루프다. 그래서 안건이 "없앨까" 가 아니라 **"어디로 옮길까"** 가 됐다.

### 결정 1 — 첫 챌린지 생성 직후로 옮긴다

네 안(현행 / 생성 직후 / 홈 배너 / 하이브리드) 중 **생성 직후**. 승인이 곧 실제 예약으로 이어지는 **첫 순간**이고, 온보딩이 3화면으로 짧아지며, 요청 기회를 동기가 가장 높은 곳에 쓴다.

- **"챌린지를 안 만드는 사용자에겐 영영 안 묻는다" 는 손실이 아니다** — 그 사용자에겐 예약될 알림이 어차피 0건이다.
- **첫 기록 직후는 왜 아닌가**: 맥락은 더 강하지만 챌린지 시작일이 미래일 수 있어 **며칠 뒤**가 된다. 그 사이가 정확히 리마인더가 필요한 구간이라 늦다.
- 홈 배너(비차단)는 도달이 약하고, 하이브리드는 배너 노출·해제 상태가 새로 생겨 지금 규모에 과설계.

### 결정 2 — 형태는 바텀시트. **시안을 그려서 정했다**

말로는 "시트가 맥락을 유지해서 낫다" 였는데, **실제 치수로 그려보니 그 근거가 흔들렸다.** 360×640dp 에 실제 토큰으로 3안을 렌더해 비교했다([#18](#결과-카드-디자인-2026-08-01) 에서 정착한 *HTML 시안 → Artifact* 방식).

| 안 | 결과 |
|---|---|
| A 시트(현행 내용 그대로) | 시트가 화면 대부분을 덮어 **뒤 목록이 탭바까지만 보인다** |
| B 시트(아이콘 상자 제거 + 제목 20px) | 방금 만든 카드가 시트 위로 보인다 |
| C 풀스크린 유지 | 코드 변경 최소, 대신 생성 폼 직후에 **또 전체 화면** |

⚠️ **A 는 시트를 고른 유일한 이유를 스스로 지운다** — 그린 뒤에야 보였다. 그래서 실질 선택지는 B·C 였고, **사용자가 A 를 골랐다**(현행 내용 유지 우선).

> ⭐ **그런데 실기에서 A 의 단점이 예측만큼 크지 않았다.** 에뮬(360×640) 실측 시트 높이는 **약 63%** 여서 **뒤에 방금 만든 카드가 한 장 온전히 보인다.** 시안의 높이 추정이 실제 폰트·여백보다 후하게 잡혔던 것. 교훈은 시안을 그린 것 자체는 옳았지만(**A 의 위험을 미리 알아 선택이 정보에 근거하게 됐다**) **추정 높이로 결론을 내리지는 말 것** — 최종 판정은 실물이다. 더 줄이고 싶으면 B 안(아이콘 상자 제거)이 그대로 남아 있다.

- **바깥 탭·드래그로는 안 닫는다** (`isDismissible: false` + `enableDrag: false`). 일반 선택 시트와 다른 점이고 **모달 기준표에 '권유' 행을 새로 만든 이유**다 — 다시 물어볼 수 없는 것을 묻기 때문에 실수로 닫히면 되돌릴 길이 설정 화면밖에 없다.
- **시스템 back 은 막지 않는다** (= '나중에' 와 같은 결과). 게이트가 아니라는 원칙이 그대로 살아 있고, 모달에서 back 을 막는 건 플랫폼과 싸우는 것이다.

### 결정 3 — 한 번만 묻는다. 플래그는 **띄우는 순간** 세운다

`AppSettings.notificationPrimingShown`. 승인·나중에·back 어느 쪽으로 닫혔든 **시스템 다이얼로그 기회를 한 번 쓴 것**으로 본다 — 결과가 아니라 *물었는지* 를 기록하는 게 핵심이다. 챌린지를 더 만들어도 다시 뜨지 않는다.

트리거 조건은 3개 AND: **목록 길이 증가**(그 자리 주석대로 pop result 는 못 믿는다) + 아직 안 물음 + 마스터 꺼짐.

### 결정 4 — 문구는 한 줄만 고친다

`기록을 놓치지 않도록 하루 한 번만 알려드려요.` → **`기록을 놓치지 않게, 챌린지가 시작되면 하루 한 번만 알려드려요.`**

**"챌린지가 시작되면" 을 지우지 말 것** — `_isActiveOn` 이 시작일 전에는 리마인더를 걸지 않으므로, 이 말이 없으면 내일 시작하는 챌린지를 만든 사람이 "켰는데 오늘 안 왔다" 로 읽는다. [#26](handoff-archive.md) 문구 규칙의 *"지우면 안 되는 설명 = 결과 설명"* 에 해당한다. 나머지(제목·불릿 3·버튼·푸터)는 규칙에 맞아 유지.

### 구현 중 잡힌 것 — 가드가 엉뚱한 걸 재고 있었다

위젯 테스트를 시트 버전으로 옮기며 **`SafeArea` 를 통째로 빼도 통과**하는 걸 발견했다. `알림 받기` 버튼으로 재고 있었는데 **그 아래에 '나중에' 와 푸터가 더 있어서** 버튼은 잘리지 않았던 것. 측정 대상을 **최하단 요소(푸터)** 로 바꾸고 나서야 되돌렸을 때 실패한다(640: 631>616 / 560: 544>536).

> 교훈은 [#19·#20](handoff-archive.md) 과 같은 결이다 — **가드는 "통과한다" 가 아니라 "되돌리면 실패한다" 로 확인해야 한다.**

### 안 하기로 한 것

- **홈 배너 / 하이브리드** (결정 1) — 상태 관리가 새로 생기고 지금 규모에 과설계.
- **첫 기록 직후로 미루기** (결정 1) — 시작일이 미래면 며칠 뒤라 늦다.
- **거부한 사람에게 재권유** — 시스템이 다이얼로그를 다시 안 띄우므로 앱이 할 수 있는 게 없다. 설정 화면의 `설정 열기` 스낵바가 그 역할을 이미 한다.

## 로고 · 앱 아이콘 (2026-08-02)

> 백로그 #6. 안건은 **"TenK 로고 + 런처 아이콘 확정"**. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "로고 / 앱 아이콘".
> **결론: 마크는 `10`(링 = 예산 게이지), 흰 바탕 + 민트. 자산 PNG 가 아니라 코드로 그리고, `flutter_launcher_icons` 는 도입하지 않는다.**

### 출발점 — 백로그가 짚은 것보다 구멍이 컸다

백로그는 "기본 Flutter 아이콘" 만 문제 삼았는데, 열어보니 두 가지가 더 있었다.

1. **`mipmap-anydpi-v26` 이 없어 adaptive icon 자체가 없었다.** 원형 런처(픽셀 계열)와 Android 13+ 테마 아이콘에 대응이 안 되고, 시스템이 legacy PNG 를 강제로 마스킹한다.
2. **앱 안에 로고라 부를 게 없었다.** 로그인 화면이 `Text('TenK', fontSize: 48)` + 하드코딩 `Colors.black54` — 디자인 토큰조차 안 쓰고 있었다.

그래서 범위를 "런처 아이콘 교체" 가 아니라 **"마크를 정하고 그 마크가 나오는 자리를 전부 맞추기"** 로 잡았다.

### 판단 기준 — "예쁜가" 가 아니라 "48px 에서 형태가 남는가"

후보를 말로 고르지 않고 **전부 실제로 그려서** 48px(mdpi 런처, 아이콘이 가장 오래 살아 있는 크기)까지 놓고 비교했다. 이 기준 하나가 결정을 거의 다 만들었다.

| 후보 | 결과 |
|---|---|
| **`10` (채택)** | 워드마크가 `TenK` 를 담당하므로 마크는 `10` 만 지면 된다 — **세 글자를 두 글자로 줄여** 48px 에서 형태가 남는다. `0` 을 게이지 링으로 쓰면 "예산 안에서 쓴다" 가 마크 하나에 들어간다. |
| `T` (가로획을 게이지로) | 글자 하나라 48px 은 가장 여유로웠으나, **로고 조합에서 워드마크 `TenK` 의 첫 글자와 겹쳐 `T TenK` 로 읽혔다.** 스펙 시트에선 안 보이고 로그인 화면 목업에서 드러난 문제. |
| `10K` / `KK` | 세 글자라 48px 에서 획이 가늘어지고, 워드마크와 나란히 놓으면 같은 말을 두 번 한다. |
| `K` (`10` 을 변형) | `1` 을 기둥, `0` 을 쪼갠 곡선을 팔로 써서 K 를 만든 안. 잘 읽히지만 **숫자 의미가 사라져** 그냥 알파벳이 된다. |
| 링 게이지로 K 만들기 | 갭 방향(왼쪽/우상단/오른쪽)과 크기를 6가지로 돌렸는데 전부 `10`·`1C` 로 읽혔다. **K 는 한 점에서 뻗는 열린 획 두 개**인데 링은 갭이 있어도 닫힌 곡선이라 눈이 '팔' 이 아니라 '그릇' 으로 읽는다. |

### 결정 1 — 게이지 트랙은 '완전한 원' 이다

갭만 열어둔 링은 큰 화면에서 게이지로 잘 읽히지만, **48px 에서 `0` 이 `C` 로 무너졌다**(`1C`). 옅은 트랙으로 원을 닫으면 갭이 메워져 `10` 이 유지되면서, 진한 링과의 대비로 게이지 의미도 남는다. **트랙을 지우거나 `primaryTint`(#E3F6F0)처럼 더 옅은 색으로 바꾸면 이 효과가 사라진다** — 그래서 `AppColors.logoTrack`(#C6EEE4)을 진행률 바 트랙과 **별도 토큰**으로 뒀다.

같은 함정이 결과 카드 워터마크에서 한 번 더 나왔다. 워터마크는 조용해야 하니 단색 실루엣으로 두려 했는데, 렌더해보니 역시 `1C` 였다. **뮤트 톤이되 트랙은 남기는** 것으로 고쳤다.

### 결정 2 — 자산 PNG 가 아니라 코드로 그린다

`flutter_launcher_icons` 를 쓰는 게 통례지만, 그 도구는 **원본 PNG 를 리사이즈만** 한다. 원본은 어차피 손으로 만들어야 하고, 그러면 획 굵기 하나 바꾸는 데 외부 편집기가 필요해진다.

대신 파이썬 생성기가 마크를 **폰트·외부 자산 없이 기하학으로** 그린다. 상수만 고치면 41개 산출물이 한 번에 다시 나오고 어느 머신에서든 결과가 같다. 그래서 **그 스크립트가 형상의 진실의 원천**이고, `flutter_launcher_icons` 는 **도입하지 않는다** — 도입하면 생성기가 둘이 되어 산출물이 갈라진다.

앱 안 렌더도 같은 이유로 `CustomPainter` 다(배지 컨페티를 Lottie 에서 옮긴 것과 같은 논리). ① 색을 호출부가 정할 수 있어 민트/흰색/뮤트 반전에 자산이 여러 벌 필요 없고 ② **결과 카드 캡처 경로에서 `precacheImage` 가 필요 없다** — 배지 PNG 는 첫 프레임 placeholder 가 캡처되는 회귀 때문에 precache 가 필수인데, 페인터는 그 함정 자체가 없다.

**대가는 형상 상수가 두 파일에 있다는 것**이다. 감수하기로 했다 — 마크는 자주 바뀌는 물건이 아니고, 양쪽에 서로를 가리키는 경고를 박았다. 한쪽을 SVG 로 통일하는 방법도 있으나 `flutter_svg` 의존성이 늘고 런처 PNG 는 어차피 따로 뽑아야 해서 이득이 없다.

**옮겨 적은 게 맞는지는 눈으로 확인했다** — 임시 위젯 테스트로 Dart 렌더를 PNG 로 뽑아 파이썬 산출물과 대조했고(호(arc) 방향이 가장 틀리기 쉬운 자리였다), 확인 후 테스트는 지웠다.

### 결정 3 — 스플래시에는 로고를 넣지 않는다

`launch_background.xml` 은 흰 배경 그대로 뒀다. 스플래시와 로그인 화면이 둘 다 흰 배경이라 지금은 이음매가 안 보이는데, **스플래시에만 로고를 넣으면 로그인 화면 로고와 위치·크기가 어긋나며 점프**가 생긴다. 넣으려면 두 화면의 좌표를 함께 맞추는 별도 작업이다.

### 남은 것 — 흰 바탕의 구조적 약점

아이콘 바탕이 흰색이라 **밝은 배경화면 위에서 경계가 사라진다.** 시안 단계에서 확인하고 감수하기로 했지만(마크가 민트라 앱과 색 언어가 이어진다), 실기기에서 견디기 어려우면 **민트 반전**(민트 바탕 + 흰 마크)이 대안이다 — 마크 색만 바꾸고 생성기를 한 번 다시 돌리면 된다. adaptive icon 은 마스크가 가장자리를 자르므로 **보더를 두르는 방식은 쓸 수 없다.**

### 후속 — 마크 크기 `MARK_EXTENT` 0.56 → 0.70 (2026-08-05, 백로그 #25)

실기기에 설치해보니 **마크가 작아 여백이 넓어 보인다**는 지적이 나왔다. 재보니 감이 아니라 수치로도 맞았다 — adaptive 안전영역(72dp) 원 **반지름 대비 잉크가 62%** 까지밖에 안 닿았다.

후보를 말로 고르지 않은 건 이번에도 같다. 4종을 **원형·스퀘어클·테마 마스크 + 실제 크기(48·72·96px)** 로 그려 나란히 놓고 골랐다(108 캔버스에 전경을 그린 뒤 가운데 72dp 만 남기는 **실제 런처 동작 그대로** 재현).

| extent | 안전원 채움 | 판정 |
|---|---|---|
| 0.56 (기존) | 62% | 여백이 넓다 |
| 0.64 | 71% | 개선되지만 소극적 |
| **0.70 (채택)** | **78%** | 여백 문제가 사라지고 원형 마스크에서 획이 가장자리와 싸우지 않는다 |
| 0.76 | 84% | 원형에서 깃발 끝과 링 오른쪽이 눈에 띄게 조인다 |
| 0.80 | 89% | 빡빡 |

⭐ **"형상 상수는 두 파일" 규칙이 이 값엔 적용되지 않는다.** 위 결정 2의 대가로 적어둔 그 경고 때문에 Dart 도 같이 고쳐야 하는 줄 알았는데, `MARK_EXTENT` 는 형상이 아니라 **아이콘 캔버스 안의 여백**을 정하는 값이라 Dart 엔 대응 상수가 없다 — `TenkLogoPainter` 는 주어진 박스를 꽉 채워 그려서(`unit = shortestSide / max(inkW, inkH)`) 여백 개념 자체가 없다. `--ink` 출력이 수정 전후 **완전히 동일**한 것으로 실측 확인했다. 경고가 과잉으로 읽히지 않도록 **어떤 상수가 짝이고 어떤 게 아닌지**를 스크립트 주석·README·CLAUDE.md 세 곳에 나눠 적었다.

## 알림 기능 (2026-08-02)

> 백로그 #17. [#8](#배지-획득-연출-2026-08-01) 에서 '설정' 화면을 만들 때 분리해 둔 안건.
> **이 회의는 설계 확정까지고 구현은 아직 안 했다** — 코드가 없으니 아래 결정이 유일한 진실의 원천이다.

### 진단 — 바닥부터다

실측: `pubspec.yaml` 에 알림 패키지 **0개**, 매니페스트에 `POST_NOTIFICATIONS` **없음**, 백엔드에 푸시 토큰·전송 코드 **없음**. 있는 건 [settings_screen.dart](../tenk_app/lib/presentation/settings/settings_screen.dart) 주석에 예약된 자리뿐이었다.

그래서 첫 질문을 "어떻게 만들까" 가 아니라 **"우리 앱에서 알림이 정당한 자리가 어디냐"** 로 잡았다. 알림은 기능을 더하는 게 아니라 **사용자의 주의를 빌리는 것**이라, 자리를 먼저 정하지 않으면 만들 수는 있어도 꺼질 뿐이다.

### 결정 1 — 로컬 알림만. FCM 은 도입하지 않는다

- **서버가 꼭 필요한 알림이 하나도 없다.** 후보 전부(리마인더·종료 임박·확정 대기)가 **기기가 이미 아는 정보**로 예약된다. 다른 사람의 행동을 알리는 소셜 기능이 없어서다.
- ⚠️ **iOS 푸시는 Apple Developer Program($99/년) 없이 불가능**(APNs 키). 현재 미보유라 FCM 을 골랐으면 **iOS 는 알림이 없는 앱**이 된다. 로컬 알림은 무료 계정으로도 동작한다.
- **Play 데이터 안전 답안이 흔들린다** — [play-console-app-content.md](play-console-app-content.md) §0 이 "광고·애널리틱스 SDK **0개** / 기기 ID **미수집**" 을 강하게 주장 중인데 Firebase installation ID 때문에 다시 짜야 한다. 폼 입력이 §0 잔여로 남은 시점이라 타이밍도 최악.
- 로컬의 유일한 약점인 **"이미 기록했는데 리마인더가 온다"** 는 앱을 열 때 전량 재예약하면 거의 사라진다 — **앱을 안 열었다는 건 기록도 안 했다는 뜻**이다(기록은 앱 안에서만 한다).

### 결정 2 — 발신 채널 3종. **배지 근접은 리마인더에 흡수**

사용자는 4종(리마인더·확정 대기·종료 임박·배지 근접)을 골랐는데, 파보니 배지 근접은 **별도 채널이 될 수 없었다.**

- 배지 근접과 매일 리마인더는 **같은 시각에 같은 말을 한다.** 둘 다 저녁에 "오늘 기록해" 다. 별개로 두면 **근접일에 두 번 울린다.**
- 문구만 승격하면 **발신 개수는 안 늘고 리마인더가 잔소리에서 "받을 게 있다" 로 바뀐다.** 종류를 뺀 게 아니라 합친 것이라 사용자 요구는 그대로 충족된다.

### 결정 3 — 문구 우선순위 (다른 종류끼리도 합친다)

"묶어서 1개" 를 종류 안에서만 적용하면 **마지막 날 저녁에 리마인더 + 종료 임박이 동시에** 온다. 둘 다 "오늘 기록해" 라서 같은 말이다.

```
마지막 날   > "오늘이 챌린지 마지막 날이에요"
배지 근접   > "오늘 기록하면 7일 연속 배지예요"
평소        > "오늘 기록이 아직 없어요"
```

**토글 3개는 그대로 유지된다** — *발신*을 합치는 것이지 *채널*을 없애는 게 아니다. 종료 임박만 켠 사람은 마지막 날에만 받고, 리마인더만 켠 사람에겐 마지막 날 문구가 뜨지 않는다.

### 결정 4 — 서버가 `currentStreak` 을 준다 (백엔드 변경이 딸려온다)

[ChallengeResponse](../tenk-backend/src/main/java/com/hjson/tenk/domain/challenge/dto/ChallengeResponse.java) 에 **현재 STREAK 값이 없다.** 클라가 아는 건 *획득한 배지*뿐이라 STREAK 3 배지를 가진 사람이 지금 3일인지 5일인지 모르고, 하나도 못 땄으면 0인지 2인지도 모른다. [badge_next_goal.dart](../tenk_app/lib/presentation/challenge/widgets/badge_next_goal.dart) 가 *"연속/누적 집계를 클라에서 다시 구현하지 않아도 된다"* 며 **명시적으로 피해간 자리**다.

- **NO_SPEND 는 예외** — 무지출 일수는 DISTINCT 날짜라 규칙이 단순해 [challenge_detail_screen](../tenk_app/lib/presentation/challenge/challenge_detail_screen.dart) 이 이미 클라에서 센다. **STREAK 만 못 센다** — `consecutiveStreakEndingOn` 의 "오늘 기록이 없으면 어제 기준" 같은 규칙이 있어 클라 재구현은 **서버와 어긋난다.**
- → `ChallengeResponse.currentStreak` 추가. 계산은 `BadgeGrantService` 의 기존 로직을 재사용해 **진실의 원천을 하나로** 유지한다.
- ⚠️ **회의 중 내 말을 정정했다** — "로컬이라 백엔드 변경 0" 이라고 했는데 그건 배지 근접을 뺀 셈이었다. 배지 근접을 넣는 이상 **백엔드 재배포가 딸려온다**(마침 #7 도 미배포라 같이 나가면 된다).

### 결정 5 — 정확한 알람을 쓰지 않는다 (정책상 못 쓴다)

`USE_EXACT_ALARM` 은 **알람시계·캘린더 앱 전용의 highly restricted 권한**이라 TenK 은 자격이 없고, `SCHEDULE_EXACT_ALARM` 도 Android 13+ 에선 **기본 거부**다. inexact 예약으로 간다 — 오히려 잘 맞는다. 리서치도 *"정확히 7시보다 6~8시 사이가 낫다"* 고 하고, 우리 알림은 분 단위가 중요한 종류가 아니다.

### 결정 6 — 시각과 횟수

- **매일 리마인더 = 기본 오후 9시** (사용자 변경 가능, [wheel_time_picker](../tenk_app/lib/presentation/common/wheel_time_picker.dart) 재사용). 하루 지출이 거의 끝나 기록이 정확하고 **무지출 판정도 확정에 가깝다**. 잠들기 전이라 놓칠 확률도 낮다.
- **종료 임박 = 마지막 날** (D-1 아님). D-1 은 아직 급하지 않아 **행동을 안 바꾼다**. 리마인더와 같은 시각이라 결정 3 의 우선순위로 합쳐진다.
- **확정 대기 = 종료 다음 날 1회 + 3일 뒤 1회, 총 2회.** 확정을 안 누르면 배지·결과 카드 페이오프가 **영영 묻히는** 구조(확정 트리거가 수동 하나뿐)라 한 번은 약하고, 그 이상은 잔소리다.
  - **시각은 오전 10시** — 저녁 리마인더와 **시간대를 갈라야** 하루에 두 번 울려도 덜 피곤하고, "결과를 보러 오세요" 는 "기록하세요" 와 성격이 다르다.

### 결정 7 — 탭하면 앱만 연다 (v1)

딥링크를 넣으면 **부팅 게이트(버전 → 연령 → 동의 → 닉네임) 뒤에** 배선해야 해서 복잡도가 붙는다. 목록에 이미 앰버 **'확정하기' 마커**가 있어 2탭이면 닿는다. 필요해지면 나중에 올린다.

### 결정 8 — 권한은 가입 직후 + 설정 양쪽. **단 게이트가 아니다**

> ⚠️ **이 결정의 '가입 직후' 는 [알림 권유 화면 (2026-08-05)](#알림-권유-화면-2026-08-05) 에서 뒤집혔다** — 그 시점엔 챌린지가 0개라 승인해도 예약이 0건이라, 권유는 **첫 챌린지 생성 직후**로 옮겼다. '게이트가 아니다'·'설정에서도 요청' 은 그대로 유효하다.

- 가입 직후(닉네임 다음)에 **프라이밍 화면**. ⚠️ **back 을 차단하지 말 것** — 앞의 셋(연령·동의·닉네임)은 필수 관문이지만 **알림은 선택**이다. '나중에' 로 건너뛸 수 있어야 하고, 강제하면 정책 위반이기도 하다.
- 설정의 마스터 토글을 켤 때도 요청. ⚠️ **Android 13+ 는 한 번 거부하면 시스템 다이얼로그가 다시 안 뜬다** — 앱 설정 화면으로 보내는 안내가 필요하다.
- **기본값**: 권한 승인 = 알림을 원한다는 뜻 → **마스터 ON + 종류별 3개 ON**. 거부하면 마스터 OFF. (효과음·진동이 기본 ON 인 것과 달리 알림은 권한이 곧 opt-in 이라 따로 기본값을 정할 게 없다.)

### 안 보내는 조건 (설계의 일부다)

- **진행 중 챌린지가 0개면 리마인더를 예약조차 안 한다** — 챌린지가 없는데 "기록하세요" 는 스팸이다.
- **오늘 이미 기록했으면 오늘 것 취소.**

### 언제 푸시를 붙이나 (트리거 — 회의 중 추가)

*"로컬로 충분하더라도 관리를 위해 서버 푸시를 쓰는 경우는 없나"* 라는 질문에서 나온 절이다. **결정 1 을 뒤집지는 않지만 그 논거가 반쪽이었다** — "로컬로 충분한가" 만 봤고 **"운영자가 알림으로 능동적인 무언가를 하고 싶어질 때"** 를 안 봤다.

- **둘은 대체재가 아니라 보완재다.** 규모가 커져도 **사용자가 시각을 고른 반복 리마인더는 계속 로컬**이다(서버가 매일 각자 다른 시각에 수백만 건을 쏘는 건 낭비고, 오프라인에서도 떠야 하고, 정확도도 로컬이 낫다). 푸시는 **로컬이 못 하는 다른 일**을 하러 온다.
- **로컬이 못 하는 일**: ① 휴면 유저 재활성화 — **대상 선별을 서버만 할 수 있다** ② 운영 공지(점검·장애·정책) ③ ⚠️ **잘못 예약된 알림을 끄거나 문구를 바꾸는 것 — 로컬은 앱 업데이트를 배포해야 바뀐다**(이게 "관리를 위해" 의 정확한 답이고 로컬의 진짜 약점이다) ④ 도달률·오픈율 측정 ⑤ 서버 발원 이벤트(TenK 엔 아직 없음).
- **임계는 사용자 수가 아니다** — 그로스/마케팅 역할이 생기는 시점이고, 국내는 FCM 이 무료라 사실상 출시와 동시에 붙이는 경우가 많다(*첫 90일에 푸시를 1회 이상 받은 유저의 리텐션이 ~3배* 라는 수치가 그 이유).
- ⚠️ **국내 함정 — 광고성 푸시는 정보통신망법상 사전 수신동의가 필수고, 오후 9시~오전 8시 광고성 전송은 별도의 야간 수신동의가 있어야 한다**(위반 시 3천만원 이하 과태료). **우리 리마인더 기본 시각이 정확히 오후 9시**다 — 지금은 *사용자가 스스로 켜고 시각까지 고른* 리마인더라 **정보성**이라 무관하지만, 같은 채널로 "이번 주 이벤트!" 를 쏘는 순간 광고성이 되어 **선택 동의 항목이 생긴다**(TenK 이 "선택 동의 항목 없음" 으로 설계된 걸 깨는 변화).
- **그래서 지금 로컬로 가는 게 미래를 막지 않는다** — 리마인더는 푸시로 대체되지 않으니 **나중에 푸시를 얹을 때 버려지는 코드가 없다.**
- **도입 트리거**: ① 휴면 유저 재활성화 캠페인을 하고 싶어질 때 ② 운영 공지를 앱으로 보내야 할 때 ③ 서버 발원 이벤트가 생길 때. **딸려오는 것**: 마케팅 수신동의 + **야간(21~08시) 별도 동의** / Play 데이터 안전 재작성 / iOS 유료 계정. (관리자 패널을 "UGC 모더레이션이 생기면" 으로 박아둔 것과 같은 패턴.)

### 안 하기로 한 것

- **FCM/Firebase** (결정 1, 위 트리거 전까지) — 서버 발신이 필요한 알림이 생기면 그때 재검토.
- **딥링크** (결정 7) — v1 범위 밖.
- **챌린지별 리마인더** — 동시 진행이 되는 구조라 3개면 하루 3번이다. **앱 전체 하루 1회**.
- **정확한 시각 알람** (결정 5).

### 구현 시 주의사항

- **Android 알림 채널은 종류별 3개.** 시스템 설정과 앱 설정이 1:1 로 맞는다 — 채널 하나로 뭉치면 사용자가 시스템에서 종류별로 못 끈다.
- **예약 갱신은 앱 포그라운드 진입 + 챌린지 목록 로드 성공 시 전량 취소 후 재예약.** 부분 갱신을 하면 취소·중복의 경우의 수가 폭발한다.
- **설정값이 바뀌면 그 자리에서 재예약**한다. `AppSettings` 에 **구독(리스너)을 붙이지 말 것** — 붙이는 순간 [Flutter 상태 관리 재검토](#flutter-상태-관리-재검토-2026-07-29) 의 Riverpod 착수 트리거("화면 간 공유 상태")에 걸린다. setter 안에서 스케줄러를 호출하면 된다.
- `POST_NOTIFICATIONS` 매니페스트 추가 → [play-console-app-content.md](play-console-app-content.md) **§0 권한 목록 갱신 필수**(문서 갱신 규칙).
- **데이터 안전 폼·privacy.html 은 변경 없음** — 로컬 알림은 수집이 아니고 Firebase 를 안 써서 SDK·기기 ID 답안이 유지된다. 이게 결정 1 의 이유 중 하나였다.
- **iOS 는 이 Windows 머신에서 검증 불가** — 코드만 넣고 맥에서 확인.

## 결과 카드 디자인 (2026-08-01)

> 백로그 #18. 안건은 **"결과 카드 디자인 수정"**. ②(2026-05-26)에서 만든 카드의 **보이는 층만** 다시 짜는 회의다 — 진입점·비율·캡처 방식·영상 마지막 클립 같은 구조 결정은 그대로 둔다.
> **결론: 컬러 블록(민트/레드) + 화이트 / 예산 바 + 일자 그리드 / 축하는 두 겹.** ② 의 결정 #6(성공=노랑/실패=그레이)을 뒤집었다. #7(카테고리 분포 제외)은 한 번 뒤집었다가 **결국 원래대로 돌아왔다**(아래 결정 2-1).
>
> **총 7라운드가 걸렸고 마지막 3라운드는 실패 카드 하나 때문이었다.** 아래 결정 6~9 가 그 기록이다.

### 요구사항 — 한 문장이 기준을 바꿨다

사용자가 처음 준 건 "결과 카드 디자인 수정" 한 줄이었고, 진단을 깔고 물어보니 답이 이랬다:

> **"제일 큰 건 안 예쁘다는 거야. 결과 카드가 예뻐야 자랑하고 싶을텐데."**

이게 북극성이 됐다. **정보 위계·중복 제거는 수단이고 목표는 미감** — 보통 화면이면 반대(가독성이 목표)지만 **공유 카드는 공유되지 않으면 존재 이유가 없다.**

### 진단 — 무엇이 안 예뻤나 (사용자가 4항목 전부 동의)

1. **히어로가 숫자가 아니라 단어였다.** 제일 큰 글자가 `성공`(64px)인데 자랑거리는 *얼마 아꼈나*다.
2. **같은 정보가 두 번씩.** `3,200원 아꼈어요` ↔ 통계의 `절약 ↓3,200원`, 헤더 `만원 챌린지` ↔ 푸터 `만원 챌린지`.
3. **🎉/💪 시스템 이모지가 시각 자산의 전부.** 96px 로 상단 시선을 다 먹는데 **OS 마다 글리프가 달라 캡처물이 기기별로 갈라진다.**
4. **통계가 성취가 아니라 정산서로 읽혔다.** 라벨-값 4줄 + 구분선 2개 = 영수증.
5. **배지 유무로 무게중심이 흔들렸다.** `Spacer()` 하나로 아래만 밀어서 배지 0개면 위가 무거웠다.

### 결정 1 — 배경: 다크를 만들어봤다가 화이트로 되돌렸다

**처음엔 다크로 갔다.** 논리는 이랬다 — 불만이 "색·톤이 앱과 따로 논다" 인데 밝은 배경을 유지하면 못 푼다(흰 배경+민트=그냥 앱 화면 / 노랑+보라=계속 따로). 그래서 **특별함의 축을 색상(노랑)에서 명도(다크)로** 옮기고 accent 만 앱 민트로 되돌리면 둘 다 만족한다고 봤다.

**실물을 보니 틀렸다.** 사용자 판단:

> "블랙은 앱과 너무 따로 놀게 되네. 차라리 그냥 앱 화면처럼 보여도 좋으니 화이트 민트가 좋을 것 같아."

**교훈: 리워드의 특별함을 '표면색'으로 만들면 브랜드와 갈라진다.** 표면은 앱과 같아야 하고, 특별함은 **표면 위에 얹히는 것**(컨페티·컬러 블록·진입 연출)이 담당해야 한다. "앱 화면처럼 보여도 좋다" 는 타협이 아니라 **공유 카드가 앱의 얼굴이어야 한다**는 더 강한 요구였다.

**그런데 화이트로 온 뒤에도 "밍밍하다" 가 남았다** — 상단 블록을 명도 94% 민트 틴트(`#E3F6F0`)로 뒀더니 **썸네일·피드에서는 그냥 흰 카드**로 읽혔다. 색을 쓰긴 썼는데 **안 쓴 것과 비슷한 세기**로 쓰고 있었던 것.

외부 레퍼런스를 뒤져보니 이게 공통 항목이었다:

| 레퍼런스 | 규칙 |
|---|---|
| [Spotify Wrapped](https://elements.envato.com/learn/spotify-wrapped-2024) | 배경을 **색으로 완전히 커밋**(솔리드/그라데이션 full-bleed). 타이포가 보조가 아니라 **주 그래픽 요소**("gigantic text"). 카드당 핵심 요소 **3~5개** |
| [Strava](https://www.designrush.com/best-designs/apps/trends/fitness-app-design-examples) | 다크 배경 + **accent 하나**로 위계. 통계를 "공유용 그래픽"으로 패키징 |
| [카뱅 26주적금](../references/kakaobank/26주적금.png) | 진행도를 **칸을 채운 그림**으로 |
| [Duolingo YIR](https://duolingoguides.com/duolingo-year-in-review/) | 스트릭 캘린더 + 최장 기록 — **여정 자체가 콘텐츠** |
| [카드 UI 원칙](https://www.layoutscene.com/card-ui-design-patterns-guide-2026/) | 히어로 넘버 하나에 **크기·색·위치·대비를 전부** 몰아준다 |

→ **최종: 브랜드 민트를 꽉 채우고 글자를 흰색으로.** 앱 `FilledButton` 이 이미 민트 채움이라 색 언어가 이어지면서, 피드에서 스크롤할 때 눈에 걸린다.

실패 블록은 이 시점에 **그레이 채움**으로 갔다 — 코랄을 꽉 채우면 경고창처럼 공격적이라고 봤다. **이 판단은 뒤에 뒤집혔다**(결정 6-5 → 7): 실물을 보니 레드가 나았고, 최종은 **앱 `danger` 그대로 + 데이터에도 빨강**이다.

### 결정 2 — 링 게이지를 버렸다 (척도가 보이는 그래프로)

1차에서 히어로를 **링 게이지 + 중앙 금액**으로 만들었는데, 사용자가 정확히 짚었다:

> "링은 전혀 유의미한 데이터를 표현해주고 있지 않아. 최대 값이 몇 인지 그래서 얼마 쓴건지 이런게 링으로 전혀 나타나지 않잖아. 밑에 작게 적혀있는 데이터를 봐야 간신히 알 수 있어."

**맞는 지적이다. 도넛은 비율만 인코딩하고 척도(최대값·현재값)는 못 나른다.** 결과적으로 정보를 나르는 건 링 밑의 작은 캡션이었고 링은 장식이었다 — 그래프가 자리를 제일 많이 먹으면서 일을 안 하고 있었다.

**대체 1차 = 예산 바 + 카테고리 가로 바. 그런데 카테고리는 다시 걷어냈다** (아래 결정 2-1).

- **예산 바의 핵심은 양 끝에 `사용 6,800원` / `목표 10,000원` 을 직접 적는 것.** 링이 못 하던 "최대가 얼마고 얼마 썼나"가 그래프 위에서 바로 읽힌다. **이 라벨을 빼면 링 시절 문제로 되돌아간다.**
- 히어로 금액(절약/초과)은 그대로 주인공이고, '성공/실패' 는 작은 pill 로 내려간 채 유지.

**도넛/파이를 다시 넣지 말 것** — 같은 이유로 또 걸린다.

### 결정 2-1 — 카테고리 분포도 걷어냈다 (일자 그리드로)

카테고리 가로 바를 넣은 카드를 보고 사용자가 *"디자인이 너무 안 예쁜데 어디가 문제인지 모르겠다"* 고 했다. 뜯어보니 문제는 **"유의미한 데이터"를 잘못 골랐던 것**이었다:

> **카테고리 분포는 자랑거리가 아니라 정산서다.** 공유 카드의 주인공은 성취인데 "식비 3,500원 51%" 가 카드의 40%를 먹고 있었다. 남이 볼 때 흥미로운 정보가 아니고, 막대 4개가 전부 같은 민트라 서로 구분도 안 됐다.

링을 걷어낸 판단은 맞았지만 **그 자리를 카테고리로 채운 게 실수**였다. 필요한 건 "유의미한 데이터" 가 아니라 **자랑할 만한 그림**이었다.

**대체 = 일자 그리드** (카카오뱅크 26주적금 방식). 챌린지 N일을 N칸으로 그리고 무지출/지출/미기록을 색으로 칠한다.

- **칸 수가 곧 기간이라 척도가 눈에 보인다** — 링이 못 했던 바로 그것.
- **"30일을 다 채웠다" 가 그림으로 읽혀 자랑거리가 된다.** GitHub 잔디·듀오링고 스트릭과 같은 익숙한 언어다.
- 무지출 연속이 눈에 띈다 (우리 도메인 고유의 성취).
- **범례에 일수를 같이 적어**(`무지출 4일 · 지출 4일`) 범례가 곧 요약이 되게 했다. 색 이름만 있는 범례는 자리만 먹는다.

⚠️ **열 수는 기간에 따라 접는다** — 짧은 챌린지를 한 줄로 늘어놓으면 칸이 폭에 눌려 작아지고 **카드 하단이 텅 빈다.** 5~20일은 2줄, 21일 이상은 10열 3줄(세로 초과 방지). 카테고리 분포는 **상세 화면에 그대로 있으니** 정보가 사라지는 것도 아니다.

**그리드 색은 성공/실패와 무관하게 항상 민트 계열이다** — 기록한 날은 결과와 상관없이 잘한 것이고, 실패 카드까지 온통 코랄이면 카드가 우울해진다. → **이 규칙은 결정 7 에서 부분 폐기됐다**: 무지출은 늘 민트지만 **지출한 날은 실패 카드에서만 빨강**이다(잘한 날과 넘긴 날을 갈라 표시).

### 결정 3 — 축하는 두 겹 (카드 안 + 얻는 순간)

사용자 요구: *"성공 시 더 축하하는 효과가 필요하고, 얻을 때와 카드 내에도 모두."*

- **카드 안(정적)**: 컨페티가 카드에 인쇄돼 **저장·공유 PNG 와 영상 마지막 클립에도 남는다.** 성공 전용 — 실패엔 안 붙인다.
- **얻는 순간(진입 연출)**: 화면 위 오버레이로 컨페티가 쏟아진다. **캡처 대상이 아니라 PNG 엔 안 들어간다.**
- **진입 연출은 확정 직후에만** (`ResultCardScreen.celebrate`). 상세의 진입 카드로 다시 열 때마다 터지면 축하가 아니라 **지연**으로 느껴진다.

### 결정 4 — 구조를 2블록으로 (레퍼런스에서 읽은 것)

카테고리를 걷어내면서 **레이아웃 자체를 다시 봤다.** 흰 배경 하나에 요소 8개를 등간격으로 나열하니 위계가 없어 카드가 아니라 **폼(form)처럼** 읽혔다. 레퍼런스 3종([toss/reward.jpg](../references/toss/reward.jpg), [kakaobank/26주적금.png](../references/kakaobank/26주적금.png), [challengers](../references/challengers/))의 공통 문법은 이랬다:

**요소 3~5개 / 타이포 대비 극단적 / 배경이 컬러 블록.**

그래서:

- **상단 컬러 블록 + 하단 화이트 2블록** (카뱅의 크림 블록과 같은 역할). **흰 배경 하나로 두면 밍밍해진다** — 대비를 만드는 게 이 블록의 일이다. (이 시점의 채움은 옅은 틴트였고, 뒤에 **꽉 찬 민트/레드**로 강해졌다.)
- **블록이 카드의 절반 이상**을 차지하게 여백을 넉넉히 준다. 기간이 짧아 그리드가 작을 때 하단이 비어 보이는 걸 막는 장치이기도 하다.
- **히어로를 압도적으로** — 56px 이던 1차안은 카테고리 카드와 시각 무게가 비슷했다. (이때 84px 까지 키웠는데, 가이드 2번["보조 글자가 너무 다 작다"]을 반영해 **나머지를 올리면서 66px 로** 내려왔다 — 대비는 히어로만 키우는 게 아니라 스케일 전체로 만든다.)
- **콘텐츠는 블록 바로 아래 붙이고 남는 공백은 아래로 몬다.** 가운데에 띄우면(=`Expanded`+`Center`) 기간이 짧을 때 카드 하단 절반이 통째로 빈다. (블록 아래 첫 요소는 결정 8 에서 그리드 → **배지**로 바뀌었다.)
- **컨페티는 컬러 블록 안에서만** 그린다. 흰 배경에 뿌렸을 땐 콘텐츠를 피하려다 가장자리로 밀려 **축하가 아니라 액자 테두리**가 됐는데, 틴트 필드 위에 얹으니 축하로 읽힌다. 좌표는 블록 크기 대비 **비율**이라 이름이 1줄이든 2줄이든 무너지지 않는다.

### 결정 5 — 화면은 풀블리드 (AppBar 제거)

사용자 요구: *"← 챌린지 결과 부분이 없고 화면을 꽉 채우면 우선 나을 것 같아."* 맞다 — AppBar + 카드 + 버튼 3층이라 카드가 화면의 60%만 쓰고 있었다.

- AppBar 를 없애고 카드를 **화면 폭에 꽉** 맞춘다. 닫기는 **우상단 X**(헤더가 가운데 정렬이라 그 자리가 비어 있고, 좌상단은 긴 이름과 겹친다). 카드 상단 패딩이 이 버튼 자리를 비워둔 것이다.
- ⚠️ **상태바 뒤를 카드 상단 블록과 같은 색으로 덮는다.** 안 그러면 카드가 상태바 밑으로 파고들어 닉네임 줄이 시계와 겹친다. 화면 전용 처리이고 캡처물엔 상태바가 없다.
- 카드 **테두리·라운드도 없앴다.** 공유 이미지는 full-bleed 여야 하고, 화면에서도 액자처럼 보이면 카드가 작아 보인다. 카드 하단이 화이트라 아래 버튼 영역과 seamless 하게 이어진다.

### 안 건드린 것 (② 회의의 결정 유지)

색 hardcode(캡처가 ThemeData 영향을 안 받아야) · 480x864 좌표계(영상 해상도와 1:1) · 배지 `precacheImage` · off-screen RepaintBoundary 캡처 · 진입점 3지점 · 영상 마지막 3초.

### 결정 6 — 사용자가 직접 짠 가이드 (4라운드 실패 후)

다크 → 화이트 → 그리드 → 민트 채움까지 **네 번 고쳤는데 계속 "맘에 안 든다"** 가 나왔다. 내가 원칙에서 추론한 진단이 매번 빗나간 것이고, 그래서 사용자가 직접 6개 항목을 짚었다.

1. **"만원 챌린지는 누구 맘대로 붙인 거야?"** — 목표 금액은 챌린지마다 다른데(30만원짜리 테스트 데이터가 바로 그 예) 모든 카드 헤더에 "만원 챌린지" 를 박고 있었다. 서비스 컨셉 이름이지 카드가 말할 사실이 아니다. → `○○님의 챌린지`.
2. **"강조하지 않는 글자들이 너무 다 작다. 일정을 더 크게."** — 히어로만 키우고 나머지를 12~14px 로 깔아둔 게 카드를 밍밍하게 만들고 있었다. 타이포 대비를 벌린다는 게 **나머지를 뭉개도 된다는 뜻이 아니다.** 특히 일정은 부가 정보가 아니라 **성취의 조건**이다.
3. ⭐ **"7,000원 아낀 게 중요한 게 아니라 10,000원 목표를 지킨 게 중요하다."** — **내가 네 라운드 내내 틀리고 있던 지점.** 히어로가 계속 절약액이었는데 그건 성취가 아니라 **부산물**이었다. → 히어로를 `N일 동안 / {목표액} / 안에서 지켰어요` 한 문장으로 바꾸고 **절약액 계산 자체를 코드에서 제거**했다.
4. **배지에 규칙** — 단순 나열 대신 3칸 고정(성공 가운데), 타입별 최상위 등급만, 못 딴 자리는 빈 칸, 크게.
5. **실패는 빨간 계열** — 직전 라운드에서 "코랄을 꽉 채우면 공격적" 이라며 그레이를 골랐었는데 실물을 보고 레드가 낫다고 판단했다. 대신 **앱 danger 보다 어둡게**(대비 확보).
6. **색/흰색 경계가 너무 뚜렷** — 블록 하단을 투명으로 페이드시켜 경계선을 없앴다. → **이건 두 번 뒤집혀 결국 원위치했다**: 사용자가 곧바로 *"경계선 문제는 그라데이션이 해결책이 아닌 것 같다"* 고 했고(대안으로 하단을 옅은 동색으로 채우는 안을 제시했으나 그것도 흰색이 낫다고 정리), 마지막엔 *"경계선이 있어야 하는데 그라데이션으로 되어 있다"* 로 명확히 반려됐다. **지금은 선명하게 끊는다** — 페이드는 색이 바래며 끝나 **블록이 덜 칠해진 것처럼** 보였고, **컬러 블록이 하는 일이 대비를 만드는 것**이라 그 끝이 흐려지면 존재 이유가 약해진다.

**교훈: "예쁘게 해줘" 를 원칙으로 추론해서 맞히려 하지 말 것.** 네 라운드를 원칙(레퍼런스·위계·색 이론)으로 밀었지만 결과는 계속 빗나갔고, **사용자가 6줄 적어준 게 그 전부보다 정확했다.** 미감 작업에서 확실히 맞힐 수 있는 건 구조·일관성·가독성이지 취향이 아니다 — **일찍 타겟을 요청했어야 했다.**

### 결정 7 — 실패 카드: 색면을 유지하고 **빨강을 데이터로도** 쓴다

가이드 5번("실패는 빨간 계열")을 반영한 뒤에도 실패 카드만 계속 미끄러졌다. 세 번을 더 돌았다.

1. **딥 레드(`#D94F4F`) 꽉 채움** — 대비를 이유로 앱 `danger` 보다 어둡게 눌렀는데 **카드가 경고창처럼 무거워졌다.** (덧붙여 이때 내가 보고한 대비 수치 자체가 틀렸다 — 아래 함정 참고.)
2. **실패는 색면을 아예 없애고 흰 배경 + 데이터만 빨강** — 사용자 제안이었다. *"12,000원 썼어요 게이지에 초과분 2,000원을 빨강으로, 지출도 빨강으로 표시해서 전체적으로 빨간색이 보이게."*
3. **최종 = 1 + 2 를 합친 것.** *"윗면에 빨간색으로 하는 건 유지하는 게 좋을 것 같다. 데이터에 초과분을 표시하거나 지출에 대해 빨강으로 표시하는 건 유지해도 좋을 것 같아."*

색은 **앱 `danger`(`#FF6B6B`) 그대로**로 확정했다. 어둡게 누르면 무거워지고, 리워드 전용 레드를 새로 만들면 실패를 말하는 색이 앱 안에서 둘로 갈린다.

**게이지의 초과 구간이 이 라운드의 진짜 문제였다.** 빨강 블록 위라 초과분을 빨강으로 칠할 수가 없어서 딥레드(`#A32E33`)로 눌렀더니:

> **"넘긴 부분으로 읽히지는 않네. 빈 색으로 보여."**

**어두운 색은 배경/빈 칸으로 읽힌다** — 트랙과 구분이 안 된다. 그래서 **밝기를 뒤집었다**: 목표까지가 흐린 흰색(.42), **넘긴 만큼만 불투명 흰색**. 빨강 위에서 제일 밝은 게 초과분이 되니 시선이 거기로 간다. (같이 만들어본 빗금(hatch) 안은 기각.)

- 목표 지점엔 **흰 눈금 + 블록색 링** — 링이 없으면 흐린 구간 위에서 눈금이 묻힌다.
- 초과액은 사용액 옆 **흰 칩 + 블록색 글씨**(`2,000원 초과`). 빨강 위에서 가장 튀는 조합이다.
- ⚠️ **막대 아래 라벨 줄(`목표 10,000원` / `초과 2,000원`)은 넣었다가 뺐다.** 초과액은 위 칩이, 목표액은 히어로가 이미 말하는데다, **줄이 하나 붙는 만큼 빨강 면이 성공(민트)보다 아래로 내려와 두 카드의 블록 높이가 어긋났다.** 사용자가 이걸 정확히 짚었다.
- **그리드의 지출한 날도 빨강**(무지출은 결과와 무관하게 늘 민트). 88줄의 "그리드 색은 항상 민트" 규칙은 이걸로 **부분 폐기**됐다 — 잘한 날은 민트, 넘긴 날은 빨강.

### 결정 8 — 하단은 배지 → 기록 순서

사용자 제안(*"뱃지와 기록이 자리가 바뀌는 것도 좋은 것 같아"*)을 시안으로 비교해 채택했다. 성취(배지)가 블록 바로 아래 붙고 근거(기록)가 따라오면 **카드 위쪽이 "결과" 로 뭉친다.** 남는 공백은 워터마크 위 한 곳으로 몰려 이전보다 정리된다.

부수 변경: **배지 슬롯은 획득/미획득 양쪽 다 흰 원 + 테두리**다(사용자 지정). 미획득만 회색으로 채우던 안은 빈 칸이 얼룩처럼 읽혔다.

### 결정 9 — 히어로 마지막 줄은 `챌린지 성공`

`안에서 지켰어요` → `챌린지 성공했어요` → **`챌린지 성공`** 순으로 줄였다. 앞 두 줄이 이미 "N일 동안 / 10,000원" 이라 서술형으로 이으면 문장이 길어지는데, 카드가 말할 결론은 두 글자다.

### 프로세스 변경 — 시안은 이미지로만

4라운드까지는 매번 앱을 고쳐서 에뮬로 확인했는데, 사용자가 멈췄다:

> "계속 디자인이 확정이 안 됐는데 앱을 바로 수정하니까 토큰을 너무 많이 쓰게 되네. 이미지만 만들어줘보는 건 어때?"

이후는 **HTML 시안(실제 배지 자산을 base64 로 임베드, 480×864 를 62.5% 축소) → Artifact 로 게시 → 확정 후 위젯에 1회 반영**으로 돌렸다. 한 라운드에 카드 4~5장을 나란히 놓고 비교할 수 있어 오히려 판단이 빨라졌다. **디자인이 흔들리는 동안은 이 방식이 기본값이어야 한다.**

### 곁가지

- `AppColors.reward*` 토큰을 새 색으로 정합. `rewardSuccessTop`/`rewardFailTop`(상단 틴트) + `rewardBottom`(화이트) + `rewardConfetti`(3색). **accent 는 리워드 전용 토큰을 만들지 않고 앱의 `primary`/`danger` 를 그대로 쓴다** — 그게 "앱과 이어진다" 는 이 디자인의 핵심이다.
- 챌린지 상세의 **결과 카드 진입 카드**가 `rewardSuccessTop`(옛 크림색)을 틴트로 빌려 쓰고 있었다. 표면색과 용도가 달라(목록 사이에서 그 줄만 눈에 띄게 하는 색) `rewardTint`/`rewardTintInk` 로 분리했고, 거기 박혀 있던 raw hex(`0xFF8A6100`)도 토큰으로 걷어냈다.

### 함정·교훈

- **"예쁘게" 는 요구사항으로 그냥 받으면 안 된다.** 진단 5개를 먼저 깔고 "이 중 뭐가 거슬렸나" 로 물으니 4개 + 진짜 이유("자랑하고 싶다")가 돌아왔다. 그 한 문장이 없었으면 정보 위계만 고치고 끝났을 것이다.
- **"어디가 문제인지 모르겠다" 는 답을 못 준다는 뜻이 아니라, 진단이 내 몫이라는 뜻이다.** 2차 때 사용자가 정확히 그렇게 말했고, 그때 필요한 건 선택지가 아니라 **레퍼런스를 뜯어서 "요소 3~5개 / 타이포 대비 / 컬러 블록" 같은 구체적 기준을 제시하는 것**이었다.
- **자리를 제일 많이 먹는 요소가 일을 하는지 매번 확인할 것.** 링(292px)도, 카테고리 카드(카드의 40%)도 자리는 최대인데 전달하는 게 적었다. 둘 다 같은 실수의 반복이다.
- **색은 "썼다/안 썼다" 가 아니라 세기의 문제다.** 민트를 쓰긴 썼는데 명도 94% 라 안 쓴 것과 같았다. **썸네일로 줄여놓고 봐야** 이게 보인다 — 풀사이즈로만 보면 "은은하고 좋네" 로 넘어간다.
- **내부 레퍼런스만으로는 한계가 있었다.** 리포의 4종(토스·카뱅·챌린저스·뱅크샐러드)은 전부 *앱 화면*이라 구조는 배웠지만, **공유 이미지 특유의 요건**(피드에서 눈에 걸리기·썸네일 가독성)은 Wrapped 계열을 봐야 나왔다.
- **컨페티 좌표는 콘텐츠 열(좌우 패딩 36 안쪽)을 침범하면 안 된다.** 카드 안쪽은 챌린지마다 높이가 달라(카테고리 1~4줄, 배지 유무) 가운데에 조각을 두면 **어떤 조합에선 글자 옆에 붙어 오타처럼 보인다** — 실제로 제목이 2줄인 카드에서 그렇게 됐다. 지금은 최상단 띠 + 좌우 여백 + 바닥만 쓴다.
- **디자인 토큰을 지울 땐 사용처를 먼저 grep 할 것.** `rewardSuccessTop` 이 결과 카드가 아니라 **앱 화면의 입구 카드**에서 쓰이고 있었다 — 값만 바꿨으면 상세 화면이 조용히 깨졌다.
- ⚠️ **대비 수치는 계산해서 말할 것 — 눈대중으로 근거를 만들지 말 것.** 딥 레드(`#D94F4F`) 위 흰 글씨를 "4.4:1" 이라고 보고했는데 **실제로는 약 2.0:1** 이었고, 그 틀린 숫자로 "그래서 앱 `danger` 는 못 쓴다" 는 결론까지 세웠다. 게다가 그 4.5:1 기준을 **레드에만 적용하고 민트(2.36:1)는 통과시켰다** — 기준이 결론을 정당화하는 도구가 돼 있었다. 사용자가 방향을 바로잡았다(*"채도를 낮추지 말고 진하기를 낮춰야 해"*).
- **어두운 색은 "강조" 가 아니라 "빈 칸" 으로 읽힌다.** 빨강 위 딥레드로 초과 구간을 표시했더니 데이터가 아니라 배경으로 보였다. 유색 면 위에서 무언가를 강조할 땐 **더 눌러서가 아니라 더 밝게** — 그 면에서 가장 밝은 것이 시선을 가져간다.
- ⚠️ **고정 크기(480×864) 카드는 "최악 케이스" 를 정하고 거기서 여백을 맞출 것.** 이름 2줄 + 30일 그리드 + 배지 조합에서 **7.2px 넘쳤다.** 이름이 2줄이면 블록이 32px 자라 하단이 그만큼 밀리는데, 짧은 이름으로만 확인하면 안 보인다. 간격을 늘릴 때마다 **30일 카드로 재확인**할 것.
- **에뮬 스크린샷의 희미한 가로줄에 속지 말 것.** 다크 카드에서 밴딩처럼 보이는 줄이 나왔는데 **갤러리 저장 PNG(960x1728)를 뽑아 보니 깨끗했다** — 스크린샷 다운스케일 아티팩트였다. 캡처물 품질은 화면 스크린샷이 아니라 **실제 저장 파일로** 확인할 것.
- **`AppBarTheme.titleTextStyle` 은 `AppBar.foregroundColor` 를 이긴다.** 다크 시안에서 제목이 다크 배경에 다크로 그려졌다(뒤로가기 화살표는 icon theme 이라 흰색이라 더 안 보였다). 화이트로 돌아오며 해당 코드는 사라졌지만, **다크 화면을 새로 만들면 색을 `copyWith` 로 덮을 것.**

## 배지 획득 연출 (2026-08-01)

> 백로그 #8. 안건은 **"배지 획득 축하 연출을 더 풍부하게"**. 레퍼런스는 사용자가 지정한 **듀오링고 + 챌린저스**. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "배지 UI 원칙" · "설정(효과음·진동)".
> **결론: 모달 유지 + 내부 구조 재설계.** 9종 전부 동일하게 최대 연출, 칭호 없음, 컨페티는 직접 그리고, '다음 목표' 는 도달 가능할 때만 사다리·아니면 완주로 폴백. 효과음 도입에 따라 '설정' 화면을 신설했다.

### 출발점 — 백로그 문구가 사실과 달랐다

"현재 Lottie 컨페티 + 줌·바운스 연출을 더 풍부하게" 로 적혀 있었는데, **`assets/lottie/` 에 `confetti.json` 이 없었다.** 코드의 `errorBuilder` 가 조용히 생략하도록 돼 있어서 아무도 눈치채지 못한 채, 실제 연출은 줌·wobble·글로우·햅틱 1회뿐이었다.

그래서 이 작업은 "화려한 걸 더 화려하게" 가 아니라 **절반이 미완 메우기**였다. 자산을 붙이는 것만으로 체감이 달라질 수 있어, 상한부터 정하지 않고 레퍼런스를 먼저 뜯었다.

### 레퍼런스에서 읽은 것 — 우리에게 없던 4가지

리포의 [references/toss/reward.jpg](../references/toss/reward.jpg)(만보기 리워드)와 [references/challengers/](../references/challengers/)(인증 완료)를 실제로 뜯어보니 공통 문법이 있었다.

1. **획득의 크기가 숫자로 보인다** — 토스 "30원", 챌린저스 "경험치 25 / 100% 달성". 우리는 "배지 획득!" + 라벨뿐이었다.
2. **다음 목표가 있다** — 듀오링고가 사람을 붙잡는 핵심. 우리는 3/7/14/30 사다리와 상세의 게이지까지 있으면서 **정작 배지를 딴 순간에 다음 칸을 안 알려줬다.**
3. **명시적 닫기 액션** — 토스는 back, 챌린저스는 전폭 '완료' 버튼. 우리는 "탭하여 닫기" 힌트 텍스트뿐이었다.
4. **정체성 언어** — 토스 "프로 뚜벅이". 우리는 "7일 연속" 이라 수치의 이름표로 읽힌다.

### 결정 1 — 모달을 유지한다 (화면으로 빼지 않는다)

두 레퍼런스 다 화면이지만 성격이 다르다. 토스의 그것은 **리워드 수령**(돈이 지갑에 들어온다)이라 화면이 정당하고, 우리 배지는 기록을 남기다 **부수적으로** 얻는 성취다. 기록 하나 남겼는데 화면이 통째로 바뀌면 무겁고, finalize 경로에서는 배지 화면 N개 + 결과 카드가 전부 풀스크린 푸시가 된다.

대신 **모달 내부를 다시 짰다** — 지금 구조("이미지 + 텍스트 + 힌트")로는 숫자·다음 목표·CTA 가 들어갈 자리가 없어서, 연출만 얹어선 레퍼런스 수준이 안 나온다.

### 결정 2 — 9종 전부 동일하게 최대 연출 (등급 차별화 없음)

듀오링고는 마일스톤(7·30·100일)만 특별대우하고, 나는 처음에 "30 + 챌린지 성공만" 을 추천했다. **사용자 결정은 전부 동일하게 최대치.**

그리고 **자산을 열어보니 이 결정이 오히려 잘 맞았다** — 배지 PNG 가 이미 브론즈(3) → 실버(7) → 골드(14) → 주얼골드(30) 사다리로 그려져 있었다. **연출을 똑같이 해도 자산의 색이 위계를 만든다.** 30일이 더 무겁게 느껴지면서도 3일짜리가 홀대받지 않는다.

다만 **글로우가 `rewardGlow` 골드 고정이라 구리색 3일 배지와 어긋나 있었다** → 아래 결정 4.

### 결정 3 — 칭호는 도입하지 않는다

"7일 연속" → "꾸준함의 증명" 같은 이름을 9종에 붙이는 안. **기각.** 매핑 테이블이 하나 더 늘고, 자산이 이미 숫자를 크게 박고 있어 이름과 숫자가 경쟁한다.

### 결정 4 — 색은 **단계**로 갈린다 (타입 아님), 파티클은 직접 그린다

`streak_3` 과 `no_spend_3` 이 같은 구리색이라 **매핑이 9개가 아니라 5개**(3/7/14/30/성공)면 된다. 유지보수 지점이 절반 이하로 줄었다.

컨페티를 **Lottie 대신 `CustomPainter`** 로 그린 이유가 바로 이 색 연동이다 — Lottie 는 색·수량·방향이 JSON 에 박혀 있어 배지 색을 따라갈 수 없다. 덤으로 `lottie` 의존성을 통째로 뺐다(다른 데서 안 썼다).

세부 호응 2건: **30·성공은 파티클을 다색**(자산에 박힌 시안·핑크·퍼플 보석과 맞춤), **반대로 광택 sweep 은 약하게**(그 자산들은 반짝임이 이미 그려져 있어 세게 걸면 겹쳐서 지저분해진다).

### 결정 5 — '다음 목표' 는 사다리를 그대로 읽으면 거짓말이 된다

**사용자 지적이 이 안건을 살렸다**: *"우린 챌린지에 기간이 있으니까, 챌린지가 5일짜리면 7일 배지를 얻지 못해."*

문제는 두 겹이었다. ① **기간 상한** — 5일짜리는 7/14/30 이 처음부터 불가능 ② **남은 기간** — 10일짜리라도 8일차면 STREAK 7 은 이미 불가능(연속이라 남은 2일로는 못 채운다). 그래서 판정은 사다리가 아니라 **`현재값 + 남은 일수 >= 다음 칸`** 이다.

**폴백은 위로가 아니라 실제 다음 페이오프다.** 사다리가 막혀도 `CHALLENGE_SUCCESS` 는 기간과 무관하게 살아 있으므로 "챌린지 종료까지 N일" 이 참이면서 정확히 다음 배지를 가리킨다.

**버린 대안 — "이 챌린지 배지 3개 중 2번째" 식의 분모 표기.** 진행 중에 사다리가 막히면 분모가 실제보다 커서 **못 딸 배지를 딸 수 있는 것처럼** 보인다. 챌린저스의 "100% 달성" 이 정직한 건 인증률이 실시간 값이라서고, 우리 분모는 그렇지 않다.

현재값은 **방금 받은 배지의 `conditionValue`** 로 본다. 배지는 칸을 넘는 순간 지급되므로 획득 시점의 현재값과 같고, 이렇게 하면 연속/누적 집계를 클라에서 다시 구현하지 않아도 된다(서버가 진실의 원천).

### 결정 6 — 페이싱은 연출 강도가 아니라 CTA 로 푼다

"전부 최대 연출" 의 부작용: STREAK+NO_SPEND 동시 획득이 실제로 가능해 **최대 연출이 2연속**이고, finalize 때는 결과 카드까지 붙는다. 등급 차별화를 안 하기로 했으니 강도로는 못 줄인다.

듀오링고 방식대로 **CTA 라벨이 체인의 길이를 밝힌다** — `다음 (1/2)` → `완료`. 몇 개 남았는지 알면 반복이 지루함이 아니라 **수확**으로 읽힌다. "탭하여 닫기" 힌트를 명시적 버튼으로 바꾸는 것과 같은 작업이라 추가 비용도 없었다.

### 결정 7 — 효과음을 넣고, 그래서 '설정' 화면이 생겼다

효과음을 넣으면 **카메라 녹화 시작음도 같은 토글을 따라야 한다** — 아니면 "효과음 끔" 인데 촬영할 때만 소리가 나는 모순이 생긴다. 같은 논리로 **진동 토글은 앱의 모든 햅틱**(배지·녹화 시작·시간 휠)에 적용했다. ([[feedback-consistency-over-pinpoint]])

- **메뉴에 '설정' 신설**, 그 바람에 **'계정 설정' 을 '계정 정보' 로** 바꿨다 — 나란히 두면 "설정이 두 개" 로 읽힌다. `내 정보`(본인 정보) / `계정 정보`(계정 자체) / `설정`(앱 동작 환경) 3분으로 경계를 다시 그었다. 표시 라벨만 바꾸고 클래스·파일명은 유지(브랜드를 TenK 로 통일할 때 내부 식별자를 안 건드린 것과 같은 논리).
- **이름을 '알림/효과 설정'(예고된 이름)이나 '소리 및 진동' 으로 하지 않은 이유**: 앱에 푸시 알림이 아직 없어 전자는 헛걸음을 부르고, 후자는 나중에 알림이 들어올 자리가 없다. **'설정' 은 지금 정확하고 나중에도 맞는다.** 푸시 알림 자체는 별도 백로그 #17 로 분리했다.
- **`#15` 트리거에는 걸리지 않는다** — 설정은 앱 전역 값이지만 **구독자가 없다**(재생 직전에 읽고, 리빌드가 필요한 건 설정 화면 자신뿐). `SettingsScope` 하나 추가(8개째, 임계 10 미만)로 끝났다.
- 저장은 `shared_preferences` 신규 도입. 토큰용 `flutter_secure_storage` 는 설정에 쓰기엔 과하고 느리다.

### 곁가지 — 실제로 잡아낸 것 3건

- **사다리 상수 사본** — `_NoSpendTodayCard._ladder` 를 `kBadgeLadder` 로 승격해 '다음 목표' 와 공유. 사본이 셋이 될 뻔했다.

## DB 코드성 컬럼 정리 (2026-07-30)

> 백로그 #9. 안건은 **"문자열로 저장 중인 코드성 컬럼을 enum 으로 정리하자"**. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "코딩 컨벤션 — 백엔드" + "지출(amount) — 카테고리".
> **결론: 두 축으로 갈라서 둘 다 실행.** ⓐ DB 자료형을 `VARCHAR` 로 통일(네이티브 `ENUM` 3개 제거) ⓑ `amount.category` 를 `@Enumerated(STRING)` 으로 전환. 룩업 테이블은 도입하지 않는다.

### 조사 — 전제가 절반쯤 어긋나 있었다

착수 전 목록화를 해보니 **두 개의 다른 축이 각각 어긋나 있었고**, 백로그 문구는 그중 하나만 가리키고 있었다.

| 축 | 현황 |
|---|---|
| **Java 매핑** | 8개 중 7개가 이미 `@Enumerated(STRING)`. 남은 건 `amount.category` 하나 |
| **DB 자료형** | `user.provider` · `challenge.result` · `badge.type` 만 네이티브 `ENUM(...)`, 나머지 5개는 `VARCHAR` |

`@Enumerated(EnumType.STRING)` 은 **DB 자료형이 아니라 Java↔DB 매핑 방식**이라 상대 컬럼이 `ENUM` 이든 `VARCHAR` 든 정상 동작한다(그래서 `ddl-auto=validate` 가 통과하고 있었다). 두 축을 뭉개면 "7개는 끝났다" 는 잘못된 결론이 나온다.

DB 자료형이 갈린 이유도 설계가 아니라 **시간순 흔적**이었다 — 초기 테이블은 `ENUM` 으로 만들었고, 이후 `ALTER` 로 추가한 컬럼(`gender`/`role`)과 새 테이블(`feedback`/`withdrawal_feedback`)은 전부 `VARCHAR` 로 갔다.

**`@Enumerated(EnumType.ORDINAL)` 은 한 곳도 없다** — 상수 순서만 바꿔도 과거 데이터 의미가 뒤집히는 진짜 위험 패턴인데, 애초에 안 쓰고 있었다.

### 결정 1 — DB 자료형은 `VARCHAR` 로 통일 (네이티브 `ENUM` 제거)

**핵심 논거는 "상수 목록이 두 곳에 생긴다"** 는 것. Java enum 이 진실의 원천인데 DB 도 자기 목록을 들고 있어 어긋난다. 우리 코드에 이미 두 사례가 있었다:

- **`AuthProvider.TEST`** — 코드에선 `@Deprecated` 인데 DB `ENUM` 엔 멀쩡히 살아 있다. 지우려면 `ALTER TABLE` 이 필요하다.
- **`Gender.OTHER` 제거(2026-07-29)** — `gender` 가 `VARCHAR` 라 `UPDATE` 한 줄로 끝났다. `ENUM` 이었으면 `UPDATE` + `ALTER` 둘 다 필요했다. **하루 전에 `VARCHAR` 의 유연함이 실제로 이득이 된 사례.**

그 외 `ENUM` 의 함정: 값 추가는 목록 끝에 붙일 때만 싸고 중간 삽입·삭제는 테이블 재구축 / `ORDER BY` 가 사전순이 아니라 선언 순서 / **정수와 비교하면 인덱스로 해석**된다(`WHERE result = 1` 이 첫 번째 값과 매칭) / MySQL·MariaDB 전용.

**`ENUM` 의 최대 장점은 다중 쓰기 주체 방어**인데 TenK 은 앱이 DB 를 단독 소유해 해당 없다. 업계 관행도 같은 방향이다 — JPA·Django·Rails 모두 코드성 컬럼의 기본 매핑이 `VARCHAR`(또는 `INT`) + 앱 레벨 enum 이고, DB 네이티브 `ENUM` 이 아니다. (다만 이 통념은 상당 부분 **MySQL `ENUM` 경험**에서 나온 것이라, 값 추가가 싼 Postgres 에 그대로 옮기는 건 과한 일반화다.)

**이 `ALTER` 는 코드 배포와 순서 커플링이 없다** — 양쪽 자료형 모두 validate 를 통과하므로 언제 쳐도 되고 되돌리기도 쉽다. 다른 배포 SQL 과 성격이 다르니 런북에도 그렇게 표기했다.

### 결정 2 — `amount.category` 를 `@Enumerated(STRING)` 으로

raw String 이었던 근거는 *"쓰기는 엄격, 읽기는 관대"* — 카테고리 검증 도입(2026-07-11) **이전에** 저장된 자유 텍스트 row 를 읽을 때 enum 매핑 크래시를 피하려던 것이었다. **이 근거엔 유효기간이 있다.** 레거시 row 를 `ETC` 로 접고 나면 남는 건 방어 가치 없는 String 필드뿐이고, 지금이 가장 싼 시점이다(로컬 0건, 라이브도 내부 테스터뿐).

마이그레이션이 **사용자 눈에 무변화**인 게 이 결정을 싸게 만들었다 — 클라의 `spendCategoryForCode()` 가 이미 미매칭 코드를 '기타'로 폴백해 그리고 있어서, `ETC` 로 접으면 화면 결과가 동일하다.

### 결정 3 — 변환 지점은 엔티티 안, DTO 는 `String` 유지

`Amount.spend()/update()` 의 **시그니처는 `String` 그대로** 두고 내부에서 `SpendCategory.from()` 으로 변환한다. 검토한 대안(팩토리 파라미터를 enum 으로 올리고 서비스에서 변환)은 **세 가지를 깨뜨린다**:

1. **에러 코드가 뭉개진다** — 서비스가 먼저 파싱하면 빈 카테고리가 `AMOUNT_CATEGORY_CONTENT_REQUIRED`(A0005) 대신 `AMOUNT_CATEGORY_INVALID`(A0008) 로 나간다. 그래서 `from` 은 **null·공백에 예외를 던지지 않고 null 을 반환**하도록 계약을 잡았다(미입력 판정은 엔티티가 먼저).
2. **무지출 수정이 깨진다** — 무지출은 "카테고리를 서버가 무시" 하는 게 도메인 규칙인데, 서비스가 눈치 없이 먼저 파싱하면 무시돼야 할 값이 예외를 던진다. 엔티티의 noSpend 분기는 파싱 전에 early return 한다.
3. **검증이 엔티티 밖으로 샌다** — "엔티티 정적 팩토리가 invariant 를 검증한다" 는 프로젝트 컨벤션과 어긋난다.

**요청 DTO 를 enum 으로 올리지 않은 이유**도 같은 계열이다 — Jackson 이 먼저 파싱에 실패하면 A0008 의 한국어 메시지 대신 범용 400 이 나간다. **응답 DTO 는 `.name()` 으로 코드 문자열을 유지**해 wire format 을 안 건드렸다(Flutter 변경 0). 이게 B 의 유일한 실질 리스크라 회귀 가드를 따로 뒀다.

### 결정 4 — 룩업 테이블은 도입하지 않는다

판단 기준은 **"코드 말고 그 값에 딸린 다른 정보가 있는가"**. 해당하는 건 `badge`(조건값·아이콘 경로) 하나이고 **이미 룩업 테이블**이다. 나머지는 코드가 전부라 테이블을 만들면 컬럼 하나짜리가 된다.

`SpendCategory` 만 애매했는데 — 라벨(`식비`)은 있지만 **아이콘이 Dart `IconData` 라 DB 에 넣을 수 없다.** 옮기면 "라벨은 DB, 아이콘은 코드" 로 오히려 갈라지고, 라벨 변경이 코드 리뷰·git 이력을 안 거치게 된다. 현행(라벨=서버 enum, 아이콘=클라 상수)이 낫다.

### 함정 — 네이티브 SQL 테스트 헬퍼가 검증을 우회하고 있었다

전환 후 통합 테스트 **5건이 `No enum constant SpendCategory.x` 로 깨졌다.** 원인은 `AmountRepositoryIntegrationTest`/`BadgeEventIntegrationTest` 가 시딩 속도를 위해 네이티브 `INSERT` 로 `'x'`·`'test-category'` 를 박고 있었던 것 — 엔티티 검증을 우회하니 **쓸 땐 통과하고 읽을 때 죽는다.**

고친 것 자체는 사소하지만(유효 코드로 교체), **이게 enum 전환이 실제로 잡아낸 종류의 문제**다. String 이었다면 영원히 드러나지 않았다.

### 검토했다 버린 대안

- **전부 네이티브 `ENUM` 으로 통일** — 일관성은 얻지만 값 변경마다 `ALTER` 가 붙고 이중 진실의 원천이 남는다.
- **`VARCHAR` + `CHECK` 제약** — MariaDB 10.2.1+ 부터 실제로 강제돼 절충안이 되지만, **목록 변경에 `ALTER` 가 필요한 건 `ENUM` 과 똑같아** 주된 불만을 해결하지 못한다.
- **현행 유지** — 고장이 없다는 건 사실이라 유효한 선택지였다. 다만 새 컬럼이 계속 `VARCHAR` 로만 추가돼 격차가 벌어지고, `amount.category` 는 실사용 데이터가 쌓이면 되돌리기 비싸진다.
- **`AuthProvider.TEST` 상수 동시 제거** — 별건으로 남겼다. 기존 로컬 데이터 호환이 깨진다. 결정 1 덕에 이제 `UPDATE` 한 줄로 지울 수 있다.

## Flutter 상태 관리 재검토 (2026-07-29)

> 백로그 #15. 안건은 **"Scope 가 7개가 돼 자체 임계(5개)를 넘겼는데, Riverpod 으로 갈 때인가"** 하나. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "레이어 규칙".
> **결론부터: 현행 유지 — 임계를 10개로 상향하고 진짜 트리거를 따로 명문화. 코드 변경은 주석 2곳뿐.** 이 회의록은 *왜 안 옮겼는지*와 *언제 옮겨야 하는지*를 남기려고 쓴다.

### 출발점 — 임계를 넘긴 건 사실이다

[scopes.dart](../tenk_app/lib/app/scopes.dart) 에 `Auth`/`Challenge`/`Amount`/`Media`/`User`/`App`/`Feedback` **7개**가 있고, CLAUDE.md 는 "5개를 넘기면 재검토" 라고 적어뒀다. `AppScope` 에는 임계를 넘겼다는 경고 주석까지 달려 있었다.

### 진단 — 이름이 "상태 관리"였을 뿐, 지금 있는 건 DI 다

**Scope 안에 든 건 전부 stateless 싱글턴이다.** `ChallengeApi` 류는 HTTP 호출 메서드만 있고 필드를 들고 있지 않으며, 앱 부팅 때 [main.dart](../tenk_app/lib/main.dart) 에서 한 번 만들고 끝이다. 그래서 `updateShouldNotify`(`api != oldWidget.api`) 가 **사실상 영원히 false** — 이 위젯들은 트리에 값을 흘리지 않고 그냥 **`getBean()` 통로**로만 쓰인다.

실제 상태는 화면별 로컬(`AsyncStateMixin` 의 `_loading/_data/_error`)에 있고, 화면 간 공유가 필요하면 명시적으로 넘긴다(메뉴 → 계정 설정에 `User` 전달). **즉 "여러 화면이 같이 보고 한쪽이 바꾸면 다른 쪽도 알아야 하는" 상태가 아직 하나도 없다.**

정리하면 문제는 둘로 갈린다:

| | 지금 상태 |
|---|---|
| **DI 부담** | 있음 — 중첩 7단 + Scope 하나 추가마다 생성·필드·중첩 **3곳** 수정 |
| **상태 관리 부담** | **없음** — 공유할 상태 자체가 없다 |

Riverpod 은 DI 와 상태 관리를 한 몸으로 파는 물건이라, 후자가 0 인 지금 도입하면 **전 화면의 `Scope.of` 호출부를 갈아엎는 비용만 치르고 얻는 건 중첩 정리뿐**이다.

### 결정 1 — 임계를 5 → 10 으로 올린다

5 라는 숫자는 규칙을 처음 박을 때 감으로 잡은 값이고 **근거가 없었다**. 개수는 리빌드·정합성 어디에도 영향을 주지 않으므로, 임계가 하는 일은 "언젠가 중첩이 읽기 힘들어지면 한 번 돌아보라"는 알림뿐이다. 7개인 지금 `main.dart` 는 아직 한눈에 읽히므로 10 으로 올린다.

### 결정 2 — 진짜 트리거를 따로 못 박는다 (핵심)

숫자만 올리면 다음 사람이 **8개째에서 같은 고민을 처음부터 반복한다.** 그래서 규칙에 "개수는 보조 지표이고 착수 트리거는 **화면 간 공유 상태가 생길 때**"를 같이 적었다.

구체적인 예가 이미 코드에 있다 — 배지 축하 모달은 지금 챌린지 상세의 reload diff 로만 감지하고, CLAUDE.md 는 "다른 진입점에서도 알리려면 global `BadgeNotifier` 로 승격(현재 범위 밖)" 이라고 적어뒀다. **그 승격이 곧 첫 공유 상태**고, 그때가 재검토 시점이다.

### 결정 3 — 중첩 평탄화도 지금은 안 한다

라이브러리 없이 중첩만 줄이는 안(서비스 로케이터 객체 하나에 담아 Scope 1개로, 또는 `List<InheritedWidget>` 접기 헬퍼)도 검토했다. 화면 코드를 안 건드려도 되는 싼 수술이지만 **지금 아픈 데가 없고**, 타입별 Scope 는 "이 화면이 무엇에 의존하는가" 가 호출부에 드러나는 장점이 있어 굳이 뭉개지 않기로 했다. 중첩이 실제로 읽기 힘들어지면(=임계 10) 그때 1순위 후보.

### 검토했다 버린 대안

- **지금 Riverpod 도입** — 위 진단대로 상태 관리 수요가 0 이라 전 화면 이관 비용을 정당화할 수 없다. 과설계.
- **임계 자체를 폐기** — 알림이 사라지면 중첩이 20단이 돼도 아무도 안 본다. 숫자는 무의미하지만 **알림 장치로는 값이 있어** 남긴다.
- **`AppScope` 의 경고 주석만 지우기** — 경고를 지워도 CLAUDE.md 의 5개 규칙이 남아 다음 세션에 같은 안건이 또 올라온다. 규칙을 고치는 게 맞다.

### 전수 조사부터 — 백로그가 짚은 것보다 넓었다

백로그 #4 는 대상을 3개(카테고리 셀렉박스 / 성별 팝업 / 닉네임 팝업)로 적어뒀는데, 전수로 훑으니 모달이 **16곳**이었고 같은 종류가 둘 더 있었다:
**챌린지 이름 변경**(닉네임과 동형인 텍스트 입력+검증)과 **의견 유형 셀렉박스**(카테고리와 같은 `DropdownButtonFormField`).
짚어준 것만 고치면 반쪽이 남는 전형적인 경우라 같이 넣었다 ([[feedback-consistency-over-pinpoint]]).

### 결정 — 갈림길은 "맥락을 유지해야 하나" 하나다

| 성격 | 형태 | 근거 |
|---|---|---|
| 파괴적 행동 확인 · 흐름 차단 알림 | **다이얼로그 유지** | 확인을 화면으로 빼면 되돌릴 자리가 멀어져 오히려 위험 |
| '내 정보' 의 내 속성 편집 | **화면** | 설정형 드릴다운이라 떠나도 맥락이 안 끊기고, 검증 에러·안내가 길다 |
| 폼·목록 안에서 값 하나 고르기 | **바텀시트** | 입력 중인 폼·진행 중인 챌린지·클립 목록이 계속 보여야 한다 |

닉네임과 챌린지 이름은 **입력 형태가 같은데도 갈렸다** — 전자는 '내 정보' 항목이고 후자는 상세 화면의 맥락 안에서 고치는 값이라서. 처음엔 "둘은 동형이니 같이 가야 한다"고 봤는데, 이 기준을 세우고 나니 **갈리는 게 맞다**로 뒤집혔다.

### 구현에서 걸린 것

- **`DropdownButtonFormField` → 바텀시트는 검증을 잃는다.** 카테고리는 `validator` 로 미선택을 막고 있어서, 대체 위젯 [SelectionField](../tenk_app/lib/presentation/common/selection_field.dart) 를 **`FormField` 로 감싸** `Form.validate()` 흐름을 그대로 살렸다. 의견 유형은 Form 이 없고 버튼 비활성으로 검증해서 상태만 옮겼다.
- **탭 필드 룩이 중복될 뻔했다.** 날짜·시간 칸의 `_FieldBox` 가 `date_time_fields.dart` 안에 사유화돼 있었는데 카테고리 칸도 같은 룩이 필요해, 공용 [TapFieldBox](../tenk_app/lib/presentation/common/tap_field_box.dart) 로 추출하고 날짜 칸도 갈아탔다.
- **자막 편집은 이미 바텀시트였다** — 전환이 아니라 공용 위젯으로 흡수. 그 과정에서 `InputDecoration` 에 `OutlineInputBorder` 를 직접 박아 테마를 우회하던 것도 정리됐다(폼 규칙 위반이었다).

### 범위에서 뺀 것

배지 축하 모달(연출), 날짜·시각 picker(공용 헬퍼로 이미 통일 + 휠 규격이 규칙으로 박혀 있음), `showLicensePage`(이미 화면).

## 성별 수집·변경 (2026-07-29)

> 백로그 #16. 안건은 **"성별을 나중에 바꿀 수 있게 두는 게 맞는 동작인가"** 하나. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "성별 (선택 수집)".
> **결론부터: 현행 유지 — 코드·스키마·문서 변경 0.** 이 회의록은 *왜 안 바꿨는지*를 남기려고 쓴다.

### 출발점 — 걱정은 "무의미한 데이터"였다

제기된 우려는 *성별은 특별한 경우가 아니면 바뀌는 게 아닌데, 수정할 수 있게 두면 무의미한 데이터만 쌓이는 것 아닌가* 였다.
정당한 우려지만 **편집 차단은 이 문제에 듣지 않는 레버**라는 게 회의의 핵심 결론이다.

### 결정 1 — 자유 변경·철회를 유지한다

**노이즈는 편집이 아니라 입력에서 들어온다.** 잘못된 값이 생기는 경로는 셋뿐이고, 편집을 막으면 오히려 나빠진다:

| 경로 | 편집을 막으면 |
|---|---|
| 오탭·실수 | 틀린 값이 **영구 고착** — 우려한 오염을 오히려 만든다 |
| 일부러 거짓 입력 | 최초 입력에서 이미 발생. 막든 안 막든 동일하고, 거짓이 박제될 뿐 |
| 호기심으로 바꿔봄 | 편집이 여는 유일한 경로지만 **바꿔도 화면에 아무 변화가 없어** 탐색할 게 없다 |

전제도 한 겹 어긋나 있었다 — **우리가 여는 건 '성별 변경'이 아니라 '입력값 정정'이다.** 성별이 잘 안 바뀐다는 건 맞지만 이 컬럼에 든 값은 실제 성별이 아니라 *사용자가 입력한 값*이고, 입력은 실제로 틀린다.

막을 수 없는 이유도 둘 더 있다:
- **법**: 정보주체의 정정·삭제 요구권(개인정보 보호법 제36조)과 처리정지·동의철회권(제37조). 앱에서 막아도 권리가 사라지는 게 아니라 **문의 창구로 수작업 처리할 의무만 남는다**. 같은 법 제3조③은 처리자에게 **정확성·최신성 보장**을 요구하므로, 정정을 막는 건 정확성 원칙을 거스르는 쪽이다.
- **이미 공개한 약속**: [privacy.html](../tenk-backend/src/main/resources/static/privacy.html) §1 에 *"입력한 뒤에도 언제든 '입력 안 함'으로 되돌려 삭제할 수 있습니다"* 가 명시돼 있다. 막으려면 공개 방침을 **이용자 권리를 줄이는 방향으로** 개정해야 하는데 근거를 댈 수 없다.

**업계 관행 대조**: 성별 변경을 잠그는 국내 서비스는 ① 본인확인기관 실명인증으로 값을 받은 경우(사용자가 임의로 바꾸면 인증의 의미가 사라짐) ② 성별이 혜택·매칭과 직결된 경우(어뷰징 방지) 둘뿐이다. TenK 은 **자기신고 값이고 아무 혜택과도 연결돼 있지 않아** 두 근거 다 해당 없음. 프로필에서 자유 변경이 이 유형의 표준.

### 결정 2 — 변경 이력·변경 시각을 남기지 않는다 (신설)

"통계 신뢰도"를 걱정하면 자연히 나오는 대안이 *변경 이력을 남기자* 인데 **이건 하면 안 되는 방향**이라 규칙으로 못 박았다.
성별 변경 이력은 일반 개인정보가 아니라 **트랜스젠더 아웃팅 위험이 있는 정보**다. 지금 이력이 안 남는 건 설계 의도가 아니라 우연이라, 누가 "감사 목적"으로 컬럼 하나만 붙여도 조용히 위험이 생긴다.

### 결정 3 — 수집 항목 자체는 현행 유지

제거도, 제거 트리거를 거는 것도 하지 않기로 했다.

### 이 통계를 진짜로 망가뜨리는 요인 (기록만)

편집 churn 이 아니라 **자기선택 편향**이다. 성별은 가입 흐름 밖에 있어 '내 정보'에 들어가 스스로 눌러야 입력되므로 ① 응답률이 낮고 ② 굳이 입력하는 층이 전체를 대표하지 않는다. 응답률이 낮으면 그 표본의 성비는 전체 성비의 근거가 못 된다.
**이건 편집을 막든 말든 그대로 남고**, 고치려면 필수로 만드는 수밖에 없는데 기능에 안 쓰는 항목이라 최소수집 원칙상 불가다. 즉 편집 허용 여부로 답할 문제가 아니라 **항목 존폐로 답할 문제** — 그래서 결정 3 과 한 묶음으로 다뤘다.

### 후속 — `OTHER` 제거 + 3칸 토글 (같은 날, #4 작업 중)

입력 UI 를 `SegmentedButton` **남성 / 입력 안 함 / 여성** 3칸으로 바꾸기로 하면서 `Gender.OTHER` 를 **enum 에서 지웠다**.
평소 원칙("이미 쌓인 상수는 지우지 말 것")의 예외인데, **아직 내부 테스트 데이터뿐이라 잃을 통계가 없다**는 판단이었다(사용자 확인).

- '입력 안 함' 을 **가운데**에 둔 건 좌우가 값이 되는 대칭 배치라서다. 세그먼트의 가운데가 *중간값*으로 읽힐 수 있다는 점은 검토했고, `OTHER` 가 사라져 축 위에 성별이 둘만 남으므로 그 오해의 소지도 같이 사라졌다.
- 선택 항목의 요건("'입력 안 함' 을 값들과 동등하게 노출")은 **칸 하나로 승격**되면서 오히려 강화됐다 — 예전 다이얼로그에선 라디오 4번째 항목이었다.
- ⚠️ **enum 상수 삭제는 DB 정리와 한 쌍이다.** `@Enumerated(EnumType.STRING)` 이라 enum 에 없는 문자열이 남아 있으면 그 유저 조회가 예외로 죽는다. 로컬은 `OTHER` 행이 0건이었고, 라이브는 §0-DEPLOY 에 `UPDATE user SET gender=NULL WHERE gender='OTHER';` 를 넣었다.

### 검토했다 버린 대안

- **성별 변경 차단(1회 확정)** — 위 결정 1 의 세 근거로 기각. 오탭이 영구 고착돼 데이터 품질이 오히려 나빠진다.
- **닉네임식 쿨다운(24h)** — 닉네임의 쿨다운은 *표시 이름이 자주 바뀌면 다른 사용자가 혼란스럽다*는 근거인데, 성별은 **남에게 보이지 않고 바꿔서 얻을 이득도 없어** 그 근거가 통째로 없다. 어뷰징 유인이 0 인 곳에 마찰만 남는다.
- **변경 이력 테이블** — 결정 2 대로 아웃팅 위험. 통계 정확도를 위해 더 민감한 정보를 만드는 교환은 성립하지 않는다.

## 의견 보내기 (2026-07-28)

> 백로그 #2 의 마지막 항목("피드백 보내기")을 닫은 회의. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "의견 보내기 (피드백)".

### 출발점 — 사용자 지적으로 전제가 바뀌었다

처음에 나는 **mailto(메일 앱 열기)** 를 추천했다. 논거는 "인앱 폼은 회신 경로가 없고, 받아놓고 아무도 안 읽는 구조가 된다" 였다. 사용자가 두 가지를 짚었다.

1. **"고객센터/문의 기능과 피드백 기능은 다르지 않아?"** — 맞다. 그리고 이 구분이 내 반대 논거를 무너뜨린다. **피드백에는 애초에 회신이 전제되지 않는다.** "회신이 안 된다"는 인앱 폼의 결함이 아니라 피드백의 성질이다.
2. **"그냥 앱 내에 글 남기게 하고, 난 DB로 보면 되지"** — 이것도 맞다. 피드백은 **즉시 처리해야 하는 큐가 아니라 모아서 훑는 데이터**라 관리자 UI 없이 SQL 조회로 충분하다. 문의였다면 방치가 곧 실패지만, 피드백은 아니다.

세 번째로 **비용 전제도 틀렸다** — "스키마 변경 + 재배포가 는다"고 봤는데, §0-DEPLOY 묶음이 **아직 안 나간 상태**라 `CREATE TABLE` 하나를 얹는 한계비용이 거의 0이었다.

### 리서치 — 국내 표준·사례

- **[KRDS(정부 디지털서비스 디자인시스템)](https://www.krds.go.kr/html/site/global/global_05.html)** 는 '사용자 피드백'을 독립 패턴으로 정의한다. 구성(제목/설명/평가/추가질문/완료 메시지), 배치(**과업을 방해하지 않게**), 수집 순서(**폐쇄형 먼저, 자유서술 마지막**). 그리고 *"심도 깊은 평가나 복합 질문은 별도 문의 채널로"* — **표준도 둘을 병존시키되 역할을 나눈다.**
- **현업 아티클**: 고객센터로 오는 사람은 *내 돈·내 시간이 걸린 긴급 상황*, 피드백은 *낮은 긴급도에서 우선순위 근거를 모으는 것*. 고객센터 = 현재 문제 해결, 피드백 = 미래 제품 개선.
- **가장 중요한 발견 — 문의 창구가 없으면 불만은 스토어 리뷰로 간다.** ["칭찬은 스토어로, 불만은 이메일로"](https://velog.io/@tykan/%EC%8A%A4%ED%86%A0%EC%96%B4-%EB%A6%AC%EB%B7%B0-%EB%B3%84%EC%A0%90-%EC%96%B4%EB%96%BB%EA%B2%8C-%EC%98%AC%EB%A6%B4%EA%B9%8C)로 분기를 넣은 뒤 1~2점 리뷰가 줄고 평점이 회복된 사례가 있다. 초기 앱에 1점 몇 개는 설치율에 직격이고 되돌리기도 어렵다.

### 결정

**하나의 화면으로 합치되, 답변 여부는 '회신 이메일'로 가른다.**

대형 앱이 문의와 피드백을 나누는 건 **CS 팀과 제품 팀이 서로 다른 큐를 보기 때문**인데, TenK 은 받는 사람이 한 명이라 그 이유가 성립하지 않는다. 대신 유형 칩(불편/오류 · 기능 제안 · 좋았던 점 · 기타)으로 분류만 하고, **"답을 원하는가"는 회신용 이메일을 적었는지 하나로 판정**한다.

**유형으로 판정하지 않는 이유**: 같은 '불편/오류'라도 답을 원하는 사람과 그냥 알려주는 사람이 갈린다. 유형은 *무엇에 대한 이야기인가*고, 이메일은 *답을 원하는가*다. 서로 다른 질문이라 하나로 대신할 수 없다.

그리고 이메일 칸 아래에서 **"답변이 필요할 경우에만 적어주시면 돼요"** 로 밝힌다. 답을 기다리게 해놓고 안 주는 건 창구가 아예 없는 것보다 나쁘다.

### 익명 저장 — `withdrawal_feedback` 의 논리를 그대로

`feedback` 테이블에 **`user_id` 를 두지 않는다.** 계정과 연결하지 않으면 개인정보가 아니라 익명정보라서 보관 기간 논쟁이 없고 계정 파기 후에도 남는다.

**예외는 `reply_email` 하나.** 이건 그 자체로 개인 식별자라 privacy.html 수집표에 '선택' 한 줄이 들어갔다. 여기서 한 가지를 더 정했다 — **"답변 후 파기, 미회신 시 최대 1년"을 문서에만 적지 않고 배치로 강제**한다([FeedbackRetentionScheduler](../tenk-backend/src/main/java/com/hjson/tenk/domain/feedback/FeedbackRetentionScheduler.java), 매일 01:40). 사람이 답장 후 지우는 건 반드시 빠지고, 그러면 **개인정보처리방침에 적어놓고 실제로는 계속 갖고 있는 상태**가 된다. 이메일만 지우고 본문은 남긴다.

Play 데이터 안전에서는 **한 화면인데 항목별 답이 갈린다** — 의견 내용은 `연결 = 아니요`, 회신 이메일은 `연결 = 예`. [play-console-app-content.md](play-console-app-content.md) §6-2 참고.

### 법적 검토 — 인앱 고객센터는 의무가 아니다

사용자가 "고객센터/문의 기능이 없어도 법적으로 괜찮냐"고 물어 정리했다.

- **개인정보보호법**: 처리방침에 보호책임자 연락처 기재 + 열람·정정·삭제 요구 접수 경로가 의무다. **형식은 이메일이면 되고 인앱 채널을 요구하지 않는다.** privacy.html §9(당시 §8) 로 이미 충족.
- **전자상거래법**: 표시 의무는 **통신판매업자** 대상. TenK 은 결제·재화 판매가 없어 해당 없음 — 덤으로 **환불·주문 문의라는 유형 자체가 구조적으로 안 생긴다**.
- **Google Play**: 스토어 등록정보의 개발자 이메일 + 계정 삭제 경로(이미 있음). 인앱 문의 기능은 요건이 아니다.

**진짜 리스크는 "고객센터가 없어서"가 아니라 "고지한 이메일을 안 봐서"** 다. 열람·삭제 요구는 받은 날부터 10일 이내 조치가 원칙이라, 방치된 메일함이 곧 위반 소지다. 창구를 늘리는 것보다 **하나를 실제로 확인하는 게** 핵심이다.

> ⚠️ **이 문단의 '문의' 행은 2026-08-05 에 바뀌었다** — mailto 대신 **인앱 폼**을 열고 라벨도 `'개인정보 문의'` 로 좁혔다. 최신은 [문의 창구 정리](#문의-창구-정리-2026-08-05) — 지금은 **메뉴 → 고객센터 → '문의하기'** 인앱 폼이다. 아래 문단은 그 행이 왜 생겼는지의 기록으로 남긴다.

그래서 **법적 고지 화면에 '문의' 행(mailto)** 을 곁가지로 넣었다. 그 주소가 privacy.html 을 열어 스크롤해야만 보이던 걸 **두 단계로 줄인 것**이고, 개인정보 요구 접수 경로의 실질적 접근성을 올린다. 메일 앱을 못 열면 주소를 클립보드에 복사한다 — 아무 일도 안 하는 버튼은 창구가 없는 것과 같다.

### 문구 다듬기 (같은 날 2차)

구현 뒤 사용자와 문구를 다섯 번 주고받으며 다듬었다. 남길 만한 판단만:

- **유형은 칩 → 셀렉박스.** 4개짜리 칩이 세로로 3줄을 먹어 화면이 길어졌는데, 지출 카테고리가 이미 셀렉박스(아이콘+라벨)라 **선택 UI 언어를 앱 전체에서 하나로** 맞추는 쪽이 맞았다. 바꾸고 나니 스크롤 없이 전체 폼이 들어온다. 미선택 검증은 `Form`+validator 대신 **'보내기' 비활성**으로 — 이 화면엔 `Form` 이 없고, 그것 하나 때문에 `Form` 을 두는 건 과하다.
- **감사 인사의 자리.** 처음엔 "시간 내주셔서 고마워요" 를 완료 스낵바에 뒀다 — *아직 안 쓴 시간에 미리 감사하는 것보다 실제로 써준 뒤에 인사하는 게 자연스럽다*는 판단이었다. 최종적으로는 **상단 인트로가 감사를 전담**하고 스낵바는 담백한 한 문장이 됐다. 둘 다 인사하면 겹쳐서 옅어지기 때문이고, **인사가 어디에 있든 한 군데뿐이어야 한다**는 게 남는 규칙이다.
- **완료 문구를 하나로 통일.** 이메일 유무로 갈라 안내하던 걸 `의견이 성공적으로 보내졌어요.` 하나로 합쳤다. 잃은 것은 "적어주신 이메일로 답변이 간다"는 마지막 확인인데, 그 약속은 이미 이메일 칸 아래 안내가 하고 있다.
- **맞춤법은 손보되 뜻은 건드리지 않았다** — `가능한한`→`가능한 한`, `적어주시는게`→`적어주시는 게`, `구체적일 수록`→`구체적일수록`. 문체도 앱 기준인 해요체로 맞췄다(`큰 힘이 됩니다`→`돼요`). **내용 자체는 사용자가 쓴 문장을 그대로 뒀다.**

### 범위에서 뺀 것

- **스토어 리뷰 유도**(`in_app_review`, "칭찬은 스토어로") — 리서치에서 효과가 확인됐지만 별개 기능이라 백로그로.
- **rate limit** — 인증 + 길이 제한(1000자)으로 충분하다고 봤다. 사용자가 없는 지금 도배 방어는 과설계고, 남용이 실제로 보이면 그때.
- **관리자 UI** — 트리거는 여전히 UGC 모더레이션이다(회의록 ⑥ 과 동일 판단).

## 메뉴 앱 버전 행 (2026-07-28)

> 백로그 #12("메뉴 진입 시 매번 로딩")의 **잔여 갈래**를 정리한 회의. 본체(메뉴 낙관적 렌더)는 2026-07-26 에 끝났고, 남아 있던 두 갈래를 여기서 닫았다. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "앱 버전 / 강제·권장 업데이트" + "메뉴 화면".

### 안건 1 — '내 정보' 진입 스피너: **없애지 않는다**

사용자 지적으로 전제가 정리됐다. #12 의 원래 불만은 *"단순 메뉴인데 로딩이 걸린다"* 였고, 그건 메뉴가 **콘텐츠 없이도 그릴 수 있는 내비게이션 허브**인데 기다렸던 게 문제였다. MyInfoScreen 은 성격이 다르다 — 닉네임·성별이 **화면 콘텐츠 그 자체**다.

캐시(stale-while-revalidate)를 넣지 않기로 한 이유:
- 로그아웃·탈퇴 후 재로그인 때 **이전 계정 값이 한 프레임 비친다** (무효화를 한 곳이라도 빠뜨리면).
- 닉네임 쿨다운(`nicknameChangeAvailableFrom`)이 stale 하면 **잠금 안내가 틀린 시각을 말한다**.
- 얻는 것은 스피너 한 번, 잃는 것은 정확성. 교환이 성립하지 않는다.

### 안건 2 — '앱 버전' 행: 로딩의 원인이 네트워크가 아니었다

코드를 열어보니 **같은 질문을 두 번 하고 있었다.** [SessionGate](../tenk_app/lib/app/session_gate.dart) 가 부팅 때 강제 업데이트 게이트를 위해 `checkVersion()` 을 부르는데, [AppApi](../tenk_app/lib/data/app/app_api.dart) 에 캐시가 없어 메뉴가 열릴 때마다 또 물었다. **답을 앱이 이미 알고 있는데 버리고 다시 묻던 것**이지 네트워크가 꼭 필요했던 게 아니다.

**세 안을 비교**했다.

| 안 | 내용 | 판정 |
|---|---|---|
| A | 현행 유지 | ❌ 불필요한 왕복 1회 + `'확인 중…'` 플래시 |
| B | **탭하면 확인** (사용자 제안) | ❌ 아래 논거 |
| C | **부팅 판정 결과 재사용** | ✅ 채택 |

**B 를 기각한 논거 — 업데이트 안내는 push 여야지 pull 이면 안 된다.** 이 행의 진짜 일은 "물어보면 알려주기"가 아니라 **"업데이트가 있으면 먼저 알려주기"** 다. 탭해야만 알 수 있게 만들면 정작 알려야 할 순간에 아무도 누르지 않아 기능이 죽는다. 버전 숫자를 능동적으로 확인하러 오는 사람도 사실상 없다(보통 CS 문의 때뿐). 게다가 탭 결과를 보여줄 화면/다이얼로그가 필요해져 **단계가 줄지 않고 늘어난다**. 업계도 같은 방향이다 — 카카오톡(설정>앱관리)은 버전과 최신 여부를 **그 자리에** 띄우고, "업데이트 확인" 버튼은 데스크톱 앱 패턴이며 모바일에선 발견성이 낮다는 지적을 받는다.

**C 의 세부 결정**
1. **성공한 판정만 캐시한다.** 실패(`unknown`)를 캐시하지 않으면 getter 가 null 로 남고, **그 null 이 곧 "재확인 대상" 표시**가 된다 — 별도 플래그가 필요 없다.
2. **동기 getter로 노출.** `didChangeDependencies`(첫 build 이전)에서 읽어 `setState` 없이 채우므로 플래시가 원천적으로 없다.
3. **신선도는 문제가 아니다.** 버전 정책은 우리가 릴리스할 때만 바뀌고 콜드 스타트마다 다시 확인한다. 한 세션 stale 은 무해.
4. **행이 두꺼워 보이던 건 줄 수가 아니라 정렬 문제였다.** 이 행만 두 줄이라 목록에서 튀어 보였는데, 중간에 *"상태 라벨을 없애고 한 줄로"* 를 시도했다가 되돌렸다 — **상태는 상시 보이는 게 맞다**는 판단(원래의 push 논거와도 일관). 진짜 원인은 ListTile 이 leading/trailing 을 **두 줄 전체를 기준으로** 놓아 둘째 줄이 제목과 동등한 무게로 읽혔던 것.
   - **`titleAlignment: ListTileTitleAlignment.top` 은 답이 아니었다** — 이름과 달리 *제목 줄* 이 아니라 *타일 위쪽* 에 맞추는 거라, 아이콘·버전이 제목보다 위로 떠서 오히려 더 어긋나 보였다. 결국 **두 슬롯을 쓰지 않고 첫째 줄 요소를 전부 `title` 의 Row 에 담아** 같은 줄에 놓았다. 가로 위치는 ListTile 기본 치수(아이콘 24 + 간격 16)를 그대로 재현해 다른 항목과 맞추고 `subtitle` 은 40 들여쓴다.
   - 곁들여 버전 숫자를 `AppTypo.body`(제목과 같은 크기) + `inkSub` 로 키웠다 — 이 행의 주인공이라서.
5. **최신일 때도 탭되게 둔다** — 아무 반응 없는 행은 고장처럼 보인다. SnackBar 로 **"최신 버전을 이용 중이에요."**
   - 처음엔 "이미 최신 버전이에요." 로 썼다가 바꿨다. `이미` 를 붙이면 라벨의 단순 복사가 아니라 탭에 대한 응답으로 읽히는 이점이 있지만, 동시에 **"업데이트하러 눌렀다"고 전제**하게 된다 — 실제로는 그냥 버전을 확인하러 누르는 경우가 더 많다. 라벨과 겹치지 않으면서 전제도 없는 표현이 "이용 중이에요" 다. 문체는 앱 전체 기준인 **해요체** 유지("…입니다" 아님).

### 곁가지 — #14 의 잔여 갈래는 삭제

탈퇴 화면의 "잃는 것을 숫자로"(챌린지 N개·기록 N건)와 "탈퇴 전 영상 내보내기" 제안을 백로그에서 **뺐다**. 사유 화면은 *"경고를 반복하지 않고 감사 + 아쉬움 + 부탁으로 연다"* 는 규칙이 있어 숫자를 넣으려면 앞의 확인 다이얼로그로 가야 하는데, 그러면 **탈퇴가 가입보다 어려워진다** — 같은 회의록 ⑧ 의 대전제와 충돌한다.

## 탈퇴 UX (2026-07-27)

> #1("탈퇴 철회 흐름")을 구현한 **직후** 붙은 논의. "탈퇴 후 3개월 보관이 괜찮은 건가"에서 시작해 보관 기간·목적·재가입·통계까지 다시 짰다. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "인증 — 탈퇴 후 유예 기간". 여기엔 왜 이렇게 골랐는지만.

### 배경 — 철회를 붙이자 보관의 목적이 바뀌었다

원래 3개월 보관의 명분은 처리방침에 적힌 **"부정 이용 방지 및 문의 대응"** 이었다. 그런데 따져보니 Tenk 에는 그 목적이 성립하지 않는다.

| 실무에서 보관하는 이유 | Tenk |
|---|---|
| 재가입 어뷰징 방지 (쿠폰·리워드·무료체험 재취득) | ❌ 결제·보상이 없어 유인 자체가 없음 |
| 분쟁·신고 대응 (커머스 클레임, UGC 신고) | ❌ 신고 체계가 아직 없음 (생기면 재검토) |
| **탈퇴 철회 / 실수 복구** | ✅ #1 로 방금 만든 그것 |

PIPA 원칙은 목적 달성 시 **지체 없이 파기**이고, 보관은 법령상 보존 의무나 별도 동의가 있을 때의 예외다. Tenk 은 결제·거래가 없어 전자상거래법 보존 대상도 아니다. 즉 **처리방침에 목적을 적는 것과 그 목적이 근거가 되는 것은 다르고**, 실질적 근거는 "철회 대응" 하나만 남았다. (법률 자문이 아니라 판단 — 검수는 §0 백로그.)

### 사용자가 제기한 두 문제

1. **"탈퇴 후 재가입이 바로 안 되는 UX 가 싫다"** — 유예 기간이 재가입 장벽이 되면 안 된다.
2. **"탈퇴 즉시 다 지우면 탈퇴 사유·통계 분석을 못 한다"** — 아쉽다.

그리고 이 둘과 철회가 서로 충돌하는 것처럼 보였다("철회를 보장하려고 데이터를 들고 있으면 재가입이 막힌다").

### 결정 사항

1. **유예 기간 3개월 → 1개월.** 재가입 장벽이 아니라 순수한 철회 유예가 되면 길게 잡을 이유가 없다. 실수를 깨닫는 데 걸리는 시간이 기준 (구글 20일·인스타 30일·디스코드 14일 등과 같은 범위).
2. **복귀 시 철회/재가입을 사용자가 고른다.** 돌아온 사람은 *기록을 되찾으러 온 사람* 과 *리셋하러 온 사람* 으로 갈린다. 후자에게 철회를 강요하는 것이 정확히 문제 ①이 지적한 UX다.
3. **"새로 시작하기" 는 옛 계정을 즉시 파기한다.** 그래야 유예를 기다리지 않고 곧바로 재가입된다. `(provider, provider_user_id)` unique 도 이걸로 자연히 풀린다.
4. **탈퇴 통계용 원본 보관은 기각.** raw 를 남기고 `user_id` 만 끊는 건 익명이 아니라 **가명처리**라 여전히 개인정보고, 안전조치·결합제한 의무가 붙어 "3개월 논쟁"이 이름만 바꿔 돌아온다. 게다가 **영상(얼굴이 곧 식별자)·자유 텍스트(내용·한 줄 평)는 익명화 자체가 불가능**하다.
5. **익명 집계 로그(`withdrawal_log`)도 두지 않는다.** 파기 직전 숫자 한 줄만 남기는 안(챌린지 수·이용 일수·마지막 활동 후 경과일·사유 코드)을 검토했고 PIPA 부담 없이 문제 ②를 풀 수 있었지만, **현 단계에 과하다는 사용자 판단으로 채택하지 않음**. 나중에 탈퇴 분석이 실제로 필요해지면 이 안을 꺼내 쓸 것 — 원본 보관으로 돌아가지 말고.
6. **보관 목적 문구를 "탈퇴 철회 대응" 으로 교체.** privacy.html §3 · delete-account.html 동시 갱신.

### 탈퇴 확인 다이얼로그는 철회를 안내하지 않는다

별도로 결정한 항목. 탈퇴를 결심한 사람에게 "되돌릴 수 있어요"는 결정을 흐리는 잡음이라, **철회는 실제로 돌아왔을 때 로그인 화면에서만** 알린다. 단 예전 문구 "영구히 삭제되고 복구할 수 없어요" 로도 되돌릴 수 없다 — 철회가 생긴 뒤로 거짓이 됐다. 그래서 참이면서 철회를 광고하지 않는 문장으로: *"탈퇴하면 모든 챌린지와 기록을 더 이상 볼 수 없고, 일정 기간이 지나면 완전히 삭제돼요."*

구성도 바꿨다 — **제목 없이 설명 → 질문("정말 탈퇴하시겠어요?")이 이어지는 한 문단**. 제목으로 먼저 물으면 사용자가 답을 정한 뒤에 근거를 읽게 되고, 설명이 결정에 반영되지 않는다. 질문을 굵게·크게 강조하는 안도 시도했다가 **뺐다** — 문장이 끊겨 보여서, 위계 없이 한 호흡으로 읽히는 쪽이 낫다는 판단(왼쪽 정렬 + 단일 `AppTypo.body`).

**UI 카피와 법적 고지는 기준이 다르다** — privacy.html·delete-account.html 은 보관 기간 중 처리 방식을 사실대로 적어야 하는 문서라 철회·재가입을 **명시**한다.

### 복귀 선택 다이얼로그는 버튼 라벨에 기대지 않는다

"이어서 쓰기" 만 보여주면 **탈퇴한 사람에게는 말이 안 된다** — *탈퇴했는데 뭘 이어서 쓴다는 거지?* 로 읽힌다. 그래서 본문 한 문단에서 두 선택지의 결과를 다 밝히고(철회 = 이전 기록 그대로 / 새로 시작 = 이전 기록 전부 삭제), 라벨도 `탈퇴 철회` 로 바꿨다. 버튼은 한 줄에 3개(`취소`/`새로 시작`/`탈퇴 철회`)이며 폭을 2:3:3 으로 고정한다 — 테마 기본 버튼 스타일로는 좁은 기기에서 Material 이 세로로 접는다.

재가입 2차 확인은 **만들었다가 제거**했다. 본문이 이미 삭제를 말하고 같은 다이얼로그에 취소가 있어 되돌릴 자리가 이미 한 번 있으므로, 확인을 한 겹 더 두는 건 마찰만 늘린다. 대신 `새로 시작` 을 danger 색으로 표시해 파괴적 선택임을 남긴다.

### 후속 — 탈퇴 사유는 결국 받기로 (2026-07-28)

위에서 "익명 집계 로그는 현 단계에 과하다" 로 결론냈지만, 이어진 논의에서 **탈퇴 사유는 받기로** 뒤집혔다. 다만 앞선 결론과 모순은 아니다 — 기각한 건 챌린지 수·이용 일수 같은 **7~8컬럼짜리 행동 집계**였고, 채택한 건 **`reason_code` + `detail` + `created_dt` 3컬럼**뿐이다.

저장 위치는 세 후보 중 **익명 테이블**을 골랐다.

| 후보 | 판단 |
|---|---|
| `user.withdrawal_reason` 컬럼 | ❌ 계정과 함께 1개월 뒤 사라져 누적 분석 불가 + 개인정보라 privacy 수집표에 항목 추가 |
| **익명 테이블 `withdrawal_feedback`** | ✅ user_id 없음 → 개인정보 아님 → 고지 불필요·영구 보존·**계정 파기 후에도 생존** |
| 외부 폼 링크 | ❌ 응답률 사실상 0 |

**순서는 "확인 다이얼로그 → 사유 화면 → 탈퇴 처리"** 다. 사유를 먼저 묻고 확인을 나중에 받는 안도 만들어봤지만, 아직 마음을 못 정한 사람에게 설문을 먼저 들이밀면 **설문이 만류 장치처럼 읽히고 답도 부정확해진다**. 업계 통례도 "취소 의사를 확정한 뒤의 마이크로 설문" 이고, 실제 사례들이 공통으로 지적하는 것도 ① 문항은 최소 ② 수집 목적을 그 자리에서 밝힐 것(그래야 솔직해진다) ③ 실제 이유가 목록에 없으면 아무거나 찍으므로 '기타 + 자유 입력'이 필수 ④ **만류 버튼을 진행 버튼과 나란히 두지 말 것**(어느 쪽이 진행인지 헷갈린다) 였다. 사유 화면은 이미 확정한 사람을 상대하므로 경고를 반복하지 않고 **감사 + 아쉬움 + 부탁**으로 연다.

### 국내 앱 7종 조사 → 문구·선택지 설계

화면 문구를 처음부터 다시 짜면서 국내 서비스들의 탈퇴 화면을 조사했다.

| 앱 | 방식 | 배울 점 |
|---|---|---|
| **토스** | 사유별 **맞춤 해결책** 제시 + '넘어가기' | 스킵 경로를 명시적으로 둔다. 해결책 제시는 만류 기능이 있는 서비스의 사치 — Tenk 엔 과함 |
| **밀리의 서재** | 감성적 문구 + **수집 목적 안내** | 왜 묻는지 밝히면 솔직한 답이 온다 |
| **배달의민족** | "계정 삭제하기" 완화 표현 + 유의사항 확인 후 버튼 활성 | Tenk 은 법적 명확성 때문에 '회원 탈퇴' 유지 |
| **더팀스** | **문장형 해요체 선택지 5개**("구직 활동을 종료했어요"), 기본 미선택 | 서비스 맥락에 붙은 문장형 + 어미 통일. **이 방식을 채택** |
| **포스타입** | 필수 8개, 어미 제각각("목적", "많아서") | 표현이 안 통일되면 훑어보기 어렵다 (반면교사) |
| **마켓컬리** | 사유 8개 선택 후 탈퇴 | 개수가 많으면 고르는 시간이 늘어난다 |
| **번개장터** | 사유 **필수** + 다중 확인 | 필수화는 탈퇴를 어렵게 만드는 쪽 (반면교사) |

> 브런치·네이버·카카오·구글은 아예 사유를 묻지 않는다 — 묻는 것 자체가 필수는 아니라는 참고점.

여기서 뽑은 규칙: ① 구성은 **감사 → 사유 요청 + 개선 약속 → 선택지** ② 선택지는 **문장형 해요체로 어미 통일**, '기타'만 명사 ③ **6개**(9개는 과함) ④ 필수화 금지, 다만 '건너뛰기' 버튼 대신 **"답하지 않으셔도 괜찮아요"** 한 문장으로 처리 ⑤ 이미 확정한 사람이라 경고를 반복하지 않는다.

**사유는 절대 선택**이고 '건너뛰기' 버튼은 두지 않았다 — 아무것도 안 고르고 '탈퇴하기' 를 누르는 게 곧 건너뛰기라서, 버튼을 더 두면 무엇을 눌러야 넘어가는지가 되레 헷갈린다. 자유 서술은 '기타' 를 고른 경우에만 저장하고(다른 사유면 엔티티가 버린다) 본인 정보가 섞일 수 있어 "개인정보는 적지 말아 주세요" 고지 + 200자 제한을 뒀다.

### 다루지 않은 것 (백로그 후보)

좋은 탈퇴 UX 의 나머지 요소로 정리만 해둔 것 — **탈퇴 시 잃는 것을 숫자로 보여주기**("챌린지 3개·기록 47건·영상 12개", 백엔드 집계 엔드포인트 필요), **탈퇴 전 영상 export 제안**(Tenk 에만 있는 기능이라 궁합이 좋다). 둘 다 범위 밖.

## 닉네임 쿨다운 안내 문구 (2026-07-26)

> #11("닉네임 변경 안내 날짜 텍스트 삭제")에서 출발해 **제한 규칙 자체**와 **안내 문구 형식**까지 바뀐 건. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "닉네임". 여기엔 왜 이 형식인지만.

### 배경 — 안내와 규칙이 어긋나 있었다

앱 안내문은 "변경 후 **24시간** 동안은 다시 변경할 수 없어요" 인데, 실제 판정은 `today > 마지막변경일` = **다음 날 자정**이었다. 밤 11시에 바꾸면 **1시간 뒤** 다시 바뀌는 구멍. 안내를 규칙에 맞출지 규칙을 안내에 맞출지 골라야 했고, **규칙을 24시간으로** 통일하기로 했다 (사용자 결정) — 문구를 고치는 쪽은 구멍을 명문화하는 셈이라.

### 결정 사항

1. **상시 라벨 제거, 탭했을 때만 안내.** 닉네임 행에는 `lock_outline` 아이콘만. 평소 화면에 날짜가 박혀 있는 건 잡음이고, 바꾸려고 눌렀을 때 알려주면 충분하다.
2. **문구 = 규칙 먼저 + 가능 시점 짧게.** `닉네임은 24시간에 한 번만 바꿀 수 있어요. 내일 오후 10시 11분부터 가능해요.`
3. **날짜는 절대 표기 대신 now 기준 오늘/내일 라벨.** 쿨다운이 정확히 24시간이라 변경 직후엔 항상 '내일', 다음 날 열면 '오늘'로 바뀐다. 연도는 넣지 않는다.
4. **시각은 오전/오후 + 분** (정각이면 분 생략). 24시간제 `22:11` 보다 읽었을 때 자연스러운 쪽.

### 왜 이 형식인가 — 쿨다운 길이에 따라 표기법이 갈린다

한국 앱들의 일반적 관례를 정리하면:

| 쿨다운 | 표기 | 이유 |
|---|---|---|
| 초·분 (인증번호 재발송) | 카운트다운 숫자 (`59초 후 재전송`) | 줄어드는 게 보여야 기다릴 마음이 듦 |
| **시간 (우리 케이스)** | **상대 시간 또는 오늘/내일 + 시각** | 절대 시각만 주면 사용자가 뺄셈해야 함 |
| 일·월 (닉네임 30일 제한 등) | 절대 날짜 (`8월 25일부터`) | "30일 뒤"는 달력을 봐야 해서 오히려 불친절 |

상대 표현은 단위가 커질수록 계획을 못 세우게 되고, 절대 표현은 단위가 작아질수록 뺄셈을 강요한다. 24시간은 그 경계라 **오늘/내일 라벨 + 시각**이 둘의 장점을 취한다.

토스가 공개한 라이팅 원칙 중 직결되는 것 — **Weed cutting**(잡초 제거: 연도·"다시"·"이후에" 삭제), **Focus on key message**(방금 자기가 바꾼 걸 아는 사용자에게 이유를 재설명하지 않음), **Suggest over force**("변경할 수 없어요" 대신 "~부터 가능해요"), **Easy to speak**("14시 32분" 대신 "오후 2시 32분"). 다만 **시간·숫자 표기 세칙은 토스도 공개하지 않았다** — 위 표는 관례 정리이지 인용이 아니다.

### 회귀 방지

- 문구에 연도·"다시"·"이후에"를 다시 넣지 말 것 (잡초).
- 규칙을 날짜/자정 기준으로 되돌리지 말 것 — 위 구멍이 되살아나고 안내문과 다시 어긋난다.
- 쿨다운 상수는 `UserService.NICKNAME_CHANGE_COOLDOWN`(판정)과 `UserResponse.computeAvailableFrom`(안내 시각) **양쪽에 있다**. 하나만 바꾸면 "가능하다고 안내했는데 거부당함"이 된다.

## 앱 버전·업데이트 게이트 회의록 (2026-07-26)

> 메뉴에 "앱 버전 + 최신 여부"를 넣으려다 "최신 버전을 서버가 어떻게 아나"로 번져 #5(강제/권장 업데이트)까지 함께 설계한 회의. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "앱 버전 / 강제·권장 업데이트". 여기엔 **왜 이 방식을 골랐나 + 버린 대안**만.

### 배경 — 왜 서버가 필요한가

- 메뉴에 버전만 보여주는 건 `package_info_plus` 로 끝나지만, **"최신입니까?"** 를 판정하려면 *최신 버전이 뭔지* 를 어딘가에서 알아야 한다. 내 버전(1.0.0)만으로는 알 수 없다.
- 이 "최신 여부"는 본질적으로 #5(강제/권장 업데이트)와 **같은 데이터**(서버가 아는 최신/최소 버전)를 쓴다 → 둘을 한 번에 설계.

### 결정 사항

1. **판정은 서버가 진실의 원천.** 클라는 semver 비교를 하지 않고 상태(`LATEST`/`UPDATE_AVAILABLE`/`UPDATE_REQUIRED`)만 받는다. 이유: **강제 기준선(min)을 재배포·앱출시 없이 바꾸려면** 로직이 서버에 있어야 함. (닉네임·연령 검증과 같은 "서버가 원천" 원칙.)
2. **정책 저장 = `app_config` 단일 행 (DB, "B-sql" 방식).** `min_supported_version`/`latest_version`/`android_store_url`/`ios_store_url`. **값 갱신은 관리자 UI 없이 SQL** — TESTER 승격과 동일한 운영. `GET /api/app/version?platform&currentVersion`(PERMIT_ALL, 부팅 게이트).
3. **클라 게이트**: [SessionGate](../tenk_app/lib/app/session_gate.dart) 가 버전을 **가장 먼저** 판정(로그인·동의보다 상위 차단). 강제=풀스크린 차단, 권장=목적지 위 1회 안내. fail-open(서버·버전 이상 시 미적용 — 사용자를 잠그지 않는다).
4. **관리자 패널은 지금 짓지 않는다 — 백로그.** 현재 관리자 제어 대상은 TESTER 승격 + 버전 정책 2개뿐, 둘 다 저빈도 SQL 로 충분. 패널(ADMIN role+인증+웹 화면)은 **출시 후 UGC 모더레이션(신고)** 이 생겨 SQL 로 감당 안 될 때 착수. 그때 이 값들이 전부 "DB 행 편집" 이라 패널에 자연히 흡수.

### 검토했다 버린 대안

- **ⓐ 설정 파일(yaml/env)에 버전을 둔다(A안)**: 가장 단순(테이블 없음)하나 버전을 올릴 때마다 **백엔드 재배포(최소 컨테이너 재시작)** 가 필요. "재배포 없이 SQL 한 줄" 을 원해서 B-sql 채택. (env 로 빼면 재빌드까진 아니고 재시작이지만, 그것도 떼고 싶다는 요구.)
- **ⓑ 관리자 화면(B-admin)으로 버전 입력**: 재배포는 없지만 인증·화면·권한을 지금 세우는 건 값 2개에 과설계. TESTER 승격이 이미 SQL 운영이라 같은 방식(B-sql)이 일관.
- **ⓒ 코드 상수 하드코딩**: 코드 수정+재배포+앱 출시까지 묶여 최악. 폐기.
- **ⓓ Play In-App Update API(`in_app_update`)**: 백엔드 불필요하지만 **Play 설치본·안드로이드 한정**(직접 APK·iOS 미지원). 우리가 소유하는 서버 방식이 iOS 공통 커버라 우위.
- **ⓔ 클라가 semver 비교(서버는 값만 제공)**: 가능하나 정책(강제 기준)을 바꿀 때 **앱 재배포**가 필요해져 서버 판정의 이점이 사라짐. 서버 판정으로 결정.

## 테스터 로그인 회의록 (2026-07-25)

> Play 프로덕션 승격의 "앱 액세스 권한(App access)" 답안을 확정하려고 연 회의. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "테스트 지원 (devtools)", Play 폼 답안은 [play-console-app-content.md](play-console-app-content.md) §2. 여기엔 **왜 이 방식을 골랐나 + 검토했다 버린 대안**만.

### 배경 — 전제가 바뀌었다

- 심사자 로그인을 **이메일 전용 카카오계정**(전화·본인인증 없이 `accounts.kakao.com` 가입)으로 해결할 수 있음을 에뮬레이터에서 확인(2026-07-21). → 여분 번호·앱 내 우회 없이 데모 계정으로 App access 를 채울 수 있게 됨.
- 그전까지는 프로덕션 빌드에 **devtools 테스트 로그인**(카카오 우회 + 공유 키)을 남겨 심사자에게 안내하는 잠정안이 유력했다.

### 결정 사항

1. **App access = 데모 카카오 계정.** 심사자는 순정 앱에 데모 카카오 계정으로 로그인. 앱·서버에 우회 코드 0.
2. **앱 내 테스트 로그인 완전 제거** — 로그인 화면 버튼 + `AuthRepository.loginAsTest` + `AuthApi.testLogin` + `_TestSlotDialog` + `test_config.dart` 삭제.
3. **서버 테스트 로그인 엔드포인트 제거** — `POST /api/auth/test/login` + `TestSupportService.testLogin` + `TestLoginRequest` + `TestSupportProperties`(`tenk.test.*` yaml 포함) 삭제. `AuthProvider.TEST` 는 기존 로컬 데이터 호환용으로만 `@Deprecated` 로 잔존.
4. **시딩(테스트 데이터)은 유지하되 계정 단위 권한으로 재게이팅** — `provider==TEST` 게이트를 `user.role == TESTER` 로 교체. 새 `user.role`(`UserRole { USER, TESTER }`) 컬럼 + `role.canUseTestTools()`. 내부 테스터는 **실제 카카오 계정을 DB 에서 `role='TESTER'` 로 승격**(SQL). `UserResponse.role` 로 클라가 '내 정보' 시딩 버튼을 게이팅. **전역 킬스위치(`tenk.test.enabled`)는 제거** — 플래그 없는 계정 = 시딩 불가 = 그 자체가 킬스위치.

### 검토했다 버린 대안

- **ⓐ devtools 테스트 로그인을 프로덕션에 유지**(심사자에게 버튼 안내): 프로덕션 바이너리에 우회 경로가 남고 공유 키가 바이너리에서 추출 가능한 약점(키 새면 TEST 계정 양산 → 실계정 데이터엔 무접근이나 DB 오염). 데모 계정으로 대체 가능해지자 굳이 남길 이유가 없어 **폐기**.
- **"테스트 권한"을 boolean `test_enabled` 컬럼으로**: 동작은 같지만 나중에 `ADMIN` 등 운영 권한이 생기면 플래그가 늘어난다. **role 컬럼**이 확장 여지가 커서 채택.
- **"테스트 권한"을 yaml 허용목록(provider_user_id)으로**: 스키마 변경은 없지만 테스터 추가마다 재배포 필요 + "계정에 권한 부여"라는 멘탈 모델과 덜 맞음. **DB role 컬럼**으로 결정(SQL 로 즉시 승격, 재배포 불필요).
- **전역 킬스위치 유지**: role 게이트가 이미 충분한 잠금이라(승격 계정만 시딩, 그 계정 본인 데이터만 wipe) 이중 스위치는 불필요 → 제거해 단순화.

### iOS 심사 메모 (착수 시 안건 — 지금 결정 아님)

- 애플도 데모 계정 필요(App Store Connect → Sign-In Information). **같은 데모 카카오 계정 공용**.
- ⚠️ **가이드라인 4.8**: 제3자 소셜 로그인(카카오)만 제공하면 **Sign in with Apple** 병행이 심사 조건이 될 수 있음 → iOS 출시 전 `AppleTokenVerifier` + `/api/auth/apple/login` 추가 검토.
- ⚠️ 데모 계정 새 기기 인증(이메일 코드)을 심사자가 못 받으면 반려 위험 — 구글과 동일 리스크, 제출 전 재현.

## 연령 확인 · 선택 수집(성별) 회의록 (2026-07-21)

> Play 프로덕션 승격을 위한 "앱 콘텐츠" 마무리 과정에서 나온 결정들. 영구 규칙은 [../CLAUDE.md](../CLAUDE.md) "인증 — 연령 확인 / 성별", Play 폼 답안은 [play-console-app-content.md](play-console-app-content.md). 여기엔 **왜 이 방식을 골랐나 + 검토했다 버린 대안**만.

### 배경

- Play 타겟 연령대에 **13~15세를 포함**하기로 함(이용약관이 만 14세 기준이라 18+만 고르면 약관과 숫자가 어긋남). 그 순간 **가족 정책(Families Policy)** 대상이 된다.

### 결정 사항

1. **연령 확인은 우리 앱 자체 화면으로** 받는다(카카오 위임 불가). → [AgeGateScreen](../tenk_app/lib/presentation/legal/age_gate_screen.dart)
2. **만 14세 미만 → 계정 즉시 하드 삭제 + 거부**(U0006). soft delete 아님. → [UserService.verifyAge](../tenk-backend/src/main/java/com/hjson/tenk/domain/user/UserService.java)
3. **입력 방식은 생년월일**(생년만/나이 직접입력 아님).
4. **성별은 선택 수집** — 가입 흐름 밖('내 정보'), 목적 고지 + 언제든 철회. **필수/온보딩 아님.**

### 검토했다 버린 대안

- **"만 14세 이상입니다" 체크박스만** (사용자 최초 원안): **광고가 없는 지금은 이걸로도 정책상 충분**하다(중립적 연령 심사는 *인증 안 된 광고 SDK 를 쓰는* 혼합 타겟 앱에 걸리는 조항). 그럼에도 생년월일 화면을 유지한 이유 = ① 약관의 만 14세 기준을 실제로 강제하는 유일한 수단 ② 연령대 통계를 부수적으로 확보. **단, 나중에 광고를 붙이면 체크박스로는 부족** — 그땐 ⓐ 중립적 연령 심사 도입(지금 그것) 또는 ⓑ 전원을 아동/연령미상으로 취급해 인증 SDK 의 비맞춤 광고만 노출(구현 부담 0, eCPM 손해) 중 택1. 개인 앱엔 ⓑ 가 실용적.
- **카카오가 미성년자를 걸러주게 하기**: 불가. 로그인 단계 차단은 **카카오싱크(비즈앱 전환 + 채널 연결 + 검수, 사업자 정보 필요)** 기능이고, `birthyear` 동의항목도 별도 수집 권한 심사가 필요한 데다 **만 14세 판정·차단은 결국 우리 몫**이라 자체 화면을 피할 수 없다.
- **생년(4자리)만 받기**: UX·최소수집 측면에선 오히려 더 나은 안이었으나(자기신고라 정밀도 무의미, `birthyear` 가 업계 표준), 최종적으로 **생년월일 유지**로 결정.
- **나이 직접 입력**: 기각. 저장 순간부터 낡아 통계·정책 변경에 못 쓰고, 만 나이/세는 나이 혼동이 있다.
- **성별을 가입 시 필수/온보딩 수집**: 기각. 기능에 안 쓰이는 항목이라 **PIPA 최소수집 원칙 위반 소지** + 아동 포함 타겟이라 가족 정책상 더 민감 + 온보딩 마찰로 이탈. "가계부가 왜 성별을?" 인상도 비쌈.

### 함정·교훈

- **"거부하면서 삭제"는 같은 트랜잭션에서 안 된다.** 지우고 예외를 던지면 그 롤백에 삭제까지 휩쓸린다 → [purgeImmediately](../tenk-backend/src/main/java/com/hjson/tenk/domain/user/WithdrawnUserPurgeService.java) 를 `REQUIRES_NEW` 로 분리. 회귀 가드 [UserAgeVerificationIntegrationTest.underageIsRejectedAndPurged](../tenk-backend/src/test/java/com/hjson/tenk/domain/user/UserAgeVerificationIntegrationTest.java).
- **AgeGateScreen 의 중립성 3원칙은 정책 요건**(컷오프 비노출 · 기본값 없음 · 이탈 차단) — 임의로 바꾸지 말 것.
- **Google 계정 삭제 정책은 앱 밖 삭제 요청 URL 을 요구** → [delete-account.html](../tenk-backend/src/main/resources/static/delete-account.html) 신설(앱 내 탈퇴만으론 부족).

## 기록 수정/촬영 분리 회의록 (2026-05-23)

> "지출은 영상 필수 / 카메라가 기록 화면에 인라인 / 등록 후 수정 불가" 세 가지를 한 번에 정리한 회의. 회의록 형식이 아니라 사용자 지시 → 명확화 질의 1회 → 합의된 결정의 요약.

### 사용자 요구 (원문 요약)
1. 영상 첨부는 지출/무지출 양쪽 모두 **선택**.
2. 영상 촬영은 기록 화면 안이 아니라 **전용 카메라 화면**.
3. 기록 카드 탭 → **수정 화면** 진입. 내용 + 영상 모두 수정 (영상은 추가/교체/삭제).

### 결정 사항

| # | 항목 | 결정 |
|---|---|---|
| 1 | 지출 영상 | 필수 → **선택**. 백엔드 `AMOUNT_VIDEO_REQUIRED` 에러코드 자체 삭제. `LocalFileStorage.store()` 의 null 가드는 호출자 책임으로 옮기고 들어오면 `INVALID_INPUT` (프로그래머 오류). |
| 2 | 촬영 화면 분리 | 신규 [AmountCameraScreen](../tenk_app/lib/presentation/amount/amount_camera_screen.dart). `Navigator.pop<String>(path)` 로 결과 반환. 사용 안 한 임시 파일은 본인이 정리 (호출자 책임 X). |
| 3 | 영상 첨부 UI 공용 | 신규 [VideoAttachmentSection](../tenk_app/lib/presentation/amount/widgets/video_attachment_section.dart). "없음 → 촬영하기 / 있음 → 다시 촬영 + 삭제" 두 상태만. record + edit 화면 공용. |
| 4 | 수정 화면 진입 | 기록 카드 탭. 기존 카드의 X 삭제 버튼은 **제거** — 삭제는 수정 화면 안의 별도 버튼에서만. |
| 5 | 지출 일시 수정 범위 | **시간만**, 날짜 고정. 백엔드 DTO 는 `LocalTime` 만 받고 기존 spentDt 의 LocalDate 와 결합. 날짜를 바꾸고 싶으면 삭제 후 재등록. (사용자 지시) |
| 6 | 무지출 일시 수정 | 불가. 서버 now() 강제 그대로. 수정 화면에 일시 섹션 자체 숨김. |
| 7 | 영상 액션 표현 | `videoAction: KEEP / REMOVE / REPLACE` enum. REPLACE 면 video part 필수. backend enum + Flutter enum 1:1 매칭. |
| 8 | 배지 재평가 | **안 한다**. 수정에서는 날짜·noSpend 여부가 안 바뀌므로 STREAK/NO_SPEND 가 변할 수 없음. 영상만 바꿔도 마찬가지. |
| 9 | 종료/시작 전 챌린지 | 수정도 record 와 동일하게 `CHALLENGE_ALREADY_FINISHED` / `CHALLENGE_NOT_STARTED` 로 막음. |
| 10 | 응답 형태 | record 는 기존 `AmountRecordResult` 유지, update 는 갱신된 `AmountResponse` 단건. |

### 동기 사유 (왜 이번에 바꾸나)
- **영상 필수 강제는 마찰** — 2초 영상 자체가 부담스러운 사용자가 있어 진입을 가로막고 있었음. export 는 "있는 영상만 합친다" 정책이라 누락이 생겨도 파이프라인은 영향 없음.
- **카메라 인라인은 폼을 무겁게** — 카메라 초기화 실패가 폼 입력 자체를 막는 케이스가 있었음. 단계 분리로 폼 / 촬영을 독립화.
- **수정 불가의 비용 > 구현 비용** — 이미 `Amount.update()` 가 있었고 엔드포인트만 없는 상태였음. 영상 핸들링까지 합쳐도 PUT 하나로 끝남.

## 결과 카드 회의록 (2026-05-26)

> 영상 내보내기와는 무관하게 챌린지 확정 후 결과를 1장 카드로 보여주는 기능. 영상 export 와는 별개 도메인이지만 마지막 클립으로 합성하는 옵션도 같이 결정.

### 사용자 요구사항 (원문 요약)
- 챌린지 종료 후 그 챌린지에 대한 결과 카드. 이미지로 저장하기, 내보내기.
- 영상 내보내기 했을 때 제일 마지막에도 결과 카드를 포함시킬 수 있게.

### 결정 사항 (9)
1. **진입점 = finalize 직후 자동 + 챌린지 상세 진입점 둘 다**. 확정 순간엔 페이오프 모먼트로 자동 풀스크린 push, 나중에 공유하려고 다시 볼 수 있게 상세 화면에 카드 한 장 추가.
2. **비율 = 세로 9:16 / 480x864**. 영상 export 해상도와 1:1 — 마지막 정지 카드로 그대로 붙일 수 있고 (스케일링 0), 스토리/릴스 공유 동선과 일치.
3. **영상 export 포함 = 체크박스 (기본 ON)**. export 화면에 "결과 카드를 영상 끝에 포함" 토글. 끄고 싶은 사용자만 끔.
4. **모달 충돌 = 배지 모달 → 결과 카드 순차**. 결과 카드 안에 획득 배지 row 가 있지만 배지 모달도 그대로 진행해 페이오프 계단을 만든다. 결과 카드가 페이오프 통합 후보였지만, 챌린지 성과가 헤드라인이고 배지는 후속 보상이라 두 단계로 가는 게 명확.
5. **닉네임 = "○○님의 만원 챌린지" 포함** (카카오 닉네임 fetch). 카드 진입 시점에 한 번 `/api/users/me` 호출. fetch 실패하면 그냥 "만원 챌린지" 로 폴백 — 안 깨짐. 영상 export 의 카드는 fetch 안 함 (compose 시작 지연 회피).
6. **성공/실패 색 = 드라마틱 대비**. 성공 = 따뜻한 노랑 그라데이션 + 보라 accent + 🎉. 실패 = 그레이 그라데이션 + 다크 그레이 accent + 💪. 결과가 증명사진처럼 명확해야.
7. **카테고리 분포 제외**. 9:16 자리 빡빡 + 숫자/배지로 정보감 충분. 통계 카드 = 목표/사용/절약(또는 초과)/무지출 4개 라인만.
8. **표시 형태 = 풀스크린 라우트** (모달 X). 480x864 비율을 화면에 띄우면 거의 꽉 차 모달로 띄울 이유가 없음. 영상 export 결과 화면 ([export_result_screen.dart](../tenk_app/lib/presentation/challenge/export/export_result_screen.dart)) 의 갤러리 저장/공유 두 버튼 패턴 그대로 차용.
9. **영상 마지막 카드 정지 시간 = 3초**. 영상 클립 2초 + xfade 0.3초 흐름에 이어서 수자/배지/닉네임 읽을 시간 확보. 2.5초는 짧고 4초는 임팩트로 끝나야 하는 마지막을 늘어뜨림.

### 보류·미반영
- **닉네임 옵션화** — 카드에 닉네임 노출을 설정에서 끄는 토글은 안 둠 (설정 화면 자체가 아직 없음 — 회원가입 시 닉네임 설정 화면 백로그 작업 시 같이 검토).
- **결과 카드 자체 캐싱** — 같은 챌린지 결과 카드를 PNG 로 백엔드/디스크에 영구 저장은 안 함. 매번 challenge + amounts 응답으로 동적 생성 (가벼움).

### 함정·교훈
- **색은 ThemeData 안 쓰고 hardcode**. RepaintBoundary 캡처 시 ThemeData 가 영향 안 받게. 위젯 안에서 모든 색을 const Color 로 박아둠. 회귀 금지.
- **배지 자산 precache 필수**. Image.asset 의 첫 프레임이 placeholder 라 캡처에 비어 들어갈 수 있음. ResultCardCapture 가 호출 전 challenge.badges 전체를 precacheImage 로 미리 캐시.
- **off-screen Overlay + RepaintBoundary 패턴**. 위치는 안 보여도 layout/paint 가 정상 수행되고 RepaintBoundary 가 layer 를 그대로 캡처. Off-screen 좌표는 `-2*width` 로 충분히 멀게.
- **`_concatWithXfade` 가 단일 clipLen 가정**이었던 부분 — 마지막 3초 카드 추가로 가변 duration 으로 변경했음. 다른 가변 클립이 들어와도 그대로 동작. 회귀 시 단일 길이 가정 코드로 돌아가지 말 것.

### 보류 — 결과 카드 (영상 마지막 3초)

영상 끝에 "성공! 8,200/10,000원" 같은 결과 카드를 붙일지 vs 챌린지 확정 시 별도 결과 화면으로 보여줄지 미정.
챌린지 확정 화면 자체가 별도 의사결정 항목으로 분리될 가능성이 있어 영상 내보내기 구현 도중 함께 정리. (→ 위 "결과 카드 회의록"에서 결정됨)

### 구현 시 주의사항

- **백엔드 추가 작업 거의 없음** — 영상 다운로드 엔드포인트가 이미 있으면 그대로. 없으면 인증된 사용자가 자신의 amount 영상을 받을 수 있는 엔드포인트 1개 (현재 [MediaController](../tenk-backend/src/main/java/com/hjson/tenk/domain/media/MediaController.java) 확인 필요).
- **패키지/인코더 선택**: `ffmpeg_kit_flutter_new_video` (LGPL 'video' 변종) 사용 중. sw 인코더는 최종적으로 ffmpeg 내장 **`mpeg4` (MPEG-4 Part 2, LGPL)** 채택. 회의 결정 #1 의 "h264" 표현은 H.264 고집이 아니라 "표준 동영상 코덱" 의미였고 MP4 컨테이너에 MPEG-4 Part 2 도 어디서나 재생 가능하니 무방.
- **함정 — H.264/HEVC sw 인코더 다 막힘**: 후보를 다 돌려본 결과 ffmpeg_kit_flutter_new_video 환경에선 mpeg4 외 선택지가 없다. 다음은 모두 실격 — 같은 함정에 다시 들어가지 말 것:
  - `h264_mediacodec` (hw): lavfi `color` 소스/짧은(2초) 클립 인코딩 시 return code 0 인데 duration N/A + 스트림 없는 빈 컨테이너를 뱉는다. 정규화는 통과한 척 → concat 에서 `[N:v] matches no streams` 로 죽음. 디바이스/펌웨어 의존이라 재현이 일정치 않음.
  - `libx264` (sw H.264): GPL — 현재 'video' 변종 빌드에 미포함, 라이센스 이슈로 채택 X.
  - `libkvazaar` (sw HEVC): 빌드엔 있지만 native crash. ffmpeg `exit_program` → `of_close` → `avcodec_free_context` → `pthread_mutex_destroy` 에서 `FORTIFY: called on a destroyed mutex` SIGABRT. kvazaar 자체 스레드풀과 ffmpeg cleanup 의 더블 프리. 패키지 버그라 사용자 코드 우회 불가.
- **함정 — drawtext 한글 회귀 (ffmpeg 8.0)**: `ffmpeg_kit_flutter_new_video` 2.0.0 은 ffmpeg n8.0 (HarfBuzz 통합 drawtext) 을 쓰는데 multi-codepoint 한글 입력에서 **첫 글리프만 그리고 뒤를 silent drop** 한다. "무지출" → "무", "도시락 챙겼다" → "도", "Day 1 · 잔여 8,000원" → "D" 패턴. 다음 모두 무효였음 — drawtext 로 회귀 X:
  - `text='무지출'` 인라인, `textfile='...'` + `expansion=none`: 둘 다 같은 출력. textfile 내용은 hex dump 로 9바이트 (eb ac b4 ec a7 80 ec b6 9c) 전부 정확히 박혀있는데도 첫 글자만 렌더.
  - `text_shaping=0` 으로 HarfBuzz shaping path 우회 시도: 옵션은 수락되는데 출력 동일. ffmpeg 8.0 drawtext 가 옵션을 받기만 하고 실제로는 새 shaping path 만 쓰는 것으로 추정.
  - 폰트 교체 (Tmoney RoundWind → Pretendard): cmap 으로 한글 11172자 다 커버하는 폰트로 바꿔도 동일. 폰트 글리프 문제 아님.
  - `-loglevel verbose` 에서도 drawtext 가 어떤 경고도 안 뱉음 — 디버그 단서 0.
  - **해결**: drawtext 완전 폐기하고 Flutter `TextPainter` 로 PNG 그려 ffmpeg `overlay` 필터로 합성. Flutter/Skia 가 Android 시스템 폰트 (Noto Sans CJK) 폴백으로 한글 렌더 → ffmpeg 는 그냥 픽셀만 합성하니까 텍스트 렌더링 경로 자체를 차단. 구현은 [video_composer.dart](../tenk_app/lib/data/export/video_composer.dart) `_renderTextOverlayPng` / `_drawTextBlock`.
- **앱 크기**: `ffmpeg_kit_flutter_new_video` 빌드는 +30~50MB. 더 줄이고 싶으면 `_min` 계열도 mpeg4 는 들어있으므로 시도 가능.
- **메모리/배터리**: 30일치(최대 ~60개 클립 × 2초) 합성은 저사양 폰에서 수십 초 걸릴 수 있음. 캔슬 가능해야 함. ffmpeg_kit 의 `Session.cancel()` 활용.
- **자막 렌더**: ffmpeg drawtext 가 한글에서 막혀서 (위 함정) **Flutter TextPainter PNG + ffmpeg overlay** 로 갈아탐. 시스템 폰트 폴백을 쓰니까 별도 폰트 자산 불필요. 자막 폰트를 명시 지정하고 싶으면 [tenk_app/assets/fonts/Korean.ttf](../tenk_app/assets/fonts/) 를 pubspec.yaml `flutter.fonts` 에 family 로 등록 + `_drawTextBlock` 의 TextStyle 에 fontFamily 박기.
- **잔여금 카운트다운**: 한 클립(2초)에서 시작값→끝값으로 보간된 텍스트를 매 프레임 그리려면 drawtext 의 `t` 변수(현재 재생시간)와 expression 활용. 또는 클립 길이를 짧은 세그먼트로 쪼개고 각 세그먼트마다 다른 텍스트 — 후자가 단순.
- **음성 트랙 없음**: 원본 녹화가 `enableAudio:false` 라 입력에 오디오 트랙이 없을 수도 — ffmpeg 명령에 `-an` 명시 또는 무음 트랙 강제 생성으로 출력 일관성 확보.
